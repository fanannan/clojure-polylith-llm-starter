# QUESTIONS.md — 判断保留トラッカー

LLM が作業中に判断に迷った事項、設計判断が必要な事項を記録する。
**CLAUDE.md §7.3 撤退プロトコルの「D. 人間による設計判断を求める」の受け皿**でもある。

本ファイルは `project-memory/` 配下に置かれる。原則 13（MAINTAINERS_GUIDE.md §4）で定義される**判断保留（QUESTIONS）**の実装であり、同配下の KNOWLEDGE.md（生きた知識）、adr/（決定履歴）と役割が異なる。

---

## 0. 運用プロセス（MAINTAINERS_GUIDE.md 原則 11 の実装）

> **初期状態**: §2 オープンな質問 / §3 解決済み / §4 却下 は、テンプレート配布時は §2 にサンプル Q が 1 件、§3・§4 は空。**`CLAUDE.md` §8.0 の「未決判断の確認」は該当 Q なしで完了とみなし、LLM は次のステップに進む**（空スキャン後スキップ可）。

### 0.1 Q の状態遷移

```
                      [LLM が提起]
                           │
                           ▼
                      ┌─────────┐
                      │  open   │ ─── 2週間経過 ───→ エスカレーション（§0.6）
                      └────┬────┘
                           │ [ユーザが議論を開始]
                           ▼
                   ┌──────────────┐
                   │ in-discussion│
                   └──────┬───────┘
                          │ [回答確定]
                ┌─────────┼─────────┐
                │         │         │
                ▼         ▼         ▼
           ┌────────┐ ┌────────┐ ┌──────────────┐
           │resolved│ │wontfix │ │  superseded  │
           └───┬────┘ └────────┘ └──────────────┘
               │
               └─(必要に応じて)─→ KNOWLEDGE.md §X / adr/NNNN-topic.md に昇格

  別ルート: open → blocked （外部事情・他Q依存で保留）→ open に復帰
```

### 0.2 各状態の定義

| 状態 | 意味 | 遷移可能先 |
|---|---|---|
| **open** | LLM が提起した直後、ユーザ未対応 | in-discussion, blocked, wontfix |
| **in-discussion** | ユーザが回答・議論中 | resolved, wontfix, superseded |
| **blocked** | 他 Q や外部事情で対応保留 | open（解消時）、wontfix |
| **resolved** | 回答が反映された（§0.4 で確認済み）| — |
| **wontfix** | 議論の結果、対応しないと決定 | — |
| **superseded** | 別の Q に統合・代替された | — |

### 0.3 Q の記載フォーマット

```markdown
## Q-YYYY-MM-NNN: <1 行要約>
- **状態**: open / in-discussion / blocked / resolved / wontfix / superseded
- **提起日**: YYYY-MM-DD
- **更新日**: YYYY-MM-DD（状態遷移時に更新）
- **提起の経路**: 自己停止プロトコル §7.3 / Polylith 境界判断 / その他
- **文脈**: なぜこの判断が必要か（背景・制約）
- **選択肢**:
  - A. <案>: <利点・欠点>
  - B. <案>: <利点・欠点>
  - C. <案>: <利点・欠点>
- **推奨**: <LLM としての推奨案と理由>
- **影響範囲**: <変更が波及するファイル・モジュール>
- **反映先**: <resolved 時のみ記入。§0.5 の昇格先分類を参照>
```

### 0.4 解決確認プロセス（LLM が勝手に resolved にしない）

原則 2（規約だけでは守られない）の適用：

1. LLM は「解決した」と判定する前に、ユーザに**明示的に確認**する：
   > 「Q-YYYY-MM-NNN の回答を `<反映先>` に反映しました。`resolved` にしてよいでしょうか？」
2. ユーザが承認した時点で状態を `resolved` に変更、`更新日` と `反映先` を記入
3. **§0.5 の昇格先判定**を行い、必要なら KNOWLEDGE.md / ADR へ転記
4. **§0.7 のアーカイブに移動**（削除しない）

**LLM の独断による resolved 化は禁止**。削除も禁止（§0.7 参照）。

### 0.5 昇格先の判定（原則 13 の適用）

resolved Q の内容が、以下のいずれに該当するか判定する：

| 判定 | 昇格先 | 理由 |
|---|---|---|
| **現時点で有効な契約・不変条件・暗黙知で、今後も更新され続ける** | `KNOWLEDGE.md` の該当節 | 「生きた知識」として継続参照 |
| **なぜそう決めたかの設計判断で、今後改訂しない（改訂時は新 ADR 発行）** | `adr/NNNN-topic.md`（新規発行） | 「決定履歴」として不変保持 |
| **プロダクト仕様に影響する** | `DESIGN.md` の該当節 | 「仕様」として合意の起点 |
| **一度きりの判断で、継続参照の必要なし** | 昇格なし（アーカイブのみ） | 軌跡として残すだけで十分 |

**両方に該当する場合**（例: ADR として決定理由を残しつつ、契約として KNOWLEDGE にも書く）は、両方に記載してよい。ただし：
- **KNOWLEDGE.md の側には「背景: ADR-NNNN を参照」と短く書く**（詳細は ADR）
- **ADR の側には「関連 KNOWLEDGE: §X」を書く**（実装状況は KNOWLEDGE）
- Q の `反映先` 欄に両方を記載

### 0.6 エスカレーション

提起から 2 週間経過した `open` Q は、ユーザに再度確認を促す：

1. LLM が次回ユーザとの対話時に「Q-YYYY-MM-NNN は 2 週間 open です。対応を決めたいのですが」と言及
2. それでも確定しない場合、状態を `blocked` に移し、理由を記載

### 0.7 軌跡の保全（原則 10 の適用）

解決済み Q は削除せず、本ファイルの「§3 解決済み（アーカイブ）」に移動する。
アーカイブが 100 件を超えたら、`project-memory/questions-archive-YYYY.md` のような形で年次アーカイブに分離し、本ファイルは最新年のみを保持する。

### 0.8 LLM の自走禁止ルール

`open` または `in-discussion` 状態の Q に関わる箇所では：

- **推測で実装を進めない**
- 該当箇所のコードに `;; TODO(Q-YYYY-MM-NNN): <保留している判断>` を残す
- CI で `grep -rn "TODO(Q-" components bases development` により残存 Q を検出できるようにする（Polylith 構造では `src/` は存在せず、コードは `components/<n>/src`、`bases/<n>/src`、`development/src` に分散する）
- Q が `resolved` / `wontfix` / `superseded` になったら、対応する TODO コメントを削除する

### 0.9 自己停止プロトコル（CLAUDE.md §7）からの連携

§7.3 撤退プロトコルで選択肢 D（人間による設計判断を求める）を選んだ場合：

1. §7.3 の報告フォーマット（試みた内容・残障害・仮説）を、そのまま**本ファイルの新規 Q の `文脈` と `選択肢` に転記**
2. ID を採番（`Q-YYYY-MM-NNN`）、状態を `open` で記録
3. ユーザへの報告で「`project-memory/QUESTIONS.md` に Q-YYYY-MM-NNN として記録しました」と言及
4. 以降は §0.1 〜 §0.8 の通常運用に従う

### 0.10 スクラブ運用

スクラブ時期：月次（または機能リリース時）。実施者は人間またはユーザの指示を受けた LLM。

1. 全 `open` Q を点検
2. 2 週間経過したものは §0.6 のエスカレーション
3. 類似 Q は統合（一方を `superseded`、他方に集約）
4. 前提が変わって意味を失った Q は `wontfix` に
5. `blocked` の解消条件が既に満たされているものは `open` に戻す
6. アーカイブが肥大していたら年次分離を実施

## 1. 提起の優先対象（以下に該当したら必ず Q を立てる）

自己判断禁止の領域：

### 1.1 Polylith 構造判断

- 新規コンポーネントを切るかどうか
- 既存コンポーネントの分割・統合
- `interface.clj` の関数を変更・削除
- 新規 base / project の追加
- コンポーネント間の依存関係を変える判断
- 共通スキーマ・型の配置先

### 1.2 技術選定・設計

- brick（base / component）deps.edn へのライブラリ追加・変更（採用 stack の推奨反映、CLAUDE.md §6.2、選定論理は `project-guide/STACK_GUIDE.md`）
- 新しいライブラリの採用提案
- §1 原則（全域性・不変性・副作用隔離）の解釈で迷う場面
- 原則間の競合（例: 副作用隔離と性能のトレードオフ）

### 1.3 ドメイン・契約

- KNOWLEDGE.md に記載すべき新しい不変条件の発見
- 既存 KNOWLEDGE エントリとの矛盾に気づいた時
- DESIGN.md の仕様に曖昧さや矛盾を発見した時

### 1.4 CLAUDE.md §7 自己停止プロトコルで D を選択した時

§0.9 の連携手順に従い、必ず Q を立てる。
