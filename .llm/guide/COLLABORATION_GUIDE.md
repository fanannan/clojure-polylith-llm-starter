# COLLABORATION_GUIDE.md — LLM と人間の協働ガイド

本文書は、**LLM と人間が共同で開発を進める際のプロトコル**を規定する。
原則 11（判断とプロセスの対称性、`MAINTAINERS_GUIDE.md` §4）の観点から、**誰が何を決め・誰が何をし・どう連携するか**を明示する。

## 本文書の位置づけ

| ガイド | 扱う領域 |
|---|---|
| `CODING_GUIDE.md` | Clojure の書き方（実装の作法） |
| `POLYLITH_GUIDE.md` | Polylith の構造運用 |
| `BOOTSTRAP_GUIDE.md` | プロジェクト初期化時の LLM 側手順 |
| `MAINTAINERS_GUIDE.md` | テンプレート自体の保守 |
| **`COLLABORATION_GUIDE.md`（本文書）** | **LLM と人間の協働プロトコル** |

LLM がこれを読むタイミング：
- 協働方針に迷った時
- 曖昧性の扱い方で困った時
- 質問の粒度・タイミングで迷った時
- 複数の役割（実装者・仕様提案者・知識記録者等）の優先順位で迷った時

---

## 1. 本文書の目的

LLM 駆動開発では、**LLM の能力と同じくらい「人間との連携の質」が成果を左右する**。
以下の両方を同時に追求する：

- **人間の負担最小化**: 判断・承認に必要な思考量を減らす。些末な質問で疲弊させない
- **LLM の自走と安全性の両立**: 自己解釈で暴走せず、かといって些細な判断で毎回止まらない

この両立のために、**役割分担・曖昧性解消・対話プロトコル**を本文書で規定する。

## 2. 役割分担の基本原則

### 2.1 意思決定の 4 階層

作業中の各判断は、以下のいずれかに分類される：

| 階層 | 定義 | 担当 |
|---|---|---|
| **L0: 人間専権** | LLM は決定しない。ユーザに求められた場合のみ、判断材料・影響範囲・選択肢を整理する | 人間 |
| **L1: LLM 提案 + 人間承認必須** | LLM は提案のみ可。実施は承認後 | 人間が承認、LLM が実施 |
| **L2: LLM 実施 + 事後報告** | LLM が独断で実施し、結果を報告 | LLM が実施、人間は確認のみ |
| **L3: LLM 独断可** | 結果の報告も簡潔で可 | LLM のみ |

### 2.2 典型的な判断の階層マッピング

| 判断内容 | 階層 | 備考 |
|---|---|---|
| プロダクトの目的・スコープ・主要ユースケース | L0 | DESIGN.md §1-§3。LLM は決定しない。ユーザが骨子を示した後の文章化は L1 |
| 新ライブラリ追加 | L0 | CLAUDE.md §2 禁止事項 |
| 新規 base / project の追加 | L0 | CLAUDE.md §2 禁止事項 |
| コンポーネントの統合・分割 | L0 | 影響甚大 |
| brick（base / component）deps.edn へのライブラリ追加・変更 | L0 | CLAUDE.md §2 禁止事項。推奨カタログは `STACK_GUIDE.md` |
| 新規 component の追加 | L1 | `poly create component` の実行は承認後 |
| `interface.clj` の関数追加 | L1 | シグネチャと Malli スキーマを提示して承認 |
| DESIGN.md の改訂提案 | L1 | 編集は承認後、LLM 独断禁止 |
| KNOWLEDGE.md へのエントリ追加提案 | L1 | §6.1 参照 |
| ADR の発行（決定内容がゲートまたは対話で承認済の場合） | **L2** | 決定は既に承認済なので ADR は記録の形式化に過ぎない。誤記は新 ADR で supersede（CLAUDE.md §1.2.5 失敗早期検知と承認設計）。§6.2 参照 |
| ADR の発行（決定内容が未承認の場合） | L1 | 通常この状況は発生しない（決定は必ず先行する）。発生時は Q を立てて決定自体を先行確定する |
| 推奨カタログ記載済みの技術選定 | L1 | ゲート 1 承認。LLM は該当する機能カテゴリと推奨理由を示す。依存追加承認とは別 |
| 推奨カタログ未記載の技術選定 | L0 | LLM は「未記載領域」と明示して判断材料を整理する。採用可否は人間が決定し、採用後の ADR 発行は L2 |
| Q の起票 | L2 | 起票自体は LLM が判断、内容は人間が検討 |
| Q の状態変更（open → in-discussion） | L2 | ユーザが議論を始めた時点で LLM が変更 |
| Q を resolved にする | L2 | 解決根拠が明示されている場合は事後報告。曖昧な場合のみ確認（QUESTIONS.md §0.4） |
| `core.clj` 内の実装（Malli 契約付き） | L2 | 実装、テスト追加、`poly check`/`test` まで実行して報告 |
| リファクタリング（同一 interface 維持） | L2 | ただし 50 行超の変更は L1 |
| ドキュメント内の誤字脱字修正 | L3 | テンプレート本体の文書は L1 に格上げ |
| コミットメッセージの文面 | L3 | ただしロジック変更とフォーマット変更は別コミット |

**判断の階層が不明な場合は、上位（より慎重な側）を選ぶ**。例: L1 か L2 で迷ったら L1 として承認を求める。

### 2.3 4 種文書の編集権限マトリクス

原則 13 で定義される 4 種文書に対する LLM の権限。**本節は CLAUDE.md §2 禁止事項の詳細規定であり、文書編集権限に関する詳細マッピングの正本**：

| 文書 | LLM 独断編集 | LLM 提案 + 承認 | 不変（改訂不可） | 承認手順の詳細 |
|---|---|---|---|---|
| `DESIGN.md` | ❌ | ✅（改訂提案） | 全体不変ではないが大きな方針変更は ADR 経由 | `DESIGN.md` §0 本ファイルの埋め方 |
| `.llm/memory/KNOWLEDGE.md` | ❌（§0.7 の限定例外のみ） | ✅（追加・更新・廃止提案） | — | `KNOWLEDGE.md` §0.7 LLM による更新の承認 |
| `.llm/memory/adr/NNNN-topic.md` | ✅（新規発行、決定内容が事前承認済の場合のみ、L2） | ✅（決定内容が未承認の場合は L1） | **一度 accepted は本文不変**、改訂は新 ADR で supersede | `adr/README.md` 運用手順、§2.2 ADR 階層マッピング |
| `.llm/memory/adr/README.md` | ❌ | 🟡（運用ルール変更は慎重） | — | `MAINTAINERS_GUIDE.md` §5.7.2 |
| `.llm/memory/QUESTIONS.md` | 🟡（Q 起票・状態遷移の一部は可、resolved 化は §0.4 に従う） | ✅（解決根拠が曖昧な場合のみ確認） | アーカイブ済み Q は不変 | `QUESTIONS.md` §0.4 解決処理 |
| `CLAUDE.md` / `.llm/guide/` 配下 | ❌ | ✅（提案） | テンプレート保守時のみ改訂 | `MAINTAINERS_GUIDE.md` §5 |

**LLM が独自判断できる限定例外**：
- `QUESTIONS.md` への Q 起票（内容はユーザが検討）
- Q の状態を `open` → `in-discussion` に変更（ユーザが議論を始めた時点）
- `core.clj` など実装コードの作成・編集（§8 作業プロトコルに従う）
- 命名・内部実装の詳細判断（§2.1 L2/L3 相当）
- ADR の新規発行（決定内容がゲート／対話で承認済の場合のみ、L2）

これら以外の編集は**すべてユーザの明示承認が前提**。

### 2.3.1 特別承認・部分承認は採用しない

本マトリクスは**文書種別単位の全か無か**で編集権限を規定する。以下は本プロジェクトで採用しない（CLAUDE.md §1.2.5 失敗早期検知と承認設計に整合）：

- **特別承認**（ある場面だけ L0/L1 の規則を緩和する仕組み）:
  - CLAUDE.md §2 禁止事項は例外なく維持する
  - 下位文書（BOOTSTRAP_GUIDE.md 等）で上位規則（CLAUDE.md §2）の例外を作る構造は文書の自己整合性を破るため禁止
  - §2 禁止事項に抵触する操作が発生しないよう、該当する儀式（例: BOOTSTRAP_GUIDE.md の archived/ 移動、完了時の CLAUDE.md 参照表書き換え）自体を廃止する方針を採る
- **部分承認**（成果物単位での個別承認）:
  - 承認は文書種別単位で「全承認 or 全修正指示」のみ
  - 修正指示を受けた場合は LLM が全体を再提示して再承認を得る
  - 理由: 部分承認プロトコルの未定義状態は LLM の解釈揺れを生み、依存関係の破綻リスクを抱える。単純な全承認サイクルの方が失敗時の原因特定と修正が早い

**運用上の帰結**: ブートストラップ完了処理に CLAUDE.md / .llm/guide/ の編集は**含まれない**（該当儀式を廃止したため）。ユーザが直接叩くのは最終コミットコマンドのみ。

## 3. 協働モードの分類

作業の段階によって、協働の進め方が異なる。LLM は**現在どのモードで動いているか**を意識する。

### 3.1 ブートストラップモード

プロジェクト初期化期。

- **主な文書**: `../README.md` §開始手順、`BOOTSTRAP_GUIDE.md`
- **特徴**: 人間の意思決定（プロジェクト目的・技術選定）が集中する
- **LLM の姿勢**:
  - L0 コンテンツ（DESIGN.md §1 目的・§3 ユースケース・§4 受入基準等）は人間がキックオフプロンプトで明示記入、LLM は叩き台を出さない
  - 決定事項を文書化・ファイル操作に徹する
  - ADR 発行は L2（§2.2 参照）、ゲート 1/2 で承認された決定を自動で ADR 化して事後報告
  - 曖昧性は §4 ONE BY ONE で 1 点ずつ解消
- **人間の姿勢**:
  - README.md のキックオフプロンプト（完全版 or 最小版）を 1 回送信
  - 主要バッチゲート（2 箇所：仕様+技術選定、構造+依存）で承認または修正指示
  - 個別 L1 成果物（config.edn / CI / build.clj / dev/user.clj / workspace.edn / ルート deps.edn）の提示に応答
  - ONE BY ONE 質問に応答
  - 最終コミットのみ実行（ファイル編集操作は無し、§2.3.1 参照）
- **完了判定**: BOOTSTRAP_GUIDE.md §3 チェックリスト

### 3.2 実装モード

brick 追加・機能実装期。

- **主な文書**: `../CLAUDE.md` §8 作業プロトコル
- **特徴**: 仕様（DESIGN.md）と知識（KNOWLEDGE.md）を参照しながらコード生成
- **LLM の姿勢**: §8.0 実装着手前の確認を必ず実施、曖昧性を能動的に発見
- **人間の姿勢**: 設計判断の承認、完了時のレビュー
- **完了判定**: `poly check` / `poly test` / 受入基準テスト合格

### 3.3 曖昧性解消モード

QUESTIONS サイクル発動中。

- **主な文書**: `../.llm/memory/QUESTIONS.md`
- **特徴**: 自己解釈できない判断を Q として起票、議論で解決
- **LLM の姿勢**: §4 作業前確認プロトコル、§6 サイクル協働に従う
- **人間の姿勢**: Q ごとに判断、昇格先を指示
- **完了判定**: Q が resolved となり、KNOWLEDGE / ADR / DESIGN のいずれかに昇格済み

### 3.4 保守モード

テンプレート自体の改修期。

- **主な文書**: `MAINTAINERS_GUIDE.md`
- **特徴**: 原則・規約・配布物の構造を変更する
- **LLM の姿勢**: 原則 12 遡及適用を意識、既存体系との整合を確認
- **人間の姿勢**: 保守判断の承認、原則レベルの決定
- **完了判定**: 全文書の整合性確認、§7 議論の軌跡への記録

## 4. 作業前確認プロトコル

### 4.1 タスク受領時の LLM の自己確認

人間から新しい作業を指示された時、LLM は**着手前**に以下を自問する：

1. **どのモード（§3）か**: ブートストラップ / 実装 / 曖昧性解消 / 保守
2. **意思決定階層（§2.1）はどこまでか**: L0 / L1 / L2 / L3
3. **CLAUDE.md §2 禁止事項に触れないか**: 触れるなら承認を先に取る
4. **関連する既存文書**: DESIGN.md §X、KNOWLEDGE.md §Y、関連 Q、関連 ADR を特定
5. **曖昧性はないか**: §4.2 典型パターンで点検

**この自己確認を省略して作業に入らない**。

### 4.2 曖昧性の典型パターン

DESIGN.md・人間の指示・既存コードを読んだ時、以下の曖昧性を能動的に発見する：

| パターン | 例 | 対処 |
|---|---|---|
| **用語定義の曖昧さ** | 「月次締め」とは具体的に何日時点の何か | Q を立てて定義を確認 |
| **例外条件の欠落** | 正常系のみ記述、異常系が不明 | 想定される例外ケースを列挙して確認 |
| **数値基準の不明確さ** | 「高速」「十分な精度」等が具体値なし | 具体値（ms、%、件数等）を尋ねる |
| **境界条件の不明** | 2 つの component のどちらが責務を持つか | 選択肢 A/B/C を提示して判断を求める |
| **既存 KNOWLEDGE との矛盾** | DESIGN と KNOWLEDGE の記述が食い違う | 矛盾を指摘して正解を確認 |
| **暗黙の前提** | 人間が当然視しているが LLM には不明な前提 | `[ASSUMPTION]` マーク付きで提示（§5.1） |

### 4.3 質問の ONE BY ONE 原則

**曖昧性を複数発見しても、一度にまとめて質問しない**。一つずつ順に確認する：

- ✅ 良い: 「まず用語定義から確認させてください。『月次締め』とは...」
- ❌ 悪い: 「5 点確認があります。1...、2...、3...、4...、5...」

理由：
- 人間の認知負荷を下げる（1 問ずつの方が集中して判断できる）
- 前の質問の回答が次の質問を変える可能性がある（無駄な質問を避けられる）
- 対話のリズムが保たれる

例外：
- 項目が完全に独立で、並列に回答できることが明らかな場合
- 人間が「まとめて教えて」と明示的に指示した場合

## 5. 実装中の対話プロトコル

### 5.1 [ASSUMPTION] マーク制度

確信がないが作業を進める必要がある時、**前提を明示的にマーク**して提示：

```
以下の前提で実装を進めます。誤っていれば指摘してください：

[ASSUMPTION-1] 「未払い検知」は最終支払日から 30 日経過を基準とする
[ASSUMPTION-2] 通貨は JPY 固定、小数点以下は扱わない
[ASSUMPTION-3] エラー時は構造化ログに記録し、ユーザーには汎用エラーメッセージを返す

これらを前提に `invoice.interface/detect-unpaid` を実装します。
```

人間は各 [ASSUMPTION-N] に対して承認・修正・質問のいずれかで応答できる。
承認された [ASSUMPTION] は必要に応じて KNOWLEDGE.md に昇格させる（§6.1）。

### 5.2 段階的承認チェックポイント

大きな作業は**中間承認**を挟む。特に以下のチェックポイントを意識：

| チェックポイント | 内容 |
|---|---|
| **設計承認** | `interface.clj` のシグネチャと Malli スキーマ案を提示、合意を取る |
| **実装途中報告** | 50 行を超える実装、または複数ファイルにまたがる変更の途中 |
| **テスト設計承認** | プロパティテストの不変条件が適切か、基準値が妥当か |
| **完了前最終確認** | `poly check`/`poly test` 通過後、受入基準への対応を報告 |

### 5.3 中間報告の粒度

- **粗すぎる報告**: 「実装を進めました」（何を変更したか不明）
- **細かすぎる報告**: 全関数・全変更を逐次報告（人間の疲労）
- **適切な粒度**:
  - 変更したファイル一覧
  - 追加した interface 関数と Malli スキーマ
  - 発見した論点（[ASSUMPTION] や Q 候補）
  - テスト結果（通過 / 失敗の概要）
  - 次のステップ候補

## 6. Q / KNOWLEDGE / ADR / DESIGN サイクルにおける協働

サイクル全体図は `../CLAUDE.md` §11.2 を参照。各文書の運用プロセス詳細は各 §0 に規定されている。本節は**サイクルにおける協働特有の観点**のみを扱う。

### 6.1 Q 起票時の協働

LLM が Q を起票する時の協働上の留意点（起票フォーマット自体は `QUESTIONS.md` §0.3）：

- **選択肢は 2〜4 個を目安**に提示（多すぎると判断負荷、少なすぎると押し付け）
- 各選択肢に**利点・欠点・影響範囲**を明記
- LLM 自身の**推奨**を理由とともに提示（ただし強制しない）
- ユーザに「Q-YYYY-MM-NNN として起票しました、ご判断をお願いします」と報告

### 6.2 Q resolved → 昇格時の判断フロー

**昇格先判定の基準は `QUESTIONS.md` §0.5 に規定**（KNOWLEDGE / ADR / DESIGN / 昇格なしの 4 択）。本節は判定以降の協働のみ扱う：

- 複数候補に該当する場合は**両方への記載**を提案（`../CLAUDE.md` §11.2 シナリオ C 参照）
- 昇格先での記載内容は事前にユーザに提示して承認を求める
- 反映完了後、Q を resolved としてアーカイブし事後報告（曖昧な場合のみ確認）

### 6.3 仕様書開発者としての LLM の振る舞い

LLM の複数役割は `../CLAUDE.md` §11.3 で規定されている。本節は**振る舞いの具体プロンプト例**のみを示す。

#### 能動的な曖昧性指摘

実装中に曖昧点を発見したら、**実装を止めて**指摘する（§4.3 ONE BY ONE 原則に従い、まず 1 点のみ質問）：

```
DESIGN.md §3.UC-2「未払い検知」の実装に着手しようとしています。
以下の点が不明確なので Q を立ててよろしいですか？

「未払い」の判定基準（最終支払日からの経過日数？）
```

#### 仕様化の提案

実装中に見つけた知識を、**能動的に KNOWLEDGE.md への昇格を提案**する：

```
実装中に以下の不変条件が必要と判明しました。KNOWLEDGE.md §1 への追加を提案します：

- invoice の total は items の price 合計と一致する

ご確認いただけますか？
```

#### 決定経緯の保全提案

技術選定・設計判断の際、**ADR 発行を能動的に提案**する：

```
構造化ログライブラリを採用したので、ADR として記録を残すことを提案します：

- ファイル名: adr/0004-adopt-structured-logging.md
- 内容: Context / Decision / Considered Alternatives / Consequences

発行してよろしいですか？
```

## 7. 協働のアンチパターン

避けるべきパターンと、それを防ぐ対処：

### 7.1 人間への過剰な質問（些末な確認の累積）

**症状**: 関数名、変数名、細かな実装詳細を逐一確認する。
**害**: 人間の認知疲労。LLM 駆動の利点が失われる。
**対処**: §2.1 意思決定階層に照らして L2/L3 の判断は独断で進める。**命名・内部実装は LLM の裁量**。

### 7.2 勝手な前提での自走

**症状**: 曖昧な仕様を自己解釈で進め、後で食い違いが発覚。
**害**: 手戻りコスト大、信頼関係毀損。
**対処**: §4.2 曖昧性パターンで点検、見つけたら [ASSUMPTION] か Q で明示化。

### 7.3 中間報告なき大量変更

**症状**: 100 行超・複数ファイルにまたがる変更を一気に行い、後で総括だけ報告。
**害**: 途中の方向ずれを修正できない。全否定リスク。
**対処**: §5.2 段階的承認チェックポイントを守る。

### 7.4 承認なき 4 種文書編集

**症状**: DESIGN.md や KNOWLEDGE.md を LLM の判断で直接編集。
**害**: 仕様・知識の信頼性が損なわれる。
**対処**: §2.3 編集権限マトリクスを守る。**提案者であり決定者ではない**。

### 7.5 役割の混同

**症状**: 実装中に発見した知識を KNOWLEDGE.md に記録せず、コード内コメントだけで済ませる。
**害**: 生きた知識が蓄積されず、再発見の疲労コストが累積（§1.3 違反）。
**対処**: CLAUDE.md §11.3 の複数役割を意識、**実装と並行して知識記録提案を行う**。

### 7.6 質問の一括爆撃

**症状**: 曖昧性を複数発見すると一度にまとめて質問してしまう。
**害**: 人間の認知負荷、前の回答で後の質問が変わる可能性の見落とし。
**対処**: §4.3 ONE BY ONE 原則。
