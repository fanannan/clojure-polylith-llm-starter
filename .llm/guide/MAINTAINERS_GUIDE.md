# MAINTAINERS_GUIDE.md — テンプレート保守者のための設計原則

本文書は**このテンプレート自体を改修・保守する人間および LLM のための羅針盤**である。

日々の開発で LLM が読む必要はない（それは CLAUDE / CODING_GUIDE / POLYLITH_GUIDE の役割）。
本文書が必要になるのは以下の場合：

- **ライブラリ依存を更新・追加・削除する時**
- **新しい規約や落とし穴を各種ガイドに追記する時**
- **このテンプレートを別プロジェクトに複製・派生させる時**
- **配布形態（即有効 / 判断済み推奨集 / 不配布 / 完全排除）を変更する時**

**設計判断を表層で真似ず、原則に遡って再導出する**ための基盤として読まれたい。

---

## 1. このテンプレートの設計目的

### 1.1 目的：LLM と人間の共同開発における修復コストの最小化

本テンプレートは**疲労最小化原則**（CLAUDE.md §1）を配布物のレベルで実装する試みである。
具体的には、**Clojure 1.12 + tools.deps + Polylith + Malli + clj-kondo + cljfmt** を必須技術基盤とし、用途ごとに必要なライブラリを `STACK_GUIDE.md` §3 機能別節から選んで brick の `deps.edn` に反映する構成のプロジェクトを、**LLM が最も誤りにくい形で立ち上げる**ための初期配布物である。Integrant は Web API・バッチ・ワーカ等の I/O を扱う構成で採用されるが、必須技術基盤ではない。ライブラリ配布だけなら採用しない。

### 1.2 適用範囲

- Clojure 1.12 以降、tools.deps ベース
- Polylith ワークスペース構造を採用
- Malli を境界契約として必須採用（§1.1.1 全域性の実装）
- その他（HTTP、DB、ロギング、Integrant、aero 等）は**選定固定だが有効化は任意**

非適用：
- Leiningen プロジェクト
- 非 Polylith の単一プロジェクト
- ClojureScript / babashka のみのプロジェクト

## 2. 配布物設計の 4 値判断

ファイルおよびその内部の各要素は、以下の 4 値のいずれかに分類される。
**これがテンプレート設計の最重要判定軸である**。

| 値 | 定義 | 配布形態 | 例 |
|---|---|---|---|
| **即有効** | どのプロジェクトでも必要、かつ初期コストがゼロ | そのまま配布 | CLAUDE.md、.clj-kondo 必須 linter、Malli の deps |
| **判断済み推奨集（文書配布）** | 選定済だが目的依存で、プロジェクト開始時に採用判断。brick の deps.edn に反映される | STACK_GUIDE.md §3 機能別節で推奨ライブラリとして文書化。deps.edn には出現しない | Integrant、Ring、next.jdbc、mulog |
| **不配布（文書化）** | 特定ドメイン・架空のサンプル | 配布せず、POLYLITH_GUIDE.md にコード例として埋め込む | user component、api base |
| **完全排除** | 技術選定で却下されたもの | 名前も出さない（禁止・非推奨として STACK_GUIDE.md §3 の `;; lib-catalog` block に記録、理由タグは §8） | §8.1 禁止ライブラリの 3 件 |

### 2.1 判定の原則

新規要素をテンプレートに加える提案が来たら、以下の順で判定：

1. **どのプロジェクトでも必ず使うか？** → Yes なら **即有効**
2. **技術選定として固定されているが、目的依存か？** → Yes なら **判断済み推奨集（文書配布）**（どの用途別機能カテゴリで使うかは STACK_GUIDE.md §3 機能別節で判断）
3. **特定ドメイン・架空のサンプルか？** → Yes なら **不配布**（文書化）
4. **技術選定で却下されたか？** → Yes なら **完全排除**（名前も出さない、または STACK_GUIDE.md §3 の `;; lib-catalog` block に禁止・非推奨として記録。理由タグは §8）

### 2.2 判断済み推奨集配布の運用

**真実の一箇所化**: ライブラリ依存の一次情報源は **brick の deps.edn**（Polylith の本番ビルドはそこから依存解決する）。テンプレート側はライブラリ依存を実装として持たず、**STACK_GUIDE §3 機能別節で判断済み推奨集として文書化**する。各 brick の deps.edn に推奨を書く際のガイドとして機能する。
∵ STACK_GUIDE.md §3

判断済み推奨集として配布する要素は**動作が保証された標準形**でなければならない。動作不明なものを推奨すると、採用時にハマる。したがって：

- 推奨ライブラリは**実在のバージョンで動作確認した後**に STACK_GUIDE §3 機能別節 に掲載する（§5.6.2 動作検証）
∵ STACK_GUIDE.md §3
- 各推奨の上に選定根拠（STACK_GUIDE.md §3 該当節）と却下した代替（§3 該当節、§8 禁止・非推奨）を書く
- バージョン目安は定期的に更新する（§5.1 参照）
- 採用時の確認事項を §3 該当節に記載し、用途別機能カテゴリ充足・設定漏れの防止に活用する

**判断済み推奨集方式の利点**:
- **特別扱いなし**: 判断済み推奨集のライブラリもプロジェクト固有ライブラリも、どちらも brick の deps.edn に書かれ、扱いが対称
- **Polylith の brick 独立性と完全整合**: brick の deps.edn が自己完結
- **二重管理の回避**: ワークスペースルートの deps.edn には必須技術基盤のみ配置し、用途依存ライブラリは brick に集約
- **推奨の柔軟性**: 推奨からの逸脱は ADR 発行で記録し、文書化で許容（用途別機能カテゴリ充足が確認できれば具体ライブラリ一致は強制しない）

設計根拠の詳細は **STACK_GUIDE.md §1.2 本文書の性格**。判断済み推奨集の保守規律は **§5.9** で規定。

### 3.5 不配布（C: 特定用途）

以下は**このテンプレートには含めない**。POLYLITH_GUIDE.md 内にコード例として記述する：

- `components/<any>/` 配下のファイル（ドメイン仮定）
- `bases/<any>/` 配下のファイル（エントリ種別仮定）
- `projects/<any>/` 配下のファイル（デプロイ単位名仮定）

これらは `poly create` で生成される、または `.llm/guide/BOOTSTRAP_GUIDE.md` に従って初回作成される。

## 4. 設計 13 原則（本テンプレートの作成過程で得られた学び）

本テンプレートの保守を担う者は、以下の原則に沿って判断する。
表層の「こうなっている」を踏襲せず、**原則に遡って判断する**こと。

### 原則 1: 原理を文書の最上位に置く

**内容**: 疲労最小化という第一原理は、CLAUDE.md §1 に常に最上位で存在し、各章は「§1.X の実装」として自らを位置づける。
**守らないとどうなるか**: 個別規約の羅列になり、LLM は**なぜその規約があるか**を理解できず、未知の状況で原則を外した形式適用をする。
**保守時のチェック**: 新規に章や規約を追加する時、「これは §1 のどの原則の実装か」を答えられなければ追加しない。

### 原則 2: 規約を明文化するだけでは守られない

**内容**: 「〜してはならない」を文書に書くだけで LLM が守る保証はない。実効性を持たせるには、**機械化（ツールで強制）** または **自己停止プロトコル（明示の発動条件）** のいずれかで守る手段を同時に設計する。
**守らないとどうなるか**: 文書が祈りになる。30 分ルールが典型例で、LLM は時間感覚を持たないためターン数・試行回数への変換が必要。
**保守時のチェック**: 新規規約を追加する時、「これを守らせる手段は何か」を明記できなければ追加しない。

### 原則 3: 配布物の二値判断を避ける

**内容**: 「配布するか、しないか」ではなく、「即有効 / 判断済み推奨集（文書配布）/ 不配布 / 完全排除」の **4 値で判断する**。使用頻度・目的依存性・バイアス注入の懸念が要素ごとに違うため、配布形態にグラデーションを設ける。判断済み推奨集は STACK_GUIDE §3 機能別節 で文書として配布され、実装は各 brick の deps.edn に反映される（真実の一箇所化、§2.2 参照）。
∵ STACK_GUIDE.md §3
**守らないとどうなるか**: 「全部入りで配布」して余計なバイアスを注入するか、「最小で配布」して毎回判断コストを発生させるかの両極端になる。
**保守時のチェック**: §2.1 の判定フローで各要素を分類する。判断済み推奨集の詳細運用は §5.6、選定論理は STACK_GUIDE に置く。
∵ STACK_GUIDE.md

### 原則 4: 「汎用」は相対概念。基準を明示する

**内容**: 「このファイルは汎用」と言った時、それは「Clojure 言語として汎用」なのか「このテンプレートの技術選定下で汎用」なのかを明示する。後者の場合はファイルの docstring / 冒頭コメントに「〜の採用の帰結として配布される」と書く。
**守らないとどうなるか**: LLM / 保守者がファイルを「調整対象」と「不可侵」で誤判定する。
**保守時のチェック**: 新規配布ファイルには必ず冒頭コメントで前提を明示する。

### 原則 5: LLM は削除が苦手

**内容**: 与えられたコードを LLM は「利用すべきもの」として解釈する傾向がある（Rails 等の従来テンプレート文化では「雛形から削る」が一般だったが LLM 時代には不適）。したがって**最初から余計なものを置かない**。
**守らないとどうなるか**: 架空ドメイン（`user`）、架空エントリ（`api`）、架空 project 名（`api-server`）などがプロジェクトの「慣行」として誤認される。
**保守時のチェック**: 新規ファイル追加時、「これは LLM が削除できない前提で配布されるが問題ないか」を自問する。

### 原則 6: サンプルとテンプレートは役割が違う

**内容**: テンプレートは「プロジェクト共通の初期構成」、サンプルは「書き方の教材」。サンプルをテンプレートに混ぜると、テンプレートが汎用性を失い、サンプルが教材としての純粋性を失う。
**守らないとどうなるか**: 両方が劣化する。
**保守時のチェック**: サンプルは POLYLITH_GUIDE.md / CODING_GUIDE.md のコード例ブロックに埋め込む。テンプレートファイルとしては配布しない。

### 原則 7: 「文書の自己整合性」

**内容**: 文書が自らの述べている原則を自らに適用できているかを、設計レビューの最終段階で必ず検証する。たとえば「規約を機械化せよ」と書きながら、自らの規約（30 分ルール等）を機械化していないのは矛盾。
**守らないとどうなるか**: LLM / 保守者は文書の建前と実態の乖離を感じ取り、文書全体への信頼を失う。
**保守時のチェック**: 文書を改訂したら、「この文書は自らの原則に反していないか」を問う一回路を最終工程に置く。**自己整合性は整理を通じて維持される**。具体的な整理姿勢は §9.3 を参照。

### 原則 8: 自動検出されないものを前方に置く

**内容**: 文書の章順は「自動検証できないもの」「違反影響が甚大なもの」を前方に、「ツールが検出するもの」を後方に並べる。違反を後から検出できるものは文書の前方で目立たせる必要性が低い。
**守らないとどうなるか**: 冒頭から細かいツール設定が並び、LLM が最重要の不可逆操作禁止を見落とす。
**保守時のチェック**: 章順を変更する時、「これは自動検証されるか / 影響がどれだけ不可逆か」で再評価する。

### 原則 9: 設計判断の軸を先に確定する

**内容**: 何かを「含める / 除外する」を判断する前に、判定軸が**網羅的か**を先に検証する。軸が一つだけだと表層的な結論になる。
**守らないとどうなるか**: 結論が恣意的になり、同じ問題で繰り返し再検討が発生する。
**保守時のチェック**: 重要な判断を下す前に「判定軸を何個用意したか、それで網羅できているか」を確認する。

### 原則 10: 「議論の軌跡を残す」

**内容**: 設計判断の結果だけでなく、その**判断に至った経緯・検討した反対仮説・却下した選択肢**も残す。現在有効な規則は本文書または該当ガイドに反映し、重要な決定理由は ADR に、議論過程は `.llm/memory/archive/maintainer-discussions/` に分離して記録する。
**守らないとどうなるか**: 時間経過で判断が「自明の前提」化し、前提が変わった時に気づけない。
**保守時のチェック**: 新しい設計判断を下したら、「現行ルールへの反映」「ADR が必要か」「議論アーカイブに残すべき経緯があるか」を §7.1 の記録先表で判定する。本文書に過去の暫定判断を混ぜない。

### 原則 11: 「判断とプロセスの対称性」

**内容**: 設計判断（what）を定義したら、その判断を**運用・実行するプロセス（how）**も同時に定義する。判断だけ文書化してプロセスを暗黙にすると、LLM / 人間は判断だけ受け取ってプロセスを自力で捏造する。
**守らないとどうなるか**: 「配布形態は決めたが有効化手順はない」「禁止事項は書いたが違反検出方法は書いていない」「規約は定めたが遵守確認手段はない」のような片手落ちが累積する。規約が祈りに、判断が抽象論になる。
**保守時のチェック**: 新しい設計判断を下した時、以下を同時に答えられるか確認する：
  - この判断は**誰が・いつ・どの順序で**実行するのか
  - 実行後の整合性は**どう検証する**のか
  - 失敗時の**復旧手順**は何か
  答えられないなら、プロセス未定義の判断として追加してはならない。原則 2（規約だけでは守られない）の一般化である。

### 原則 12: 原則追加時の遡及適用

**内容**: 新しい原則を §4 に追加した時、**既存の全ての判断・規約・文書にその原則を遡及適用して違反を点検する**。新原則を立てただけで放置すると、既存体系に原則違反が潜伏し続ける。
**守らないとどうなるか**: 新原則が「今後の判断には適用するが既存は例外」という二重基準になる。時間経過で新旧の規約が矛盾し、文書全体の信頼性が損なわれる。
**保守時のチェック**: 新原則を追加したら、以下の遡及適用プロセスを必ず実行する：
  1. 全文書（CLAUDE.md、CODING_GUIDE.md、POLYLITH_GUIDE.md、QUESTIONS.md、KNOWLEDGE.md、DESIGN.md、ADR、BOOTSTRAP_GUIDE.md、本文書）を新原則で点検
  2. 違反箇所をリストアップし、修正可否を判定（修正コスト vs 効果）
  3. 修正する場合は、単独追記ではなく**既存体系全体の改善として統合実施**
  4. 点検結果と修正内容を §7 の規則に従って ADR または議論アーカイブに記録
  原則の追加は「原則を 1 つ増やす」ではなく「既存体系を新原則で再評価する」作業である。**遡及適用時は追加よりも整理の機会を先に点検する**。整理姿勢の詳細は §9.3 を参照。

### 原則 13: 「分類管理の原則」

**内容**: プロジェクトに関わる文書を以下の 4 種に明確に分離し、役割を混同しない。各種別は性質・配置・ライフサイクルが対照的であり、混在すると文書の信頼性が崩壊する。

| 種別 | 性質 | 配置 | ライフサイクル |
|---|---|---|---|
| **仕様（DESIGN）** | 何を作るか。合意の起点 | `DESIGN.md`（ルート） | プロジェクト初期に確定、大きな方針転換時のみ改訂 |
| **現時点で有効な知識（KNOWLEDGE）** | 現時点の真実。契約・不変条件・暗黙知 | `.llm/memory/KNOWLEDGE.md` | 実装中に継続更新、常に最新状態を保つ（上書き） |
| **決定履歴（ADR）** | なぜそう決めたかの不変記録 | `.llm/memory/adr/NNNN-topic.md` | 一度発行したら変更禁止、改訂は新 ADR で supersede |
| **判断保留（QUESTIONS）** | 未決の判断。一時的 | `.llm/memory/QUESTIONS.md` | 未対応(open) → 解決済み(resolved) で閉じる、軌跡はアーカイブ |

**守らないとどうなるか**:
- KNOWLEDGE（現時点の真実）が ADR（不変履歴）に混入 → 後から書き換えられて歴史改変が起きる
- ADR（不変履歴）が KNOWLEDGE に混入 → 更新時に元の決定理由が失われる
- QUESTIONS（一時的判断）が KNOWLEDGE に混入 → 未決事項が継続参照の源泉と誤認される
- DESIGN（仕様）が KNOWLEDGE に混入 → 合意の起点と実装知識の区別が消える

**保守時のチェック**: 新しい情報を記録する時、以下を順に自問する：
  1. これは「何を作るか」の仕様か → DESIGN.md
  2. これは現時点の契約・不変条件で、今後も更新され続けるか → KNOWLEDGE.md
  3. これは「なぜそう決めたか」の経緯で、今後改訂しないか → ADR
  4. これは未決の判断で、いずれ結論が出るか → QUESTIONS.md
  判断できない場合は、QUESTIONS.md に Q を立てて分類自体を相談する。

**補足 — Q からの反映**: Q が 解決済み(resolved) になった時、その内容が「現時点の真実として継続参照される」なら KNOWLEDGE へ、「なぜそう決めたかの不変記録」なら ADR へ反映する。解決済み(resolved) Q 自体はアーカイブに残り、反映先を `反映先` 欄に記録する。

## 5. 保守・改修の判断フロー

### 5.1 ライブラリ依存の更新

`clj -M:outdated` で更新候補を確認後（用途依存ライブラリは brick の deps.edn 経由で走査される、§5.6.1 参照）：

1. **セキュリティパッチ系**: 即適用（必須技術基盤・判断済み推奨集両方。判断済み推奨集は STACK_GUIDE.md §3 機能別節 のバージョン目安に反映）
2. **メジャーバージョンアップ**:
   - 必須技術基盤の依存は、CI の全テスト通過後に適用
   - 判断済み推奨集内の依存は、該当プロジェクト用途構成の動作検証（§5.6.2）時にまとめて STACK_GUIDE.md §3 機能別節に反映
3. **API 破壊的変更を含む更新**:
   - STACK_GUIDE.md §3 選定根拠・§3 機能別節の `;; lib-catalog` blockを更新
   - 変更影響を CODING_GUIDE.md / POLYLITH_GUIDE.md に反映
   - 必要なら CLAUDE.md の記述も修正
4. **version 更新の記載先規律**:
   - **version は `STACK_GUIDE §2` のみに記載**（必須技術基盤・横断層の正本）
   ∵ STACK_GUIDE.md §2
   - `CLAUDE.md §3` と `BOOTSTRAP_GUIDE.md §1` は概念的な必須技術基盤列挙のみを保持し、version は書かない。version 更新時に同期する必要がない運用に倒す（drift 防止）
   - 更新後は必ず `./.llm/scripts/lint-import-hooks.sh` を実行し、依存ライブラリ提供の clj-kondo hook を再取り込む（§5.11）

### 5.2 新しいライブラリを採用する場合

以下を順に検討：

1. **そもそも必要か？**
   - Clojure 標準（clojure.string, clojure.set, clojure.walk 等）で足りないか
   - 既に採用している Malli や既存の推奨ライブラリで代替できないか
2. **§2.1 の 4 値判断でどの区分に入るか**（即有効 / 判断済み推奨集 / 不配布 / 完全排除）
3. **判断済み推奨集に入れる場合、どの用途別機能カテゴリに置くか**（STACK_GUIDE.md §3 機能別節で判断）
4. **STACK_GUIDE.md §3 に選定根拠を追記、代替として何を却下するか**を同時に決める
5. **既存コード・文書への影響範囲**を確認

詳細は §5.6.3 新規ライブラリ採用時の手順、§5.9 STACK_GUIDE.md の保守。

### 5.3 ライブラリを削除する場合

1. **なぜ削除するか**を ADR または議論アーカイブに記録（§7）
2. **代替は何か**を明示（なし、別ライブラリ、Clojure 標準）
3. **完全排除するか、STACK_GUIDE.md §3 の該当 `;; lib-catalog` block に非推奨として落とすか**を判定（理由タグは §8）
4. STACK_GUIDE.md §3 の採用記述を削除、当該 §3.X の `;; lib-catalog` block「代替と却下」節に非推奨エントリを追加（推奨代替ありタグ）
5. 関連文書（CLAUDE.md / CODING_GUIDE.md / POLYLITH_GUIDE.md）の記述を整合的に更新

詳細は §5.6.4 判断済み推奨集の削除・置換、§5.9.5 推奨ライブラリの差し替え。

### 5.4 新しい規約を追加する場合

1. **原則 1**: §1 のどの原則の実装か明示
2. **原則 2**: 守らせる手段（機械化 / 自己停止プロトコル / チェックリスト）を同時設計
3. **原則 8**: 自動検出されるか否かで文書配置を決める
4. **原則 5**: LLM が形式適用に陥らないよう、意図を「なぜ」で説明

### 5.5 新しい LLM 落とし穴を追加する場合

CODING_GUIDE.md §1 に追加。フォーマットは既存の項目（§1.1〜§1.14）と同じ：

- 兆候（どんな時に現れるか）
- 対処（どう直すか、どう回避するか）
- 必要なら良い例 / 悪い例

追加順は時系列でよい（§1.15, §1.16, ...）。

### 5.6 STACK_GUIDE.md §3 機能別節 判断済み推奨集の保守

STACK_GUIDE.md §3 機能別節で判断済み推奨集として配布されているライブラリ群は「採用されなくても腐ってよい」わけではない。用途ごとの推奨が実在・動作する状態を保つ。判断とプロセスの対称性に従い、以下のプロセスで保守する。

**判断済み推奨集の一次情報源は `STACK_GUIDE §3` 機能別節**（本ファイルは deps.edn を一次情報源としない、選択肢 H）。本節は判断済み推奨集の保守（バージョン更新、動作検証、新規採用、削除・置換）を扱う。プロジェクト用途構成そのものの整理や追加は STACK_GUIDE と §5.9 に置く。
∵ STACK_GUIDE.md §3

#### 5.6.1 バージョン更新

- **問題**: ワークスペースルートの deps.edn には用途依存ライブラリが含まれないため、`clj -M:outdated`（antq）はそれらを直接走査できない。各 brick の deps.edn、または検証用プロジェクトを介して確認する
- **対処**:
  - 四半期に 1 回、検証用プロジェクト（§5.6.2）を作成し、`clj -M:outdated` を brick 別に実行
  - 更新が必要なものを STACK_GUIDE.md §3 機能別節 のバージョン目安に反映
  - セキュリティパッチは即時反映（§5.1）

#### 5.6.2 動作検証（年 1 回）

判断済み推奨集が経年で壊れていないか定期検証する：

1. テンプレートから派生した**検証用プロジェクト**を作成（実プロジェクトとは別）
2. 用途ごとの代表構成で brick を作成し、STACK_GUIDE.md §3 機能別節の推奨ライブラリを brick deps.edn に反映
3. 各 brick が単独で依存解決できることを確認:
   ```bash
   cd bases/<entry> && clj -Spath > /dev/null && echo ok
   cd components/<domain> && clj -Spath > /dev/null && echo ok
   ```
4. 典型的な組み合わせで REPL 起動・テスト通過を確認:
   ```bash
   clj -M:dev:nrepl
   ```
5. `clj -M:lint` / `clj -M:poly check` / `clj -M:poly test :all` / uberjar ビルドが通ることを確認
6. 各プロジェクト用途構成に対応する §3 機能別節の採用時の確認事項を実際に点検
7. 通らない箇所を本テンプレート側（STACK_GUIDE.md §3 機能別節）で修正

この作業は `.llm/memory/archive/maintainer-discussions/YYYY/YYYY-MM.md` に「<日付>: 統合検証実施、修正点 <...>」として記録する。

#### 5.6.3 新規ライブラリ採用時の手順

§5.2 の手順 + 以下を追加：

1. ライブラリが「判断済み推奨集」区分なら：
   - **STACK_GUIDE.md §3 に選定根拠**を追加（採用・検討した代替・採用理由・適用用途）
   - **STACK_GUIDE.md §3 機能別節の該当箇所**の推奨ライブラリ表に追加
   - 該当 §3 機能節の**採用時の確認事項**相当を必要に応じて更新
   - `development/src/dev/user.clj` に使用例の placeholder が必要なら追加
   - `.clj-kondo/config.edn` の `discouraged-var` 追記が必要なら追加
   - **POLYLITH_GUIDE.md §2 のコード例を更新**（使用例が必要な場合）
2. 配布前に、§5.6.2 の動作検証を該当プロジェクト用途構成について実行

#### 5.6.4 判断済み推奨集の削除・置換

判断済み推奨集からライブラリを削除する、または別ライブラリに置換する場合（§5.9.5 推奨ライブラリの差し替えと連動）：

1. ADR または議論アーカイブに削除・置換理由を記録（§7）
2. **STACK_GUIDE.md §3 の該当節を更新**（採用理由の書き換え、または採用から却下への移動）
3. **STACK_GUIDE.md §3 機能別節の該当箇所**の推奨ライブラリ表を更新
4. **STACK_GUIDE.md §3 の該当 `;; lib-catalog` block**に旧ライブラリを非推奨として追加（推奨代替ありタグ、移行方針を記載。理由タグは §8）
5. 該当 §3 機能節の**採用時の確認事項**相当を必要に応じて更新
6. `development/src/dev/user.clj` / `.clj-kondo/config.edn` から該当箇所を削除（使用例があった場合）
7. POLYLITH_GUIDE.md §2 コード例から該当部分を削除
8. CLAUDE.md §3 技術スタック表（もし言及あれば）から除外

**新しいプロジェクト用途構成の追加・既存プロジェクト用途構成の廃止**は STACK_GUIDE と本書 §5.9.2 / §5.9.3 の手順に従う。
¤ STACK_GUIDE.md

### 5.7 .llm/memory 文書群の保守（分類管理の原則の実装）

区分 E（プロジェクト固有の継続更新対象）に属する QUESTIONS.md / KNOWLEDGE.md / adr/ は、テンプレートから派生したプロジェクトで運用される。テンプレート保守者はこれらの**運用規則自体**を保守する責任を持つ。

#### 5.7.1 KNOWLEDGE.md のライフサイクル規則

テンプレートの KNOWLEDGE.md §0 運用プロセスを改訂する場合：

1. 改訂理由を ADR または議論アーカイブに記録（§7）
2. KNOWLEDGE.md §0 を更新
3. 既存プロジェクトへの影響（過去エントリの扱い変更など）を文書化
4. QUESTIONS の反映先判定との整合性を確認
∵ ../memory/QUESTIONS.md §0.5
5. 原則 12 遡及適用：本文書 §4 の原則群との衝突がないか点検

#### 5.7.2 ADR 運用規則の改訂

`.llm/memory/adr/README.md` を改訂する場合：

1. **発行基準の変更**は慎重に。ADR は不変性が本質なので、ルール変更は過去の ADR 全てに影響する
2. 過去 ADR の status 更新規則変更は禁止（superseded の仕組みは変更不可）
3. 新しい書式セクションの追加は可、既存セクションの削除は禁止（過去 ADR が無効扱いになる）
4. template.md の変更は新規 ADR にのみ影響（過去 ADR には遡及しない）

#### 5.7.3 DESIGN.md 雛形の改訂

`DESIGN.md`（テンプレートのルート）の雛形を改訂する場合：

1. 🔴 必須項目の追加：慎重に。既存プロジェクトの初期化完了状態を破壊する可能性
2. 🟡 推奨 / ⚪ 任意項目の追加：影響は限定的、自由度が高い
3. 項目削除は原則禁止（過去プロジェクトで既に埋められている）
4. プロダクト特性による追加項目は、本テンプレートには反映せず派生プロジェクト側で追加する

#### 5.7.4 QUESTIONS.md 運用規則の改訂

状態機械（§0.1）、反映先判定（§0.5）、エスカレーション閾値（§0.6）などの変更：

1. 変更理由を ADR または議論アーカイブに記録（§7）
2. 既存の 未対応(open) / 議論中(in-discussion) / 保留(blocked) Q への影響を評価（マイグレーション手順を記述）
3. 自己停止プロトコルとの連携（§0.9）に影響がないか確認
∵ ../CLAUDE.md §7.3

### 5.8 README.md 雛形の保守

README.md はテンプレート配布時と派生プロジェクト運用中で**役割が正反対**（前者は内部向け説明、後者は外部向け説明）。両者の混在防止が保守の要点。

#### 5.8.1 テンプレートの README.md 改訂時

- 冒頭の**警告ブロック**（書き換え前提の明示）は**絶対に消さない**
- ファイル構成図・導線表・開始手順はテンプレート全体の変更に応じて更新
- プロダクト機能の説明は書かない（それは DESIGN.md の役割）
- 書き換え手順への参照を維持
∵ .llm/guide/BOOTSTRAP_GUIDE.md §4

#### 5.8.2 派生プロジェクトでの書き換え検証

年 1 回の統合検証（§5.6.2）で、**検証用派生プロジェクトで README.md を実際に書き換える**ことを手順に含める。書き換え手順が煩雑すぎたり、書くべき内容が不明瞭な場合は、テンプレート側の BOOTSTRAP_GUIDE.md §4 を改善する。

#### 5.8.3 README.md と DESIGN.md の重複回避

両者は役割が違う：

- **README.md**: プロジェクトに初めて触れる人向けの入口、ファイル構成・開始手順・ビルド方法
- **DESIGN.md**: 実装者・保守者向けのプロダクト仕様、目的・スコープ・機能要件・受入基準

派生プロジェクトで書き換える時、両者に同じ内容を書かない。README.md は DESIGN.md への導線を提供する形にする。

### 5.9 STACK_GUIDE.md の保守

STACK_GUIDE.md は**テンプレート設計者の知見を蓄積する中核文書**であり、他ガイドと異なる保守規律を持つ（STACK_GUIDE.md §1.2 本文書の性格）。

#### 5.9.1 基本方針

- **継続的充実**: 機能領域・プロジェクト用途構成・選定根拠は時間とともに増える。ファイルサイズを気にしない
- **「なぜ」を必ず書く**: 選定理由・却下理由が不足すると LLM も人間も将来判断できなくなる
- **派生プロジェクトでは更新しない**: 保守はテンプレート側で行う
- **整理優先（§9.3）は適用される**: 新規追加より既存の整理で済まないかを先に問う
- **過剰な充実をしない**: STACK_GUIDE.md は「採用/不採用の判断材料」と `:references` の責務に限定し、汎用トラブルシュート・再発防止 playbook・ハウツー集は追加しない

**受け皿ルール**:
- 汎用知見は `:references` へ無理に寄せない。`STACK_GUIDE.md` は lib-catalog エントリに限定する
- 再発防止価値が高い知見は、既存検証フロー経由で `KNOWLEDGE.md` / `QUESTIONS.md` / `adr/` へ昇格する
∵ CLAUDE.md §8.0/§8.0.0、§7.4

#### 5.9.2 新しいプロジェクト用途構成を追加する場合

初期化で新しい用途への対応が必要と判明した時の手順：

1. **既存のプロジェクト用途構成で実現できないか点検**（§9.3 整理優先）
   - 既存の用途別機能カテゴリの組み合わせで対応できないか
   - 既存の選定ポイントに知見追加で済まないか
2. 独立したプロジェクト用途構成として必要なら以下を実施：
   - **STACK_GUIDE.md §2.2 プロジェクト用途構成の一覧**に追加
   - **STACK_GUIDE.md §4.1 選定基準表**に追加
   - **STACK_GUIDE §3 機能別節に新しい節**を追加（統一フォーマット: 目的・必要機能・推奨ライブラリ・選定ポイント・避けるべきライブラリ・採用時の確認事項）
   ∵ STACK_GUIDE.md §3
   - **§3 機能別選定根拠**に必要な新機能が含まれる場合、§3 にも追記
   - **ADR を発行**（`adr/NNNN-add-usage-pattern-XXX.md` など）。検討した却下案も記録
3. §7 の規則に従い、ADR または議論アーカイブへ記録（「議論の軌跡を残す」）
4. 検証用プロジェクトで該当プロジェクト用途構成を採用し、brick deps.edn 反映→ `clj -Spath` 確認（§5.6.2）
5. CI に brick 単位の依存解決確認を追加（`cd bases/<entry> && clj -Spath`）

#### 5.9.3 新機能領域（§3）を追加する場合

新しい用途別機能カテゴリ（例: 新しい認証方式、新種のストレージ等）が必要になった時：

1. **既存 §3.X で扱えないか点検**
2. 独立した機能領域として必要なら：
   - **STACK_GUIDE.md §3 に新節を追加**（統一フォーマット: 採用・検討した代替・採用理由・適用用途・ノウハウ）
   - 該当する既存プロジェクト用途構成の **§3 機能別節の `;; lib-catalog` block**に反映
3. ADR 発行は**テンプレート側の大きな方針変更時のみ**（軽微な追加は議論アーカイブのみで可）

#### 5.9.4 既存ライブラリのバージョン更新

- **セキュリティパッチ**: 即時反映（§5.1 参照）
- **マイナー/パッチアップデート**: §5.1 の定期更新で反映
- **メジャーアップデート**: 破壊的変更の可能性があるため、動作確認の上で反映。場合によっては §3 の採用理由に影響がないか再評価

#### 5.9.5 推奨ライブラリの差し替え

既存の推奨ライブラリを他ライブラリに差し替える場合（例: mulog → 新しい構造化ログ系）：

1. **差し替え根拠を明確化**: 現行の何が不足で、新候補の何が優れるか
2. ADR を発行（`adr/NNNN-replace-XXX-with-YYY.md`）
3. **STACK_GUIDE.md §3 の該当節**を更新（採用・採用理由を書き換え）
4. **§8.2 非推奨に旧ライブラリを移動**（推奨代替ありタグ付き、移行方針を記載）
5. **§3 該当機能節** の `;; lib-catalog` block を更新
6. **deps.edn** を更新
7. **派生プロジェクトへの影響**: KNOWLEDGE.md への移行ガイド記載を検討

#### 5.9.6 禁止・非推奨ライブラリの追加先

本テンプレートは**各 §3.X 機能節の `;; lib-catalog` block の「代替と却下」節**で禁止・非推奨エントリを管理する（採用・不採用が同一機能節で一望できる形）。追加先は以下で判断:

| エントリの性格 | 追加先 |
|---|---|
| 特定機能に属する（例: Compojure は §3.4 HTTP の非推奨） | **該当 §3.X の `;; lib-catalog` block 末尾の「代替と却下」節** |
| 既存 §3 に対応節なし（GraphQL / GUI / メッセージキュー / Bot / SSR / その他） | **§3.44〜§3.49 の該当節** |
| 特定 coord を持たない（Keycloak / Memcached / Babashka 本番利用 等） | **§8 narrative**（EDN には含めない） |

#### 5.9.7 禁止ライブラリへの追加手順（§3.X 代替と却下 節）

セキュリティ・ライセンス・メンテ停止等の**強い理由**がある場合のみ追加：

1. **事実確認**: CVE 番号、公式声明、ライセンス条項等の**一次資料を確認**（憶測で追加しない）
2. ADR を発行（`adr/NNNN-forbid-XXX.md`）、事実根拠を記載
3. §5.9.6 の判定に従い、該当 §3.X の `;; lib-catalog` block「代替と却下」節にエントリ追加（schema は §5.9.8 参照、`:judgment :status :deprecated :severity :forbidden`）。`;;` コメントで詳細な却下理由を保持する
4. **`clj -X:gen-lib-catalog` を実行**し、`.llm/data/{libs.edn, deprecated-libs.patterns, forbidden-requires.patterns}` を再生成
5. 生成 diff を確認の上、STACK_GUIDE 変更と生成物再生成を**同一コミット**にまとめる
6. 既存の派生プロジェクトで使用されている可能性がある場合、周知が必要

#### 5.9.7b 非推奨ライブラリへの追加手順（§3.X 代替と却下 節）

推奨代替が明確な場合の追加：

1. **代替の実在を確認**（代替が推奨できる状態にあるか）
2. ADR を発行（`adr/NNNN-deprecate-XXX.md`）
3. §5.9.6 の判定に従い、該当 §3.X の `;; lib-catalog` block「代替と却下」節にエントリ追加（schema は §5.9.8 参照）
4. **`clj -X:gen-lib-catalog` を実行**し、生成物を再生成、同一コミット
5. §3.X の採用理由 narrative も必要に応じて更新

#### 5.9.8 lib-catalog EDN block の schema と生成フロー

**単一情報源**: STACK_GUIDE.md **§3.X の各機能節**が narrative と `;; lib-catalog` EDN block を同居させ、lib 情報の唯一の単一情報源として機能する。旧構成の lib-catalog 集約節は廃止済みで、§8.1/§8.2 の EDN block も §3.X 該当節へ移行済。横断的ライブラリ（mulog / integrant / aero 等）は複数の §3.X に現れうるが、generator は**構造完全一致のエントリのみ dedup** を許容し、矛盾（同じ coord + purpose で異なる judgment/reason）は error。

**§3.X 節の構造**（narrative + EDN の同居）:
```
### 3.X 機能名
**採用**: ライブラリ名
**採用理由**: - 考え方の narrative
;; lib-catalog
[;; === 採用 ===    <- 採用エントリ
 ;; === 代替と却下 ===  <- 却下エントリ (旧「検討した代替」table の情報を保持)
 ]
**適用場面**: ... (読みやすさ用のラベル)
```

**採用 + 代替の同一 block 集約**: 各 §3.X の block は `;; === 採用 ===` / `;; === 代替と却下 ===` コメントで区切って**その機能領域での採否**を一望できる構成（単一の正本徹底の副次効果: 保守時に同機能で何が採用され何が避けられているかが単一 block 内で確認できる）。`.llm/data/` 配下の EDN/pattern 生成物と shell script が読む派生物は `clj -X:gen-lib-catalog` が生成し、手編集禁止（ヘッダに `GENERATED` コメント付き）。

- `.llm/data/libs.edn` — 全エントリ（人間可読形式、pretty-print）
- `.llm/data/deprecated-libs.patterns` — `check-deprecated-libs.sh` が読む `<regex>|<reason>` 行
- `.llm/data/forbidden-requires.patterns` — `check-forbidden-requires.sh` が読む `<ns-regex>|<reason>` 行
- `.llm/data/conflicts.patterns` — `check-conflicting-libs.sh` が読む `<coord-a>|<coord-b>|<reason>` 行（`:relations :conflicts-with` 由来の併用禁止ペア）

**schema**（詳細は `.llm/scripts/gen_lib_catalog.clj` 内の `entry-schema` 参照）:

```clojure
{:purpose  [:domain :subdomain]                    ; 任意、1 要素以上の keyword vec
 :ids      {:coord <sym>                           ; 必須
            :aliases [<sym>...]                    ; 任意、代替 coord
            :ns "<ns-prefix>"}                     ; 任意、require 検知用
 :judgment {:status :deprecated                    ; 必須、5 値 enum
            :severity :forbidden                   ; 任意 (:deprecated 時)
            :replacement <sym-or-vec>              ; 任意、symbol または symbol vec
            :version "1.2.3"                       ; 任意 (:recommended 用)
            :applicable-when "条件文"}             ; 任意 (:conditional 用)
 :reasons  {:text "1 行要約"                        ; 任意
            :tags [:security ...]}                 ; 任意、§8.0 の 6 種
 :references                                       ; 任意、主要根拠の map
  {:repository "https://..."                     ; 配布元（任意）
   :doc "https://..."                           ; 公式 docs / API リファレンス（任意）
   :quick-reference "https://..."               ; 短時間で確認できる導線（任意）
   :examples ["https://..." "https://..."]}    ; 検証済み例・チュートリアル等（任意）
 :relations {...}}                                 ; 任意
```

`:quick-reference` は 1〜2 本程度の入口を置く短い補助資料で、`:examples` は導入・運用に役立つ具体コードを含む補助資料を複数束ねる想定です。`:doc` は公式 docs 本体です。`:documentation` は定義しない運用です。`:references` 未指定時、生成時に `:recommended` / `:acceptable` で `:repository` を自動補完します。

**`:status` 5 値**:
- `:deprecated` — 使用禁止 / 新規採用禁止（`:severity :forbidden` / `:superseded` で強度）
- `:recommended` — 推奨一択（同 `:purpose` に 1 件、generator が検証）
- `:acceptable` — 許容される選択肢
- `:conditional` — 特定条件下で採用可（`:applicable-when` 必須）
- `:scope-excluded` — 本テンプレートの射程外

**generator の検証項目**: 必須フィールド、enum 値、`[[:ids :coord] :purpose]` pair 重複、`:recommended` × `:purpose` 一意性。違反時は明示的に error 終了。

**生成物の同期保証**: `check-workspace-integrity.sh` が再生成 + diff で drift を検知（完了条件経由で毎セッション検証）。STACK_GUIDE 編集後に `clj -X:gen-lib-catalog` を忘れてコミットした場合、この検査で fail する。
∵ ../CLAUDE.md §5.5

**非 lib エントリ（特定 coord を持たない技術・カテゴリ）**: Keycloak / Memcached / OpenTelemetry / Babashka 本番利用 / iText 直接 / langchain4j 移植 / Java Serialization 直接 等は EDN ではなく STACK_GUIDE.md の該当機能節 narrative に記録。data には載せない（schema が `:coord` を必須にするため）。

#### 5.9.9 避けるべき改訂パターン

- **根拠なき追加**: 「なんとなく嫌い」「流行りでない」等、一次資料のない判断による追加
- **理由タグなしの分類**: §8.0 理由タグを付けずに追加すると、後続の判断者が根拠を再構築できない
- **§3 と §8 の混同**: §3 は機能別の採用判断、§8 はテンプレート全体の禁止・非推奨。同じライブラリが両方に出るのは正常だが、役割を混同しない
- **§3 の「代替と却下」節の肥大化**: 特定機能で却下した lib のみ記載。汎用的な非推奨は §8 narrative への参照で十分

### 5.10 機械化戦略の実装手段（5 層構造）

本テンプレートの §1.2.1 機械化原則を実装する手段は 5 層に分かれ、各層が得意な領域を担う。重複開発を避けるため役割分担を明確にする（Splint / clj-watson 導入時に体系化）。

| 層 | 実装手段 | 得意領域 | 代表例 |
|---|---|---|---|
| **L1 構文・型・未使用** | clj-kondo 組み込み linter | AST 解析、命名空間解決、アリティ検査 | `:unresolved-var`、`:invalid-arity`、`:unused-binding`、段階 1 / 2 の 38 linter |
| **L2 本テンプレート固有パターン** | `.clj-kondo/polyguard/hooks.clj` (custom hook) | form 単体の AST 解析 | 関数行数、top-level mutable、catch Throwable、空 catch（位置引数）、go blocking、destructuring 深さ 近似 |
| **L3 スタイル・イディオム** | Splint (`clj -M:lint-splint`) | Clojure イディオム違反、リファクタリング提案 | `(= 0 x)` → `(zero? x)`、`(first (filter ...))` → `(some ...)` 等 |
| **L4 設定ファイル・ディレクトリ構造** | `.llm/scripts/*.sh` + `.llm/scripts/*.clj` | EDN 構造、ファイル実在、採用宣言、file-level 照合、source 文書から生成物生成、併用禁止関係検知 | brick 登録（hook 取り込み）（プレースホルダ）（総合検査）、非推奨ライブラリ採用、interface 契約、1 ファイル 1 ns、`gen_lib_catalog.clj` による STACK_GUIDE.md §3 からの生成物生成、**`check-conflicting-libs.sh` による `:conflicts-with` ペア検知** |
| **L5 依存脆弱性（時間軸）** | clj-watson (`./.llm/scripts/check-vulnerabilities.sh`) | NIST NVD + GitHub Advisory Database 照合 | 承認済み依存が後から脆弱化した場合の検知。release 前必須 |

**補完関係の典型例**: 非推奨ライブラリ `timbre` は、コード内で `timbre/info` を呼び出している使用箇所は `clj-kondo :discouraged-var`が、`deps.edn` に `com.taoensso/timbre` を採用宣言している箇所は `.llm/scripts/check-deprecated-libs.sh`が検知する。両方で二重に防御する。

**新しい機械化候補を導入する際の判断手順**:

1. 検査対象が Clojure コード内のパターンか、設定ファイル・ディレクトリ構造か
2. コード内パターン → `.clj-kondo/hooks/` に custom hook を追加、`.clj-kondo/config.edn` で登録
3. 設定・構造 → `.llm/scripts/check-<topic>.sh` を追加、`.llm/scripts/check-workspace-integrity.sh` の `run_step` で起動、`.llm/scripts/README.md` を更新
4. Markdown 文書からの生成物生成が必要（単一の正本化による drift 防止）→ `.llm/scripts/gen_<topic>.clj` を追加（`gen_lib_catalog.clj` が雛形）、`deps.edn` に `:gen-<topic>` alias 追加、`check-workspace-integrity.sh` に再生成 + diff 検証を追加
4. 完了条件への組み込みは、shell script 側は `check-workspace-integrity.sh` が既に含まれるので個別追加不要。custom hook は `clj -M:lint` に含まれるので個別追加不要
∵ ../CLAUDE.md §5.5

#### 5.10.1 セッション状態ブリーフィング（セッション起動時、機械化第 1〜第 5 層とは別の役割）

上記の機械化第 1〜第 5 層はすべて **pass/fail 系の検査**（機械化による規約違反の検出）である。これとは別の役割として、**LLM のセッション起動時に現状を提示するブリーフィング**を `.llm/scripts/session-briefing.sh` + `.claude/settings.json` の `SessionStart` hook で実装している。

| 項目 | 内容 |
|---|---|
| **目的** | `CLAUDE.md §8.0`「実装着手前に DESIGN.md / KNOWLEDGE.md / QUESTIONS.md / adr/ を確認」を規律依存から機械化バックアップへ引き上げる |
| **実装手段** | `.llm/scripts/session-briefing.sh`（副作用なし、stdout のみ、常に exit 0）|
| **起動経路** | Claude Code は `SessionStart` hook で自動、Codex 等は `AGENTS.md` 経由で LLM が手動実行 |
| **出力内容** | フェーズ判定（initialization / development）、未完了指標、未対応(open) Q 一覧、最新 ADR、直近コミット、`§8.0` チェックリスト |

機械化第 1〜第 5 層との関係:

- **機械化第 1〜第 5 層は違反を検出する**（pass/fail、終了コードで表現）
- **セッション状態ブリーフィングは現状を見せる**（LLM が何を読むべきかの判断材料を提供）
- 両者は排他ではなく、併用によって「規約違反の早期検知」と「着手前の文脈確立」の両方を機械化する

**Codex 側の非対称性**: Codex には SessionStart hook 機構が存在しないため、`AGENTS.md` に「起動時に `bash .llm/scripts/session-briefing.sh` を実行してから CLAUDE.md に従え」を明記することで、**文書経由の規律依存**にとどまる。構造的制約であり回避しない（`CLAUDE.md §1.2.5` 失敗早期検知と承認設計の思想と整合。LLM の規律逸脱は可逆、AGENTS.md の記述は明示的、Codex 実行頻度も Claude Code より低い、の 3 点で許容範囲）。

**セッション状態ブリーフィングを追加する際の規律**:

1. **pass/fail にしない**: ブリーフィングは終了コード 0 で常に完走する。検査は機械化第 1〜第 5 層の責務
2. **重検査を呼ばない**: `check-workspace-integrity.sh` / `check-vulnerabilities.sh` は起動遅延を招くため、ブリーフィングには入れない
3. **情報の鮮度を優先**: キャッシュせず毎回算出する（ファイル走査は軽量な grep / awk / find / git log に限定）
4. **拡張時の追加先**: ブリーフィングの新項目は `.llm/scripts/session-briefing.sh` の出力関数として追加、`.llm/scripts/README.md` の「セッション起動時のブリーフィング」節を更新

### 5.11 `lint-import-hooks.sh` 再実行のタイミング

`.llm/scripts/lint-import-hooks.sh`は依存ライブラリが提供する clj-kondo hook を `.clj-kondo/configs/` に取り込む。以下のタイミングで再実行する:

- **初期化初回**: `BOOTSTRAP_GUIDE.md §2.9` で実行
- **brick deps.edn への新ライブラリ追加時**: 本節 §5.2 の手順に組み込む
- **STACK_GUIDE.md §3 機能別節 推奨ライブラリ採用時**: §5.6.3（新規ライブラリ採用時の手順）に組み込む
- **`clj -M:outdated` で最新化した後**: 本節 §5.1 の更新手順に組み込む

再実行を忘れると、新ライブラリ固有の lint ルールが機能しないまま開発が進む。**このタイミングを文書化せずに依存追加だけ行うと、非推奨ライブラリ検知や各ライブラリ提供の警告が無効化されるため、必ず上記タイミングで実行する**。

### 5.12 clj-kondo linter 継続点検規律（機械化充実の運用姿勢）

・ の延長。clj-kondo は活発に開発されており新 linter が追加されるため、本テンプレートの機械化を継続的に充実させる規律を定める。

**点検サイクル**:

1. **四半期に 1 回**、clj-kondo の linter 一覧（`https://github.com/clj-kondo/clj-kondo/blob/master/doc/linters.md`）を確認
2. **新規追加された linter** を本テンプレートの原則（全域性・不変性・副作用隔離・機械化・疲労最小化）と照合
3. **採否を判定**:
   - 原則と整合 + false positive リスク低 → **即有効化**（error / warning）
   - 原則と整合 + false positive リスク中 → **warning で試験導入**、安定後に error へ格上げ
   - 原則と整合しない / 機能重複 → **不採用**として本規律に記録
4. ADR 発行は**大規模採用時のみ**（軽微な追加は `.clj-kondo/config.edn` のコメントで記録し、必要なら議論アーカイブに残す）

**新 linter の採否判断基準**:

- **採用**: §1.1 三基底原則に直結、既存 linter と補完関係、false positive が限定的
- **保留**: 運用検証が必要（試験導入は warning で、本採用は error）
- **不採用**: 英語前提（docstring 句読点系）、本テンプレート原則と逆行、Polylith 固有構造と不整合

**サードパーティ lint の扱い**:

- **必須技術基盤**: Splint（スタイル・イディオム）と clj-watson（依存脆弱性）は必須技術基盤として配布（STACK_GUIDE.md §2.1）
- **補完的 lint**: Eastwood（マクロ展開解析）は保留候補、採用時は別 ADR
- **kibit / yagni / cljstyle / zprint**: 機能重複または制約ありで不採用（の調査結果）

**運用上の注意**:

- `.clj-kondo/config.edn` の追加は `.llm/scripts/lint-import-hooks.sh` の再実行が必要ない（組み込み linter のため）。custom hook 追加時のみ再取り込みを要する
- 新 linter 追加で既存コードが失敗するようになった場合、**原則として既存コードを直す**（規約を緩める側に倒さない）。機械化充実姿勢と整合

### 5.13 Markdown 参照マーカー監査

Markdown 文書どうしの参照は、無印の Markdown 参照を禁止し、独立行の marker 付き参照だけを許可する。

- `¤`: 実行前に読む必須参照
- `∵`: 根拠・背景参照
- `⚠`: 問題発生時のみ参照

保守規律:

1. 新規に Markdown 間参照を追加する時は、本文に埋め込まず marker 行へ分離する
2. default scope の整合は `./.llm/scripts/check-doc-references.sh` で常時検査する
3. 文書保守時は `./.llm/scripts/check-doc-references.sh --all` を実行し、全体監査を行う
4. 例外は機械判定できるものだけに限定する。コードブロック、外部 URL、同一文書内参照、規約説明の例示ブロック以外を意味論で免除しない
- false positive の許容は「一括 error で導入、問題が出たら個別に `:config-in-ns` で除外」の順（��断 2）

## 6. 避けるべきアンチパターン

### 6.1 文書の肥大化

**症状**: 「詳細も書いておこう」で CLAUDE.md が 1000 行を超える。
**対処**: CLAUDE.md は常時コンテキストに存在する前提なので、**300 行前後を上限目安**とする。詳細は CODING_GUIDE.md / POLYLITH_GUIDE.md に移す。

### 6.2 規約の形骸化

**症状**: 「書いてあるが守られない規約」が累積する。
**対処**: 原則 2 に従い、規約を追加する時は守らせる手段を同時設計する。手段が設計できないなら規約を削除する。

### 6.3 技術選定の揺らぎ

**症状**: 「より新しいライブラリを見つけた」で選定が変更される。
**対処**: 技術選定の変更は**§7 の規則に従う記録を伴う**。議論なき変更は禁止。

### 6.4 サンプルの混入

**症状**: 「これがあると分かりやすい」でドメイン仮定が入ったサンプルが追加される。
**対処**: 原則 6 に従い、サンプルは POLYLITH_GUIDE.md / CODING_GUIDE.md のコード例ブロックに埋め込む。テンプレートファイルとしては配布しない。

### 6.5 自動検証の無効化

**症状**: clj-kondo の警告が多すぎて `:level :off` にしてしまう。
**対処**: 警告が多いなら**コードが間違っている**。規約は緩めない。規約が現実に合っていないと判明した時のみ、§7 の規則に従って記録して変更する。

### 6.6 「万全の準備」化

**症状**: 「あれば便利」を追加し続けてテンプレートが肥大化する。
**対処**: 原則 5 に従い、配布物は最小化する。「あれば便利」は文書内コード例に留める。

## 9. 本文書の保守

本文書自身の更新時は：

- §7 の記録先表に従い、必要なら ADR または議論アーカイブに記録する（「議論の軌跡を残す」）
- 新しい原則を §4 に追加する場合、連番を続ける（見出しは `原則 N: <名称>` 形式）
- **原則を追加した場合、原則 12 に従い全文書への遡及適用を必ず実施する**
- 原則の削除・改訂は慎重に。変更前の版は ADR または議論アーカイブで保全する
- CLAUDE 冒頭からの参照リンクを維持する

### 9.1 原則 12 遡及適用の実施手順

新原則を §4 に追加した場合：

1. **全文書リストで点検対象を確定**:
   - ルート: README.md、CLAUDE.md、DESIGN.md
   - .llm/guide/: CODING_GUIDE.md、POLYLITH_GUIDE.md、STACK_GUIDE.md、COLLABORATION_GUIDE.md、BOOTSTRAP_GUIDE.md、本文書
   - .llm/memory/: QUESTIONS.md、KNOWLEDGE.md、adr/README.md、adr/template.md、既発行 ADR
2. **各文書を新原則で読み直し、違反箇所を洗い出す**
3. **違反一覧を表にまとめ、「修正コスト × 修正効果」で判定**（全体として改善するか）
4. **修正実施。単独追記ではなく既存体系の改善として統合実施**
5. **点検結果と修正内容を §7 の規則に従って ADR または議論アーカイブに記録**

このプロセスは「原則を増やすだけでなく、既存体系を新原則で再評価する」作業である（原則 12 本文参照）。

**機械的検索の活用**: 遡及適用時は**推測による影響範囲判断を避け、`grep -rn` 等で該当箇所を網羅確認**する。実例としてプロジェクト用途構成の整理時、既存文書の「Integrant」「コメントアウト」「§6.5」等の言及箇所を grep で確認し、影響範囲（9 ファイル・58+ 箇所）を正確に把握できた。LLM は「意識的に機械的確認を行う」規律を持たないと、知識の穴を推測で埋める傾向がある。

**注意**: 遡及適用は 1 回で完結しない。気付きに応じて継続的に再点検する。実例として分類管理の原則追加時の遡及適用で CLAUDE.md §0 の仕様情報残存を見落とし、後日の README.md 新設時に併せて修正した。

### 9.2 構造的対称性への気付き

ファイル・文書の配置において、**対称性や一貫性の欠落に気付いたら即時に解消する**。
原則追加時でなくても、既存体系の対称性を高める機会は逃さない。
実例：当初 `CLAUDE_QUESTIONS.md` のみルート直下だった配置を `.llm/memory/` 対称配置に修正、
`docs/` への違和感から `.llm/memory/` と `.llm/guide/` の対称構造に再編成。
これらは新原則追加ではなく、構造的直感に基づく改善であった。

### 9.3 保守作業における姿勢：整理優先（開発・保守共通）

> 「新規追加より整理を優先する」という姿勢は、**文書とコードの両面で有効**であり、本テンプレートの品質維持の両輪をなす。
> コード側の具体化は `CODING_GUIDE.md` §2.4 を参照。本節は文書側を扱う。

#### 9.3.1 基本姿勢

文書に何かを**加える前に、既存文書を点検する**。以下の順序で判断：

1. **既存の節・記述・参照関係で実現できないか** → できるなら追加しない（YAGNI）
2. **既存の記述を整理すれば実現できないか** → そちらを優先
3. **新しい節・文書が本当に必要か** → 必要性を議論（分類管理の原則に照らす）
4. **上記を経て必要と判断されたものだけを追加する**

この姿勢は「文書の自己整合性」の**実装技法**であり、原則 12（遡及適用）を実施する時の**心構え**でもある。

#### 9.3.2 具体場面

**場面 A: 新しい節を追加したい時**

- 既存節で扱うべき内容ではないか確認
- 既存節の拡張で済まないか検討
- 本当に独立した節が必要なら追加

**場面 B: 新しい原則を立てたい時**

- 既存原則 1〜13 のどれかで説明できないか確認
- 既存原則の延長・実装技法として位置づけられないか検討
- **原則群の階層を崩す概念**（判断基準レベルではない姿勢論・方法論）は原則として立てない（本節の新設もその判断の結果）
- 既存原則の深い運用で対応できないなら、原則 12 遡及適用を経て新原則として追加

**場面 C: 同じ情報を複数箇所に書きたい時**

- **DRY 違反の予兆**。どこを**一次情報源**とするか決める
- 他の文書は一次情報源への参照のみを持つ
- 情報の実効性が分散で高まる場合に限り、意図的な冗長を許容する（例: CLAUDE.md §11.2 サイクル図）

**場面 D: 既存文書の役割が曖昧になってきた時**

- 責務の再確認。4 種文書分離（分類管理の原則）、.llm/guide / .llm/memory の区分に照らす
- 複数の責務が 1 文書に混在しているなら分割を検討
- 同じ責務が複数文書に分散しているなら統合を検討

#### 9.3.3 整理の具体手法

| 手法 | 適用場面 | 注意点 |
|---|---|---|
| **一次情報源の明示と参照化** | 同一情報が複数箇所にある | どこを真実の源とするか明確に決める |
| **節の統合** | 責務が重複する節が分散 | 「議論の軌跡を残す」を壊さない |
| **節の分割** | 1 節が複数の責務を担っている | 分割後も相互参照で全体像を見失わない |
| **参照表の整備** | 文書間の関係が追いにくい | `CLAUDE.md` 冒頭の参照表のような集約点を作る |
| **非推奨化と削除** | 古くなった記述 | 削除時は ADR または議論アーカイブに経緯を残す |

#### 9.3.4 整理のタイミング

- **新機能・新原則追加の着手前**: §9.3.1 の判断フローを必ず適用
- **原則 12 遡及適用時**: 追加よりも整理の機会を先に点検する
- **文書改訂依頼を受けた時**: 改訂と同時に冗長削減の機会がないか探す
- **テンプレート統合検証時（§5.6.2）**: 年 1 回の検証で全体の整理機会を点検

#### 9.3.5 整理を避けるべき場面

整理優先は原則だが、**例外もある**：

- **変化が激しい議論の最中**: まだ収束していない論点の早期整理は後戻りを招く
- **原則 5（LLM は削除が苦手）への配慮**: LLM による大規模整理は誤削除リスクが高い。人間レビュー必須
- **「議論の軌跡を残す」との競合**: 古い記述でも議論の軌跡として価値がある場合、現行ルール本文ではなく議論アーカイブで保持する

**整理が整理のための整理にならないよう**、常に「この整理は将来のどの保守負担を防ぐか」を自問する。

#### 9.3.6 本節と「文書の自己整合性」・原則 12 との関係

- **「文書の自己整合性」**: 本節はその実装技法。自己整合性は整理を通じて維持される
- **原則 12（遡及適用）**: 遡及適用時は**追加よりも整理の機会を先に点検**する。本節は原則 12 の実施姿勢でもある
- **原則として独立させていない理由**: 本節は**判断基準**ではなく**姿勢・方法論**。原則群の階層的性格（テンプレート設計の判断基準）とは階層が異なるため、原則ではなく §9 保守姿勢の節として配置した（該当経緯は議論アーカイブ参照）

### 9.4 自己適用性：テンプレートの原則はテンプレート自身の設計にも適用される

本テンプレートの原則（疲労最小化、三基底原則、分類管理の原則を含む各原則）は、**テンプレート自身の設計にも適用される**。テンプレート保守者が新規の規約・プロジェクト用途構成・手続き・網羅を追加しようとする時、その追加自体が原則に反していないかを必ず点検する。

#### 9.4.1 具体的な陥穽

以下の動きは原則違反の典型：

- **網羅の追求**: プロジェクト用途構成表、機能領域、手続きリスト等を「すべて書き尽くそう」とする動き。網羅は永久に達成不可能（疲労最小化と自己矛盾）。**判断記録は「知っていることを記録する」、網羅は「全てを記録しようとする」。性格が全く異なる**
- **形式的な当てはめ**: 判断基準を第一原理に求めず、「プロジェクト用途構成表にあるか」「手順書にあるか」で判断する動き。LLM が未記載領域で思考停止する
- **分野のせいにする**: 「ML は Clojure に向かない」「ゲームは JVM に向かない」等の分野スコープ制限で問題を転換する動き。本テンプレートの採用理由は分野とは独立（LLM の自律的低負担実装）
- **手続きの肥大化**: 「未知への対処フロー」「Q の雛形」等を事前に網羅する動き。網羅対象がプロジェクト用途構成から手続きに変わっただけで、同じ誤り
- **二重管理の放置**: 同じ情報を複数箇所に書く動き。真実の一箇所化（選択肢 H で確立）に反する

#### 9.4.2 点検の自問

新規追加を検討する時、以下を自問する：

1. この追加は**網羅を目指す動き**になっていないか
2. 第一原理から導出すれば、この追加なしで解決できないか
3. 追加による**保守コスト**は、得られる便益を上回らないか
4. 追加内容は**判断済み結果の記録**か、それとも**網羅の追求**か
5. 同じ情報が他の場所に既に存在しないか（二重管理のリスク）

自問の結果、追加が正当化されない場合、**追加しない**という判断が正しい。

#### 9.4.3 本節が §4 原則ではなく §9 姿勢に置かれる理由

自己適用性は**原則間の関係を律する姿勢**であり、**判断基準としての原則**とは階層が異なる。原則 12（遡及適用）が「既存文書への原則の適用」を扱うのに対し、本節は「テンプレート設計自身への原則の適用」を扱う。両者は補完関係にあるが、位置づけは異なる。

#### 9.4.4 議論アーカイブとの関係

本節の規律は、議論アーカイブに記録された「設計者が同じ誤りを繰り返した経緯」から導出された。網羅主義への誘惑は**繰り返し発生する**ため、アーカイブでの記録だけでは防げない。保守姿勢として明文化することで、将来の保守者（人間・LLM）への予防線として機能する。
