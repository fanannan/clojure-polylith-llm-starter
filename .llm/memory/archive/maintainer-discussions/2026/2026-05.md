# 2026-05 Maintainer Discussions

## MD-2026-05-006: Structural Evidence 操作面への統合
- **状態**: retained-process
- **作成日**: 2026-05-16
- **吸収先**: [`CLAUDE.md §8`, `README.md`, `.llm/guide/STRUCTURAL_EVIDENCE_QUICKSTART.md`, `.llm/guide/MAINTAINERS_GUIDE.md §5.15`, `.llm/scripts/README.md`, `.llm/scripts/session-briefing.sh`, `.llm/scripts/structural_evidence.clj`, `.llm/scripts/check-evidence-boundary.sh`, `.llm/scripts/check-workspace-integrity.sh`]
- **保持理由**: Structural Evidence を「packet を作る成果物管理」から「次に何をすべきかを返す操作面」へ寄せた判断は、LLM primary user 前提の運用に直結するため、実装意図を残す

### 背景

Structural Evidence workflow は `status` / `search` / `gate` / `declare` / `run` / `close` まで整ったが、情報を列挙するだけでは LLM が次の 1 action を即座に選べない。また Review Fatigue Packet は第 5 の正本ではないと文書に書いても、closed record として検索される以上、packet 内で requirement / knowledge / decision を定義し始める drift を機械的に止める必要がある。

### 決定

1. `evidence.sh what-now` を追加し、active packet、staged diff、未宣言 residual、未実行 evidence、stale candidate から次の 1 action を返す操作面とする。
2. `session-briefing.sh` は Evidence Plane で `what-now` を必ず surface する。次セッションの LLM は packet を探すのではなく、まず「今何をすべきか」を読む。
3. closed record の `invalidated-by` を event-based staleness 判定に使い、`status` / `search` / `what-now` で stale candidate を surface する。stale は即無効ではなく、再利用前の再検証 signal とする。
4. `check-evidence-boundary.sh` を追加し、packet 内で新規 requirement / knowledge / decision を定義することを禁止する。packet は Authority / Structure / Index / Verification への generated view に留める。
5. `evidence.sh is-verified` / `why` を追加し、requirement、public boundary、任意 claim の検証 matrix と evidence chain を query できるようにする。
6. `status` は gap 集約 view として、design coverage、trace completeness、Malli contract、open QUESTIONS、関連 KNOWLEDGE を同じ画面に出す。

### 却下・保留した方向

- query API を多数追加する案: LLM は command を扱えるが、操作面が散ると「次の一手」が曖昧になるため、当面は `what-now` / `is-verified` / `why` に絞る。
- packet を正本化する案: 検索可能性は必要だが、正本性は Authority Plane に残す。
- performance / 待ち時間の議論で evidence model を縮退させる案: 性能改善は別論点として扱い、今回の設計判断からは切り離す。

## MD-2026-05-005: Structural Evidence の統合評価 anchor
- **状態**: retained-process
- **作成日**: 2026-05-16
- **吸収先**: [`CLAUDE.md §1.3`, `CLAUDE.md §8`, `.llm/guide/STRUCTURAL_EVIDENCE_QUICKSTART.md`, `.llm/guide/MAINTAINERS_GUIDE.md §5.15`, `.llm/scripts/structural_evidence.clj`, `.llm/scripts/session-briefing.sh`]
- **保持理由**: Structural Evidence は「足しすぎ」批判と「LLM 能力の過小評価」批判の両方に振れやすい。今後の判断で極端な simplification / over-engineering に戻らないため、LLM primary user を前提にした統合評価を process narrative として残す

### 背景

Structural Evidence View の実装後、全体統合の観点から「Evidence Plane だけが肥大し、第一原理の疲労最小化に反しているのではないか」という批判が出た。

これに対して、いったんは `0 new commands` / commit message footer 中心へ戻す radical simplification 案が検討された。しかし、その案は人間中心の単純化であり、LLM が主たる利用者であるという本テンプレートの前提を十分に活かしていない。

LLM は structured packet、複数 command、schema、cross-reference、EDN/Markdown の使い分けを人間より低い認知負荷で扱える。一方で、LLM が苦手なのは stale evidence の判別、暗黙 cross-reference の発見、session を跨ぐ context 維持、待ち状態での進行管理、未 surface の次アクション把握である。

### 決定

1. Structural Evidence View は維持する。commit message だけを ledger にする全面置換は採用しない。
2. ただし Evidence Plane を第 5 の正本にしない。packet は Authority / Structure / Index / Verification への generated view / evidence record / inter-session memory であり、新しい requirement、knowledge、decision を定義してはならない。
3. 「LLM の疲労」を人間の手順暗記疲労と同一視しない。command 数や field 数そのものより、次アクションが surface されないこと、stale 判別ができないこと、既存 plane との接続が弱いことを優先的に問題視する。
4. 今後の改善は、Evidence Plane を増築するより、既存 plane を強く結び直す方向を優先する。特に DESIGN gap、trace completeness、Malli contract coverage、open QUESTIONS、KNOWLEDGE 参照頻度、closed evidence の freshness を briefing / status / gate に surface する。
5. query API を増やす場合は少数精鋭にする。候補は `what-now`、`why`、`is-verified` 程度に留め、抽象的な system-health や calibration profile は record が十分蓄積してから検討する。
6. performance / 待ち時間系の改善は重要だが、設計判断とは分離して扱う。性能問題を理由に evidence model 自体を commit message footer へ縮退させない。
7. LLM primary user という anchor から見ると、正しい方向は「削って 0 command に戻す」ではなく、「LLM が構造化情報を扱える前提で、Evidence を workflow の自然な背骨にし、既存 plane の力をもっと引き出す」ことである。

### 判断基準

今後 Structural Evidence 周辺の提案を評価する時は、以下を問う。

1. それは LLM が得意な structured I/O、cross-reference、query 駆動を活かすか。
2. それは LLM が苦手な stale 判別、暗黙 context 探索、session 間記憶、次アクション把握を減らすか。
3. それは Authority / Structure / Index / Verification の既存 plane を強くするか、それとも Evidence Plane に新しい正本性を増やすだけか。
4. packet が requirement / knowledge / decision を定義する方向に drift していないか。
5. 人間向けの単純化を、LLM 向けの生産性向上と取り違えていないか。

### 却下・保留した方向

- `0 new commands` / commit message footer を主 ledger にする案: LLM の structured data 処理能力を活かせず、検索性、freshness、cross-reference、evidence tier を弱めるため不採用。
- command 数や packet field 数を主理由に削る案: LLM 主利用者の前提では弱い批判であり、具体的な疲労源に分解してから判断する。
- calibration profile / system-health / pattern synthesis の即時実装: 概念価値はあるが、十分な closed record 蓄積前は誤 signal になりやすいため保留。

## MD-2026-05-004: Structural Evidence View MVP
- **状態**: open
- **作成日**: 2026-05-15
- **吸収先**: [`CLAUDE.md §1.3`, `.llm/guide/STRUCTURAL_EVIDENCE_QUICKSTART.md`, `.llm/guide/MAINTAINERS_GUIDE.md §5.15`, `.llm/scripts/README.md`, `.llm/scripts/session-briefing.sh`, `.llm/scripts/check-workspace-integrity.sh`, `.llm/scripts/evidence.sh`, `.llm/scripts/structural_evidence.clj`, `.llm/scripts/derive-change-scope.sh`, `.llm/scripts/inspect-derivation.sh`, `.llm/scripts/propose-review-packet.sh`, `.llm/scripts/check-residual-declared.sh`, `.llm/scripts/check-structural-evidence-self-test.sh`, `.llm/work/.gitignore`]

### 背景

Evidence-Centered Trust の議論を本テンプレートへ適用すると、単に信頼性機構を追加するのではなく、`CLAUDE.md §1` の疲労最小化を時間軸へ拡張する必要があると分かった。

本テンプレートには Polylith 境界、Malli 契約、trace metadata、generated maps、`check-*.sh` が既にある。Django+JS 文脈のように LLM が scope を宣言するのではなく、git diff と既存構造から scope / archetype / required evidence を導出できる。

### 決定

1. 中心原則を `Derive First, Declare Residual, Preserve Only What Reduces Future Fatigue, Audit Derivation` とする。
2. Review Fatigue Packet は第 5 の正本ではなく、次セッションが検証済みの足場を復元するための generated view とする。
3. LLM は scope を宣言しない。導出不能な semantic impact、override、unknown、remaining fatigue だけを `none` または list で明示する。
4. derivation pipeline は agent-invariant primitive とし、Claude / Codex / subagent は `.llm/scripts/` の同一 script を呼ぶ。
5. 初期 MVP は `derive-change-scope.sh`、`inspect-derivation.sh`、`propose-review-packet.sh`、`check-residual-declared.sh`、`check-structural-evidence-self-test.sh` に限定する。close gate、event staleness、pre-flight search、residual decay は後続とする。
6. `.llm/work/` は active generated view であり git 管理しない。closed evidence record の永続化は派生プロジェクトの privacy / commit policy に委ねる。
7. `llm-declared` residual は packet 生成時に自動で `none` にしない。closed packet では `none` または具体値を必須とし、`check-residual-declared.sh` で検査する。
8. Evidence Plane は `session-briefing.sh` に surface する。packet が次セッション冒頭で読まれない状態は inter-session memory として未完成とみなす。
9. packet は git diff だけでなく、存在する生成 index (`brick-map.edn`、`workspace-map.edn`、`trace-index.edn`、`design-ir.edn`、`libs.edn`) と 4 文書系の関連 context を読む統合 view とする。
10. Structural Evidence derivation self-test は aggregate gate (`check-workspace-integrity.sh`) に組み込み、導出規則の破損を通常検査で検出する。
11. Evidence を task の成果物ではなく workflow の現在状態として扱うため、主導線を `evidence.sh status` / `predict` / `declare` / `close` に再構成する。`derive` / `propose` / `inspect` は低レベル debug / 生成 view として扱う。

### 却下・保留した方向

- 4 文書を evidence ledger と呼ぶ案: 分類管理を壊すため不採用。4 文書は Authority Plane の正本であり、packet は索引に留める。
- commit message を主 ledger にする案: squash / rebase / 構造検査 / 再検索に弱いため不採用。summary としての利用に留める。
- trust score / 星表示: 初期段階では誤信頼を生むため不採用。signal / evidence tier を優先する。
- `.work/<id>/` の自由記述 dossier: LLM の自己申告を増やすため不採用。導出 view + residual に限定する。
- close gate の即時 hard gate 化: derivation 自体の self-test と inspectability が先であるため後続に回す。

## MD-2026-05-003: IDEA-first specification flow and DESIGN IR
- **状態**: absorbed
- **作成日**: 2026-05-14
- **吸収先**: [`IDEA.md`, `CLAUDE.md §0`, `DESIGN.md §0`, `README.md`, `.llm/guide/SPEC_GUIDE.md`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.0`, `.llm/guide/TEMPLATE_USAGE_GUIDE.md`, `.llm/guide/COLLABORATION_GUIDE.md §3.1`, `.llm/templates/PROJECT_README.md`, `.llm/scripts/gen_design_ir.clj`, `.llm/scripts/check-workspace-integrity.sh`, `.llm/scripts/template-tests/check-design-ir-scenarios.sh`]

### 背景

DESIGN を自由記載から Polylith 構造へ変換する議論では、人間に最初から十分な仕様文書を書かせること自体が疲労源になると分かった。

一方で、DESIGN を軽くしすぎると仕様正本が曖昧になり、brick / test / Malli 契約との追跡が弱くなる。既存の `brick-map.edn` / `workspace-map.edn` / `libs.edn` は実装側・技術選定側の分析情報として存在するため、仕様側にも最小の機械可読 index が必要になった。

### 決定

1. `IDEA.md` を任意の着想メモとして追加する。存在しない場合・雛形だけの場合はスキップし、従来通り DESIGN から進める。
2. `IDEA.md` は仕様正本ではない。実装判断は常に DESIGN を優先する。
3. LLM は IDEA の内容を reconciliation table、DESIGN 反映案、矛盾、質問候補に分解する。仕様確定は人間レビュー後に限る。
4. DESIGN 更新後、`.llm/data/design-ir.edn` を生成する。
5. design-ir は DESIGN から明示 ID / use case / acceptance item を抽出し、既存の `brick-map.edn` / `workspace-map.edn` / `libs.edn` が存在する場合は coverage / implementation-index として照合する。
6. design-ir は生成物であり正本ではない。正本は DESIGN、brick の意図は `brick.edn`、公開 API 契約は `interface.clj`、技術選定カタログは STACK_GUIDE に残す。
7. `SPEC_GUIDE.md` を追加し、reconciliation は保存しない一時レビュー表、test obligation は実テスト本体ではない中間義務、DESIGN 更新 impact 分類は LLM の説明出力であると固定する。
8. DESIGN IR generator には template-maintenance scenario test を追加し、日常ゲートではなく保守 E2E として扱う。
9. coverage では、実装 requirement と constraint requirement を分離する。§6/§7/§9 の ID が実装 index から参照されても、未割当の実装要求とは扱わない。
10. 受入基準の長期 trace ID は `AC-001:` / `TO-001:` の明示形式だけを採用する。明示 ID がない受入基準は、行番号ではなく文言 hash 由来の `TO-XXXXXXXX` にする。
11. 仕様翻案の曖昧語カタログは置換辞書ではなく応用のための作業 index とする。例や数値は採用済み基準ではなく、実情に合わせて受入基準・制約・質問へ展開する。
12. reconciliation では、解釈した意図、置いた仮定、捨てた意味、確度、質問優先度、数値根拠を明示する。根拠のない数値は仕様確定せず質問化する。
13. 受入基準は、可能な範囲で `[UC-1][REQ-001]` と検証方法を含む形へ LLM が整える。人間には記法を強制しない。
14. ドメイン用語は曖昧語より危険な場合があるため、状態遷移・権限・schema・監査に影響する語は DESIGN / KNOWLEDGE / QUESTIONS / ADR のいずれかへ定義する。
15. design-ir は受入基準本文中の `[REQ-001]` / `[UC-1]` 形式を test obligation の related trace として抽出し、未知参照は diagnostics に留める。未知参照を即 ERROR にする運用は既存・初期化中 repo には重すぎるため採用しない。
16. テンプレート repo のルート README はテンプレート利用開始時の入口として保持する。派生プロジェクトでは同じ `README.md` をプロダクト入口として半自動生成・完全置換し、テンプレート説明を残さない。完全置換後にテンプレートの由来・初期化思想・参照導線を読み返す入口は `.llm/guide/TEMPLATE_USAGE_GUIDE.md` に置く。

### 却下・保留した方向

- IDEA を必須化する案: 入口が重くなり、既存の DESIGN 直接運用を壊すため不採用。
- IDEA と DESIGN の厳密な自然言語差分検査: LLM 判断への依存が強く、初期実装では機械検査として硬すぎるため保留。
- DESIGN の全文を構造化しようとする案: 自然言語仕様を無理に完全 IR 化すると、かえって二重正本化するため不採用。明示 ID とチェックリスト中心の保守的抽出に留める。
- reconciliation の永続ファイル化: 第 5 の正本になり drift を生むため不採用。未吸収の行は DESIGN / QUESTIONS / KNOWLEDGE / ADR へ吸収するか破棄する。

## MD-2026-05-002: Capability plan before brick creation and pure component examples
- **状態**: absorbed
- **作成日**: 2026-05-14
- **吸収先**: [`.llm/guide/BOOTSTRAP_GUIDE.md §2.3`, `.llm/guide/POLYLITH_GUIDE.md §1.1`, `.llm/guide/POLYLITH_GUIDE.md §2.1`, `.llm/scripts/check-interface-contracts.sh`]

### 背景

LLM 時代の疲労最小化では、自然言語の DESIGN から直接 brick 実装へ進むと、capability 境界・副作用境界・Malli 契約を LLM が推測する余地が大きい。

また、純粋ドメイン component の標準例が `random-uuid` / `Instant/now` を core 内で呼んでおり、「純粋関数」と説明しながら非決定性を持つ例になっていた。LLM は標準例を強く模倣するため、これは修復コストを増やす。

### 決定

1. 最初の brick 作成前に、DESIGN の要求から短い capability plan を提示して承認を得る。永続ファイル化は必須にしない。
2. capability plan では requirement、capability、brick、kind、effect、public function を明示する。
3. `DESIGN.md` 自体を data contract 化しない。DESIGN はプロダクト合意の正本に留める。
4. `brick.edn` に input/output schema は入れない。契約の正本は `interface.clj` / Malli schema に置く。
5. `:brick/effect` は現時点では導入しない。ただし設計時に `:pure` / `:adapter` / `:entry` 相当の区別を考えることを明記する。
6. 純粋ドメイン component の例では、時刻・乱数・UUID 生成を core 内で行わない。外側で生成して値として渡す。
7. `check-interface-contracts.sh` は `m/=>` の存在検査であり、arity 整合や schema 意味妥当性を保証しないことを明記する。

### 却下・保留した方向

- `DESIGN.md` に Malli schema / capability graph / fixture を詰め込む案: 分類管理を壊し、仕様合意文書が重くなるため不採用。
- `brick.edn` に入出力 schema を持たせる案: `interface.clj` と二重正本になり drift を増やすため不採用。
- component 全体への I/O 禁止を即時機械適用する案: adapter component が正当な Polylith 設計として存在するため保留。effect 分類を明示してから再検討する。
- 全受入基準への property test 強制: 意味の薄い property test を増やすため不採用。検証種別は要求ごとに選ぶ。

## MD-2026-05-001: Brick/project/workspace intent maps
- **状態**: retained-process
- **作成日**: 2026-05-13
- **吸収先**: [`.llm/guide/POLYLITH_GUIDE.md §1.1`, `.llm/guide/POLYLITH_GUIDE.md §1.2`, `.llm/guide/POLYLITH_GUIDE.md §1.3`, `.llm/guide/POLYLITH_GUIDE.md §1.4`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.3`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.5.1`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.5.2`, `.llm/guide/MAINTAINERS_GUIDE.md §5.14`, `CLAUDE.md §8.0`, `.llm/scripts/gen_brick_map.clj`, `.llm/scripts/gen_workspace_map.clj`, `.llm/scripts/check-brick-map.sh`, `.llm/scripts/check-workspace-map.sh`, `.llm/scripts/ensure-brick-map.sh`, `.llm/scripts/ensure-workspace-map.sh`, `.llm/scripts/propose-brick-edn.sh`, `.llm/scripts/propose-project-edn.sh`, `.llm/scripts/template-tests/check-map-scenarios.sh`]
- **保持理由**: `brick.edn` / generated map の位置づけは、正本の二重管理と機械化の境界を誤ると再検討が起きやすいため、判断過程を process narrative として残す

### 背景

Polylith brick が増えると、LLM と人間は「どの機能がどの brick にあるか」「新規実装すべきか、既存 capability を使うべきか」「base と component の責務を混同していないか」を毎回再発見することになる。

README や手書き Markdown に機能分担を書くだけでは drift し、テンプレートの疲労最小化・機械化・真実の一箇所化に弱い。一方で、コードや Polylith が既に正本として持つ情報を EDN に重複管理すると、別の drift を生む。

### 決定

`brick.edn` はコードの代替正本ではなく、コードだけから安全に復元できない brick の設計意図を持つ。

- component の capability ownership
- base の entrypoint と利用 capability
- `:brick/not-for` による誤配置防止
- DESIGN 要求 ID との対応
- 人間/LLM が既存機能を探索するための要約

公開 API と Malli 契約の正本は `interface.clj`、実装事実の正本は `core.clj` / `system.clj`、依存の正本は brick の `deps.edn`、Polylith 構造の正本は `workspace.edn` と実ディレクトリ構造に置く。

`docs/BRICKS.md` と `.llm/data/brick-map.edn` は正本ではなく生成物とする。前者は人間が読むビュー、後者は LLM / script が検索する index である。直接編集は禁止し、drift は `check-workspace-integrity.sh` 経由で検出する。

### 実装順序

新規 brick では、実装より先に `brick.edn` を作る。

1. DESIGN の要求を確認する
2. 既存 `docs/BRICKS.md` / `.llm/data/brick-map.edn` で重複 capability を探す
3. 新規 brick が必要な場合、`brick.edn` で capability ownership / entrypoint / not-for / requirements を宣言する
4. `interface.clj` の公開 API と `m/=>` 契約を設計する
5. `core.clj` / `system.clj` を実装する
6. `docs/BRICKS.md` / `.llm/data/brick-map.edn` を再生成する
7. integrity check で drift と境界違反を検出する

### 既存 repo への導入

既存 repo では `brick.edn` 欠落を単に ERROR にしない。まず `propose-brick-edn.sh` で案を表示し、必要なら `ensure-brick-map.sh` で skeleton と下流生成物を作る。

自動推測できるのは `:brick/name`、`:brick/type`、公開 API 候補までである。`:brick/purpose`、`:brick/provides`、`:brick/not-for`、`:brick/requirements` は設計意図なので TODO として残し、人間/LLM が DESIGN と実装を見て確定する。

`retrofit` / `partial` では TODO を WARN、`complete` では ERROR として扱う。

### 要求 ID 対応の検査順序

ID 対応は順序を誤ると、未実装の将来要求を不必要に block する。

1. `brick.edn` が参照する ID が `DESIGN.md` に存在しない場合は ERROR
2. `DESIGN.md` 内で同じ ID 定義が重複している場合は ERROR。ID 自体が壊れている状態では、未参照 / 参照済みの判定が不安定になる。文中参照、範囲表記、fenced code block 内の例示は定義として数えない
3. `DESIGN.md` の ID がどの brick にも参照されていない場合は WARN
4. 未割当要求を実装対象にする時は、先に capability / entrypoint を決めて `brick.edn` に ID を記録する

### 公開関数名

関数名だけで混乱する状態は重複実装の原因になる。ただし、同種の操作を別 brick に分ける場合、`invoice/create` と `customer/create` のように公開関数名を揃えることは自然である。

禁止すべきなのは関数名の重複そのものではなく、capability ownership が不明な重複である。許容条件は、namespace alias と関数名を合わせて意味が読め、`:brick/provides` が `:invoice/create` / `:customer/create` のように一意であること。

### `:brick/group` の扱い

類似機能の brick を俯瞰するために `:brick/group` を導入する案は有用だが、group を Polylith の構造単位として扱うと、component / base / project と `poly check` が担う境界に別軸の正本を増やしてしまう。

判断: `:brick/group` を導入する場合、その役割は検索・俯瞰・再分割 smell の発見に限定する。依存境界、capability ownership、project inclusion、テスト範囲、deploy 単位を group から導出しない。構造判断の正本は引き続き component / base / project、`interface.clj`、`workspace.edn`、`deps.edn`、`project.edn`、`poly check` に置く。

実装判断: `:brick/group` は任意の単数 keyword のみ許容する。set / vector による複数 group は採用しない。複数 group を許すと、brick の主責務が曖昧になり、generated Brick Map 上で同じ brick が複数箇所に現れ、再分割 smell の判断主体が曖昧になる。また group が検索補助ではなく tag や構造制約として使われ始めるリスクが高い。複数の補助軸が必要になった場合は、`:brick/group` の多値化ではなく、別 metadata として改めて採否を判断する。

帰結: group に対する機械検査は、形式検査、generated Brick Map の index、同一 group 内の近接 capability warning などの advisory に留める。group をまたぐ依存を ERROR にする、group から project includes を生成する、group 単位でテスト範囲を決める、といった使い方は採用しない。

実装後の補足: `docs/BRICKS.md` は group-first view を持ち、`.llm/data/brick-map.edn` は `:groups` index を持つ。これは LLM と人間が新規 brick 作成前に近傍 brick を見るための入口である。`CLAUDE.md §8.0` と `POLYLITH_GUIDE.md §1.2` から group 近傍確認へ接続し、LLM が新規 brick を提案する時は候補 group、同一 group の既存 brick、既存 brick に入れない理由を説明する。group mismatch、同一 group 内の近接 operation、base の多 group 利用は advisory warning として出すが、構造制約ではないため完了条件の ERROR にはしない。

### Project / workspace への拡張方針

同じ課題は project と workspace にもあるが、同じ解き方にしない。

`project` は capability を所有しない。導入するなら `projects/<name>/project.edn` とし、deploy / build / entrypoint inclusion の意図だけを持つ。classpath や依存の正本は `projects/<name>/deps.edn` に残す。

`:project/type` は検査ポリシーであり、`:app` / `:library` の 2 値に限定する。service / worker / CLI / batch / lambda などは実行形態であって検査ポリシーではないため、必要な場合だけ任意の `:project/runtime` に置く。3 軸以上の分類は、対応する機械検査が生まれるまで追加しない。

workspace は既に `workspace.edn`、`.llm/repo-context.edn`、`deps.edn` が正本を分担しているため、手書きの追加正本を増やさない。まずは既存正本群から `docs/WORKSPACE.md` / `.llm/data/workspace-map.edn` を生成する方向に留める。

### `poly` command との責務分担

Polylith が既に知っている構造事実は、テンプレート側で再実装しない。`poly check` / `poly test` / `poly info` が扱う領域は、まず Polylith CLI に委譲する。

`poly` に任せる領域:

- workspace 内の project / base / component 認識
- brick 間依存関係
- component / base の境界違反
- project ごとの構成
- 変更検知と影響範囲テスト
- `workspace.edn` の Polylith 的妥当性

テンプレート側が EDN で担う領域:

- capability ownership
- `:brick/not-for`
- DESIGN 要求 ID との対応
- base entrypoint と component capability の意味的対応
- deploy intent
- TODO / migration state
- generated docs / index の drift
- LLM が探索しやすい capability index

`poly` 出力の扱いは慎重にする。machine-readable output がある場合は workspace-map 生成の入力として使う。人間向け表示しかない場合、文字列 parse は壊れやすいため、`poly check` の pass/fail に委譲し、テンプレート側は file / EDN / deps の軽量整合に留める。

判断基準:

```text
poly が machine-readable に出せる構造事実
  → poly 出力を使う

poly が人間向け表示しか出さない構造事実
  → parse の価値と壊れやすさを比較し、原則として poly check に委譲する

poly が知らない設計意図
  → brick.edn / project.edn / generated map で管理する
```

### 却下した方向

- README / 手書き Markdown を機能分担の正本にする案: drift しやすく、機械検査に弱い
- `brick.edn` を実装事実の正本にする案: `interface.clj` / `deps.edn` / Polylith 構造との二重管理になる
- 既存 repo 導入時に欠落 `brick.edn` を即 ERROR にする案: retrofit の初期導入コストが高く、棚卸しが進まない
- 複数 brick の同名公開関数を全面禁止する案: `invoice/create` / `customer/create` のような自然な interface pattern を壊す
- `poly info` の人間向け出力を無条件に parse して workspace-map の正本相当にする案: CLI 表示形式に依存して壊れやすく、Polylith が提供する検査責務をテンプレート側へ重複実装することになる
- schema EDN を直ちに厳密 validator として外部化する案: 現段階では checker と schema の二重管理を増やすため保留。まず `gen_*_map.clj` と template E2E で運用実態を固める
- 自動修復で capability / requirement 対応を推測確定する案: 誤った設計意図を正本化する危険があるため不採用。機械は skeleton と TODO を作り、人間/LLM が DESIGN と実装に基づいて確定する

## MD-2026-05-002: Specification trace metadata boundaries
- **状態**: retained-process
- **作成日**: 2026-05-14
- **吸収先**: [`CLAUDE.md §4.1`, `CLAUDE.md §5.4.1`, `.llm/guide/CODING_GUIDE.md §2.1.1`, `.llm/guide/CODING_GUIDE.md §13.4.1`, `.llm/guide/POLYLITH_GUIDE.md §1.1`, `.llm/guide/SPEC_GUIDE.md §8.1`, `.llm/scripts/check_trace_metadata.clj`, `.llm/scripts/template-tests/check-trace-metadata-scenarios.sh`]
- **保持理由**: 仕様 trace をコード全体へ広げるか、安定境界へ限定するかは疲労最小化と refactor 容易性に直結するため、判断過程を残す

### 背景

DESIGN / design-ir / Clojure コード / テストコードの対応を機械検査できれば、LLM が仕様と実装をずらした時の検出が早くなる。一方で、実装内部の関数すべてに requirement ID や test obligation ID を付けると、内部 refactor のたびに trace 更新が必要になり、仕様駆動開発のための metadata が逆に保守疲労を増やす。

### 決定

実装コード側の trace metadata は stable public boundary に限定する。

- component では `interface.clj` の公開 `defn`
- base では外部 entrypoint に近い公開 boundary `defn`
- `core.clj`、private helper、adapter 内部には付けない
- test obligation は実装関数ではなく `deftest` の `:trace/test-obligations` にだけ置く
- `brick.edn :brick/requirements` は brick 全体の粗い ownership、Clojure metadata は公開関数単位の対応として使い分ける

### 機械化

`.llm/scripts/check-trace-metadata.sh` は `.llm/data/design-ir.edn` を正本として Clojure top-level form を検査する。

- 未知 requirement / use case / test obligation ID は ERROR
- 空 ID、空 vector、重複 ID は ERROR
- internal implementation への trace metadata は ERROR
- 実装関数への `:trace/test-obligations` は ERROR
- `deftest` の `:trace/requirements` / `:trace/use-cases` と test obligation の related IDs 不整合は、`:adoption-mode :complete` では ERROR、`:retrofit` / `:partial` では WARN
- design-ir の test obligation がどの `deftest` からも参照されない場合も、`:adoption-mode :complete` では ERROR、`:retrofit` / `:partial` では WARN

未対応 test obligation は既存 repo 導入時の移行余地を残すため、`:retrofit` / `:partial` では WARN に留める。strict 準拠完了後の `:complete` では ERROR とし、仕様義務がテスト trace から落ちた状態を完了条件で止める。

`.llm/scripts/gen-trace-index.sh` は `docs/TRACE.md` と `.llm/data/trace-index.edn` を生成する。これは検査ではなく活用層であり、requirement / use case / test obligation から public boundary と `deftest` へ辿る impact map を提供する。LLM は DESIGN 更新時に trace-index を読み、修正対象を先に列挙してから実装する。

### 却下した方向

- すべての関数に trace metadata を付ける案: refactor に弱く、内部実装の設計自由度を下げる
- implementation 関数へ `:trace/test-obligations` を付ける案: 「何を実装するか」と「何を検証したか」が混ざり、テスト義務の未充足を隠す
- コメントで ID を書く案: 構造検査できず、命名・文体変更で drift しやすい
