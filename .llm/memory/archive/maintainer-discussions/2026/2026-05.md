## MD-2026-05-020: brick 作成者・ライセンス属性と参照 brick 流用の L0 ゲート

- **状態**: retained-process
- **作成日**: 2026-05-17
- **吸収先**: [`.llm/scripts/gen_brick_map.clj`, `.llm/scripts/reference_repos.clj`, `.llm/scripts/reference-repos.sh`, `.llm/reference-repos.edn`, `.llm/scripts/check-workspace-integrity.sh`, `.llm/scripts/session-briefing.sh`, `.llm/scripts/README.md`, `.llm/scripts/propose_repo_context.clj`, `.llm/repo-context.edn`, `.llm/guide/POLYLITH_GUIDE.md §1.1`, `.llm/guide/POLYLITH_GUIDE.md §9.1`, `.llm/guide/POLYLITH_GUIDE.md §9.2`, `.llm/guide/POLYLITH_GUIDE.md §9.4`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.6.1`, `CLAUDE.md §2`, `.llm/guide/MAINTAINERS_GUIDE.md §3.3`, `.llm/guide/MAINTAINERS_GUIDE.md §5.14`, `.llm/template-only/tests/check-map-scenarios.sh`]
- **保持理由**: 別 repo の brick を流用する際の著作権・ライセンスリスクは、参照機能を使うたびに再発する判断である。「誰が書いた brick か」を属性として持たせ、流用可否を L0 へ倒す判断と、その判断を機械検査ではなく宣言・証拠の照合 + 文書プロトコルで機械化した理由を残す。今後 brick 属性を増やす提案や、参照機能を機械化する提案の anchor になる。

### 背景

`.llm/reference-repos.edn` allowlist と POLYLITH_GUIDE §9 の参照機能（MD-2026-05-001）は、別 repo の brick を比較材料として読み、取り込み先 DESIGN に合わせて再実装するモデルである。運用を想定すると次の欠陥が出た。

- 参照先 brick の作成者を知る手段がなく、別作者の成果をアイデアだけ流用する場合でもライセンス・著作権上のリスクが評価されないまま再実装へ進める。
- brick.edn は責務・境界を表す 9 フィールドを持つが、cross-repo で把握すべき「作成者」「ライセンス」を表現できない。
- `.llm/reference-repos.edn` はどのスクリプトからも参照されない手編集 EDN で、絶対パスの手入力・出自条件の手確認・登録内容の一覧と検証手段がなく、指定が分かりにくい。

### 決定

1. **brick.edn に `:brick/authors` と `:brick/license` を追加する**。`:brick/authors` は非空の文字列コレクション（誰が書いたかの宣言）。`:brick/license` は任意の SPDX 識別子文字列で、欠落時は repo ルートの LICENSE 継承と解釈する。
2. **作成者は宣言と証拠の照合方式で扱う**。brick.edn の `:brick/authors`（宣言＝主張）と、`gen-brick-map` が brick ディレクトリの `git log` から導出する作者集合（証拠）を照合する。**不一致は L0 reconciliation 対象**として報告し、`:complete` では ERROR、`:retrofit`/`:partial` では WARN とする。git 履歴のない未コミット新規 brick は不一致扱いしない。これは CLAUDE.md「主張と証跡の対応」モデルに沿う。
3. **参照 brick の流用可否は L0 へ倒す**。参照先 brick.edn の `:brick/authors` が現作業者の git author と一致する単一作者なら通常の再実装承認フロー、別作者・複数作者・欠落なら L0（人間専権）。アイデアのみの流用も対象。参照→再実装モデル（MD-2026-05-001）は転換せず、コピー方式は採らない。
4. **L0 ゲートは機械検査ではなく文書プロトコルで機械化する**。POLYLITH_GUIDE §9.4 に判定アルゴリズムを置き、CLAUDE.md §2 の L0 判断表に 1 行加える。参照先 repo を再帰走査する検査は作らない。
5. **git 導出は brick-map.edn に焼き込まない**。brick-map.edn に git 作者を含めると brick への commit のたびに生成物が変わり再生成 churn を生むため、導出と照合は `check` 時の transient な検証に留め、brick-map.edn は brick.edn 由来の宣言値のみを持つ。
6. **再実装時は元 repo の ID を持ち込まない**。`:trace/*` メタデータ・`TODO(Q-*)` コメント・ADR 参照は再実装先の ID 体系へ再マッピングする。既存 `check-trace-metadata.sh` / `validate-cross-brick!` / `contains-todo?` が事後の安全網。§9.4 に明文化する。
7. **参照レポ指定にヘルパースクリプトを設ける**。`.llm/scripts/reference-repos.sh`（`add` / `list` / `check`）と `reference_repos.clj` を新設し、出自検証・一覧・有効性検査を機械化する。
8. **`.llm/reference-repos.edn` を `:ownership :project-owned` に分類する**。allowlist は派生プロジェクトごとに異なる開発設定で DESIGN.md から導出できない。独立ファイルのまま `:project-owned` とし、`.llm/repo-context.edn` と `propose_repo_context.clj` の `default-ownership` の両方に反映する。template は空 `:allowed-repos` の scaffold を seed するが、内容は派生プロジェクトが所有する。
9. **bootstrap に参照 repo 登録の任意ステップを置く**。`BOOTSTRAP_GUIDE.md §2.6.1`「参照 repo の登録（任意）」を追加。identity gate（必須項目）には加えず、config.edn 等と同じ任意 tier に置く。`§2.9` 以降への参照が複数ファイルに及ぶため新規 §2.N は起こさず、任意 dev 設定である §2.6 のサブセクションとする。

### 却下した方向

- **コピー方式での brick 取り込み**。著作権チェックが意味を持つ取り込み実体はコピーだが、ユーザー確認の結果、参照→再実装モデルを維持する方針が確定したため却下。MD-2026-05-001 は転換しない。
- **`:brick/authors` を brick.edn に宣言として持たず git から完全自動導出する案**。cross-repo の参照側は相手 repo の brick.edn を file 読みするため、宣言フィールドが brick.edn に無いと作者を知れない。宣言 + 照合に倒した。
- **宣言・証拠の不一致を一律 CI ERROR にする案**。表記揺れ・rebase で恒常的に赤くなり疲労最小化に反する。不一致は L0（人間判断）として扱い、`:complete` でのみ stop とした。
- **`:brick/origin`（brick 単位の流用元マーカー）の追加**。MD-2026-05-001 が出自証明は repo 単位で足ると決定済みで、参照→再実装モデルでは流用元を brick に刻む必要がない。YAGNI で却下。
- **cross-workspace catalog / 参照先 repo 全 brick の再帰走査検査**。MD-2026-05-001 が「重すぎる」として却下済みの方向であり再採用しない。
- **`:reference-repos` を `.llm/repo-context.edn` に統合する案**。manifest に allowlist を持たせると、`repo-context.edn` が `:template-owned` のため派生プロジェクトでの登録操作が `check-mode-scope` の template-owned 変更検出に触れる。独立ファイル + `:project-owned` 分類を採った。

### 実装状況

2026-05-17 時点で本 MD と同一の作業として、gen_brick_map.clj のスキーマ拡張・git 作者照合、reference-repos ヘルパー、POLYLITH_GUIDE §9.4 新設、CLAUDE.md L0 表追記を実装する。follow-on として、`.llm/reference-repos.edn` の `:project-owned` 分類（`repo-context.edn` / `propose_repo_context.clj`）と `BOOTSTRAP_GUIDE.md §2.6.1` の任意登録ステップも同じ作業群で実装する。

## MD-2026-05-019: Instruction-Following Instrument の再定義

- **状態**: retained-process
- **作成日**: 2026-05-17
- **吸収先**: [`.llm/guide/MAINTAINERS_GUIDE.md §5.18`, `.llm/template-only/instrument/README.md`, `.llm/template-only/instrument/incident-index.edn`, `.llm/template-only/instrument/cases.edn`, `.llm/template-only/instrument/check-cases.sh`, `.llm/template-only/instrument/setup-run.sh`, `.llm/template-only/instrument/score-run.sh`, `.llm/template-only/instrument/summarize-runs.sh`, `.llm/template-only/tests/check-instrument-cases-smoke.sh`, `.llm/template-only/tests/check-instrument-setup-smoke.sh`, `.llm/template-only/tests/check-instrument-summary-smoke.sh`, `.llm/template-only/README.md`, `.llm/template-only/tests/README.md`, `.llm/template-only/benchmark/README.md`]
- **保持理由**: LLM contract test は「規約を守ったか」を測るだけだと、現行規約への過適合、Goodhart 化、reform 循環、文書肥大を招く。指示追随歩留まりを測る計測器として再定義した判断は、今後の contract runner / observer harness / model suitability 議論の anchor になる。

### 背景

session briefing の mode 別 fixture 検査と `--audit` は、LLM contract test の最初の pilot として妥当だった。一方で、議論を進めると次の欠陥が明確になった。

- 単一 run の pass rate を客観的な model 能力値のように扱う危険がある
- reform が md corpus 自体を書き換えるため、同じ suite の pass rate を採否基準にすると循環する
- oracle 側の誤りや md の本当の曖昧性を、agent failure と区別する result type が必要
- 合成 fixture に最適化すると、テンプレートが実運用ではなく suite を通す方向へ退化する
- reform を積み重ねると、指示文書と surface が肥大して salience が下がる

### 決定

1. **名称と目的を再定義する**。中心概念は LLM contract test ではなく Instruction-Following Instrument。第一の産物は指示文書 corpus の曖昧性、摩擦、実インシデント再発、改善圧の発見であり、model suitability table は副産物。
2. **case は実インシデントまたは md mandate に接地する**。`.llm/template-only/instrument/incident-index.edn` を seed index とし、maintainer archive の実観測から case family を起こす。根拠のない合成 case は exploratory bucket に隔離し、template reform の採否根拠にしない。
3. **割れた結果は平均しない**。複数 run / model / seed で結果が割れる case は、flake-rate として丸めず `:spec-ambiguous` として文書改善候補または QUESTIONS へ route する。
4. **数値は N と散らばり付きでのみ扱う**。固定 suite 上の測定は再現可能な観測だが、小 N の点推定は真の能力値ではない。単一 run の pass rate は indicative observation としてだけ読む。
5. **reform 採否は suite 非依存指標に限定する**。Friction 低下、実インシデント再発低下、hard fail 非増加だけを採否軸にし、Contract Pass Rate は採否基準にしない。
6. **corpus 保存予算を置く**。文書総量、surface 数、新 command surface を増やす reform は、同時に統合・削除・移動の検討を要求する。局所的改善が salience を下げるなら却下候補。
7. **遅い gate として扱う**。Instruction-Following Instrument は per-turn loop に入れない。`check-vulnerabilities.sh` と同じく、テンプレート version 境界または release 前に走らせる。
8. **最初の LLM family は 2 つだけにする**。`:mode-and-ownership` と `:resist-flawed-instruction`。session briefing は前者の pilot input であり、目的を session briefing 改善へ閉じない。

### 却下した方向

- `repo-kind` に `:test` を追加する案。agent-visible mode が増え、template/project 判断を汚すため却下。
- Contract Pass Rate を reform 採否の主指標にする案。測定器の目盛り自体を変える循環になるため却下。
- 実インシデントに接地しない合成 fixture を通常 suite に混ぜる案。Goodhart 化を招くため exploratory bucket に限定。
- model 絶対比較を初期目的にする案。adapter / prompt rendering / tool availability の交絡が大きいため、まず template revision regression に限定。
- raw transcript を template repo に commit する案。観測者効果、privacy、noise のため却下。

### 実装状況

2026-05-17 時点で、Phase 1 として `.llm/template-only/instrument/incident-index.edn` を追加し、MD-2026-05-018 / 017 / 014 を initial seed とした。MAINTAINERS_GUIDE §5.18 に用途優先順位、数値の扱い、case 接地、instruction taxonomy、oracle と曖昧性、reform 循環回避、corpus 保存予算、初期 family を固定した。

続く最小実装として、`.llm/template-only/instrument/setup-run.sh` と `cases.edn` を追加した。これは LLM を起動せず、template / project target repo と outside observer store、agent prompt、observation capture script、terminal marker を準備するだけである。template target からは `.llm/template-only/instrument/` を除去し、project target からは `.llm/template-only/` 全体を除去する。`check-cases.sh` は `cases.edn` / `incident-index.edn` を Clojure EDN として読み、non-exploratory case の実インシデントまたは authored mandate への trace を検査する。`score-run.sh` は観測済み run の diff path から単一 run の path-level preliminary score を作り、template run record へ mirror する。`summarize-runs.sh` は複数 score を N / invalid 数 / result 分布として集約し、割れた結果を平均せず `:spec-ambiguous` に route する。`check-instrument-cases-smoke.sh`、`check-instrument-setup-smoke.sh`、`check-instrument-summary-smoke.sh` はこの接地・隔離・採点・集約が壊れていないことを LLM なしで検査する。

実際に LLM を呼ぶ contract runner は未実装。まず `check-session-briefing-scenarios.sh` と `session-briefing.sh --audit` で agent に見せる教材品質を決定的に検査し、setup / scorer / summary は observer harness の土台として扱う。

2026-05-17 follow-on として、最初の authored mandate annotation `:session-start-briefing-first` を `AGENTS.md` に置き、`check-cases.sh` が `:trace/mandates` の実在性を authored `llm-mandate` annotation から検査する形にした。`cases.edn` は実在 annotation のない mandate ID を一旦外し、未注釈の規約は incident trace による接地だけに戻した。

2026-05-17 さらなる是正として、この `AGENTS.md` への mandate 配置を取りやめた。`AGENTS.md` はルート直下に固定される規約上の起動エントリであり、mandate の著作ホームにも projection 先にもしない。briefing-first mandate は不変連番 id `M-0001` として `CLAUDE.md §8.0` に著作し、annotation 書式を不可視の `<!-- llm-mandate {EDN} -->` から可視の 1 行ディレクティブ `[mandate: M-NNNN/hint type:… tier:…]` へ変更した。`check-cases.sh` の mandate scan 範囲を `CLAUDE.md` + `.llm/guide/*.md` に限定し、`cases.edn` の `:trace/mandates` を `M-NNNN` 文字列へ移した。これは指示コーパスを mandate id で join する改革の Track A 初手であり、直前の follow-on が `AGENTS.md` を mandate ホームにした設計判断の誤りを是正したものである。incident-index schema 検査の and/or 修正は、現実装が既に `and` であったため対象なし。

## MD-2026-05-018: control plane 不在診断の修正と salience / mandate-binding drift への絞り込み

デモ実行後の振り返りを広い視野で再評価する中で、「本 repo には上位制御機構が不足しているため `repo-control.sh status/next/done/explain` のような薄い control layer を追加すべき」という提案が出た。続く批判で、この診断は実装事実を過小評価していると指摘された。

確認した事実として、現在の repo には既に次の control plane 相当の分担がある。

- mode / ownership / adoption の SSOT は `.llm/repo-context.edn`
- session 開始時の mode、読むべき文書、所有権境界、Work Frontier、Evidence Plane は `.llm/scripts/session-briefing.sh`
- 次 action の操作面は `.llm/scripts/evidence.sh what-now`
- adoption-mode による blocking / non-blocking は `.llm/scripts/check-workspace-integrity.sh`
- maintainer archive の staging / absorption / stale 判定は `.llm/scripts/check-archive-staleness.sh`

したがって「control plane が無い」という診断は誤り。問題は absence ではなく、既存の分散 control plane が一つの概念として十分に名指されず、LLM の初動を支配するほど顕在化していないことだった。

### 決定

1. **新規 `repo-control.sh` は作らない**。`status` / `next` / `done` / `explain` の新 surface は既存の `session-briefing.sh` / `evidence.sh what-now` / `check-workspace-integrity.sh` と重複し、Capability Sprawl を悪化させる。
2. **改善するなら session briefing の再配置に留める**。必要な場合は `CONTROL PLANE` などの見出しを `session-briefing.sh` に追加し、既存情報を短くまとめる。新しい authority、state、task system は追加しない。
3. **`what-now` は増やさない**。次 action の single surface は既存の `evidence.sh what-now` を維持する。別名 command や抽象的な planner を増やさない。
4. **哲学 drift 検知は mandate-binding drift に絞る**。本当に残る新規余地は、「必須 / 禁止 / 完了条件」と書かれた規約が、script / check / briefing / manifest / explicit no-action のいずれかに接続されているかの advisory 検知である。独立した抽象的 `philosophy` command は作らない。
5. **Evidence 批判を修正する**。Evidence View は authority ではないこと、artifact regime があること、tier があることは既に実装・記録されている。改善余地があるとすれば、evidence tier（取得方法）とは別に「何を保証するか」という語彙を review aid として補う程度であり、新しい gate や正本にしない。

### 診断基準

今後、LLM が「上位機構が足りない」と診断した場合は、機能追加の前に次で分岐する。

1. 情報が成果物・script・manifest から判定できないなら、構造的ギャップとして扱う。
2. 情報は存在するが LLM が読み落としたなら、absence ではなく salience の問題として扱う。修正先は出力順、見出し、要約、警告文であり、新 surface ではない。
3. 単発の実行ミスなら、control plane ではなく局所 check / test / fixture / guide の問題として扱う。

この分岐をせずに抽象的な制御層を足すことは禁止しないが、原則として却下側に倒す。

## MD-2026-05-016: Artifact Regime / Lifecycle / Derivation Manifest の統一
- **状態**: retained-process
- **作成日**: 2026-05-16
- **吸収先**: [`.llm/guide/MAINTAINERS_GUIDE.md §4`, `.llm/guide/MAINTAINERS_GUIDE.md §5.17`]
- **保持理由**: `.llm/data/`、Structural Evidence、Work Frontier はいずれも生成 view / 宣言 / immutable record の境界に関わる。速度最適化ではなく、テンプレート全体の artifact 時間モデルを統一する判断として再燃しやすいため、設計経緯を残す。

### 背景

不変性を単なる Clojure のデータ構造ではなく、問題解決モデルとしてテンプレート全体へ適用できているかを検討した。4 種文書分類は authored current state / immutable decision history / pending question を分離しており、epochal time model としてよく機能している。一方で、`.llm/data/*.edn`、`.llm/work/*`、closed evidence record、Work Frontier は、生成物・宣言・証跡の境界が局所的に混ざっている。

初期議論では `.llm/data/*.edn` の content-addressing 化が速度改善として語られたが、速度は本質ではない。問題は「固定パスにある生成物を現在の真実として扱う」場所セマンティクスが残り、drift / housekeeping / stale-candidate / detached active packet という例外語彙が増えることである。

### 決定

1. 文書分類の原則を artifact 管理にも拡張し、MAINTAINERS_GUIDE に原則 14「Artifact Regime と Lifecycle を明示する」を追加する。
2. すべての artifact を authored current state / derived view / human declaration / immutable record / archive のいずれかに分類する。prune は derived view に対する lifecycle operation であり、archive regime と混同しない。
3. derived view は `GENERATED` コメントだけでは不十分とし、generator、observed inputs、input policy、action key を持つ derivation manifest を必須化する方向へ移行する。
4. human / LLM declaration は generated view と分離する。fingerprint mismatch 時は orphaned として surface し、生成 view の GC と同じ扱いで自動削除しない。
5. closed evidence record は immutable record とし、close 後に active work 領域へ同名 copy を残す現状は改善対象とする。
6. `obligation-index.edn` を committed Index Plane として持つなら、Work Frontier は fresh check 済み index を読む。常に再計算するなら committed artifact としての意味を再評価する。両方を意味論未整理のまま残さない。
7. `what-now` は Evidence だけでなく、authority conflict / broken manifest、derived artifact freshness、orphan declaration、stale closed record、prunable generated view、Work Frontier head を同じ lifecycle 上で扱う操作面へ拡張する。これは planner ではなく artifact regime の不整合を 1 つ返す interface とする。

### 劇的改善の条件

単に `.llm/data/*.edn` に hash を書くだけでは質的改善として不十分である。劇的改善と呼べる条件は以下:

1. Artifact の型だけでなく lifecycle が定義されていること
2. 依存宣言ではなく、generator が実際に読んだ observed inputs が manifest に刻まれること
3. `.llm/data` と Structural Evidence が同じ derivation primitive を使うこと
4. generated view と human declaration が分離され、GC 可能性が型で決まること
5. Work Frontier が保存 index と再計算 index の二重意味論を持たないこと
6. `what-now` が stale / orphan / prune / frontier head を横断して 1 つの次 action を返すこと

### 実装順序

1. Derivation Manifest schema と hashing primitive を定義する。
2. `.llm/data/design-ir.edn` / `.llm/data/obligation-index.edn` に manifest を入れる。
3. `check-workspace-integrity.sh` が manifest freshness を見る。
4. `derive-work-frontier.sh` は stale index なら frontier を出さず、再生成 command を返す。
5. その後に Structural Evidence packet を derived / declaration / run result / closed record に分解する。

### 実装メモ

後方互換性は持たせない。Structural Evidence の work artifact は `.llm/work/views/`、`.llm/work/declarations/`、`.llm/work/runs/` に物理分離する。assemble 時は change fingerprint が一致する declaration / run result だけを view に付着させ、不一致の declaration は orphan として `what-now` に surface する。clean close は declaration / run result を `.llm/evidence/closed/` の immutable record へ吸収し、work artifact を削除する。これにより「generated view は捨ててよいが human declaration は勝手に捨てない」という regime 差を実装で強制する。

追加実装として、manifest key は `:artifact/manifest` に統一する。`.llm/data/design-ir.edn` / `obligation-index.edn` は embedded manifest、lib catalog は `.llm/data/lib-catalog.manifest.edn` の sidecar manifest とする。Structural Evidence view の manifest は change fingerprint を virtual observed input として刻み、generator、manifest helper、`.llm/data/*` index、QUESTIONS / KNOWLEDGE、maintainer archive または ADR markdown も observed inputs に含める。run result は derived view ではなく transient observation として扱う。

さらに `brick-map` / `workspace-map` / `trace-index` の generated docs + index にも sidecar manifest を導入し、artifact registry に載せる。これらは glob scan を伴うため、manifest primitive は directory digest を first-class observed input として扱い、新規 brick / project / trace file 追加を false fresh にしない。

空 scaffold では `docs/BRICKS.md` 等が存在しないのが正しいため、`what-now` / `check-derived-artifacts` は registry 全体ではなく existing artifacts を freshness 対象にする。生成物が一つでも存在する場合は各 generator の check が対応 sidecar manifest まで同期検証する。

GC 方針: `propose` と writable gate は current fingerprint から外れた generated view を自動 prune する。ただし declaration / run result が存在する task は人間判断・一時観測を含むため自動削除しない。これにより `.llm/work/views/` は生成 view の置き場であり続け、orphan declaration は別 regime として surface される。

### 却下した方向

- 速度改善としての content-addressing: 速くなるかどうかは副作用であり、設計判断の本質ではない。
- 生成物をすべて非保存にする案: shell / briefing / inspectability のために安定パスの current view は有用。問題は保存ではなく provenance と lifecycle の欠如。
- hash だけを追加する案: generator source や observed inputs を含まなければ false fresh が起きる。
- `.llm/work/` を単純削除する GC: generated view は消せるが、human declaration は勝手に捨ててはならない。
- Evidence と `.llm/data` を別々に改善する案: 同じ derive/check/explain/prune 問題を二重実装し、将来また語彙が分裂する。
- Structural Evidence と `.llm/data` を同じ種類の artifact と見なす案: 共通 primitive は共有するが、derived view / declaration / immutable record は regime が異なるため、同じ GC・staleness・preservation 規則を適用してはならない。

## MD-2026-05-014: detached active evidence packet の誤案内
- **状態**: retained-process
- **作成日**: 2026-05-16

## MD-2026-05-011: 作業の全域化と Work Frontier 採用方針

- **作成日**: 2026-05-16
- **吸収先**: [`CLAUDE.md §1.1`, `CLAUDE.md §5.4.1`, `CLAUDE.md §8.0.0`, `.llm/guide/MAINTAINERS_GUIDE.md §5.16`]

### 背景

ユーザー課題は「巨大な仕様やコードベースを一人で見る代わりに、目の前の小さな未完了を淡々と処理すれば全体が完成する構造」だった。初期案として Task Contract Layer / Execution Plane が検討されたが、これは `CLAUDE.md §8.0.0` の「この振り分けに載らない task 概念は存在しない」と衝突し、`§7.4` / `§8.0` の bounded work 規律を EDN task へ再符号化する危険があった。

### 決定

1. Task Contract Layer / Execution Plane は採用しない。`.llm/work/tasks/*.edn` のような task artifact、task schema、begin/close workflow は作らない。
2. 中心概念は task ではなく **obligation** とする。obligation は DESIGN 由来の仕様義務であり、`design-ir.edn` から導出される Index Plane の生成物として扱う。
3. 追加する正式生成物の候補は `.llm/data/obligation-index.edn` とする。これは正本ではなく、`DESIGN.md` / `design-ir.edn` / `trace-index.edn` / `brick-map.edn` / `workspace-map.edn` / QUESTIONS / Evidence の join view である。
4. Work Frontier は保存物ではなく、failing obligation / blocked obligation を依存順に表示する read-only projection とする。planner が task を創作するのではなく、既存 artifact の不整合を typed failure として surface する。
5. obligation state は `complete` / `accounted-blocked` / `red` に分ける。`blocked-by-question` や `manual-verification-required` は完成扱いしない。
6. `:deferred` / `:out-of-scope` / `:manual-verified` / `:non-code` など `:satisfied` 以外の complete state は backing artifact を必須にする。backing がなければ `:unbacked-disposition` として red に戻す。
7. ambiguity heuristic は採用しない。曖昧さは `QUESTIONS.md` の open Q へ接続された `:blocked-by-question` として扱う。自動曖昧判定で task を生成しない。
8. frontier 順序は ranking 知能ではなく、design-ir 由来の relation DAG（例: requirement / use case / acceptance / boundary / test obligation）と severity から導出する。
9. テンプレート repo (`:repo-kind :template`) の空 DESIGN は配布 scaffold として許容する。obligation behavior は synthetic project の template-tests で検証する。派生 project の `:adoption-mode :complete` では未被覆 obligation を ERROR、`:retrofit` / `:partial` では WARN とする。

### Terminal state taxonomy

Complete:
- `:satisfied`: public boundary / test / trace / evidence が要求を満たす
- `:out-of-scope`: DESIGN.md §2.2 スコープ外の backing がある
- `:deferred`: DESIGN.md §10 将来計画、または open Q の backing がある
- `:non-code`: DESIGN 上、コード実装ではなく文書・運用・制約で満たす義務として分類され、backing がある
- `:manual-verified`: DESIGN に検証方法があり、fresh manual/procedural evidence がある

Accounted but not complete:
- `:blocked-by-question`: open QUESTIONS Q への有効 link がある。Q が resolved / wontfix / superseded になれば再評価で red または complete へ戻る
- `:manual-verification-required`: DESIGN に検証方法はあるが fresh evidence がない

Red:
- `:missing-boundary`
- `:missing-test`
- `:missing-trace`
- `:orphan-boundary`
- `:orphan-test`
- `:stale-evidence`
- `:unbacked-disposition`
- `:unresolved-blocker`

### 実装順序

1. 本 entry と正本文書で設計判断を固定する。
2. `gen_design_ir.clj` を拡張し、DESIGN 項目を obligation domain として扱う。section 由来 disposition を既定導出し、例外注記を parse する。
3. `.llm/data/obligation-index.edn` を生成し、complete / accounted-blocked / red state と backing を join する。
4. `check_trace_metadata.clj` / `gen_trace_index.clj` に DESIGN → public boundary / deftest の逆方向被覆を追加する。
5. `derive-work-frontier.sh` を read-only projection として追加する。永続 task は作らない。
6. `session-briefing.sh` で Work Frontier head を Evidence Plane より上に表示する。
7. synthetic project の template-tests で red → complete / accounted-blocked の遷移を検証する。
8. `check-workspace-integrity.sh` に obligation-index drift / backing check を追加する。

### 実装前に先に閉じる摩擦

Work Frontier 実装に入る前に、初期診断で見つかった以下を先に扱う。これらは「小課題へ収束しない」原因そのものなので、obligation frontier の前提として無視しない。

1. maintainer archive の MD ID 重複を `check_archive_staleness.clj` で検出する。
2. `session-briefing.sh` で `git config core.hooksPath` が `.githooks` かを surface する。
3. active Evidence packet が current staged diff と対応しない場合、`evidence.sh what-now` は primary work ではなく housekeeping として扱う。

### 却下した方向

- Task Contract Layer: task artifact と schema が増え、§8.0.0 と衝突し、planner 誤りを人間が信じる危険がある。
- IDEA から実装 task を直接生成する案: IDEA は raw intent であり、DESIGN を経由しない実装 task は分類管理の原則に反する。
- `:deferred` / `:out-of-scope` を backing なしで green 扱いする案: red を黙らせる escape hatch になる。

## MD-2026-05-006: Structural Evidence 操作面への統合
- **状態**: retained-process
- **作成日**: 2026-05-16
- **吸収先**: [`CLAUDE.md §8`, `README.md`, `.llm/guide/STRUCTURAL_EVIDENCE_QUICKSTART.md`, `.llm/guide/MAINTAINERS_GUIDE.md §5.15`, `.llm/scripts/README.md`, `.llm/scripts/session-briefing.sh`, `.llm/scripts/structural_evidence.clj`, `.llm/scripts/check-evidence-boundary.sh`, `.llm/scripts/check-workspace-integrity.sh`]

### 背景

Structural Evidence workflow は `status` / `search` / `gate` / `declare` / `run` / `close` まで整ったが、情報を列挙するだけでは LLM が次の 1 action を即座に選べない。また Review Fatigue Packet は第 5 の正本ではないと文書に書いても、closed record として検索される以上、packet 内で requirement / knowledge / decision を定義し始める drift を機械的に止める必要がある。

### 決定

1. `evidence.sh what-now` を追加し、active packet、staged diff、未宣言 residual、未実行 evidence、stale candidate から次の 1 action を返す操作面とする。
2. `session-briefing.sh` は Evidence Plane で `what-now` を必ず surface する。次セッションの LLM は packet を探すのではなく、まず「今何をすべきか」を読む。
3. closed record の `invalidated-by` を event-based staleness 判定に使い、`status` / `search` / `what-now` で stale candidate を surface する。stale は即無効ではなく、再利用前の再検証 signal とする。
4. `check-evidence-boundary.sh` を追加し、packet 内で新規 requirement / knowledge / decision を定義することを禁止する。packet は Authority / Structure / Index / Verification への generated view に留める。
5. `evidence.sh is-verified` / `why` を追加し、requirement、public boundary、任意 claim の検証 matrix と evidence chain を query できるようにする。
6. `status` は gap 集約 view として、design coverage、trace completeness、Malli contract、open QUESTIONS、関連 KNOWLEDGE を同じ画面に出す。
7. gate は matching clean close record だけで pass しない。record の evidence が `invalidated-by` により stale candidate と判定される場合は gate を止める。
8. 古い closed record には `evidence.sh backfill-invalidated-by` で `invalidated-by` と推定 `closed-git-rev` を後発充填する。
9. `is-verified` / `why` は、term と直接関係しない passing evidence を verification evidence として数えない。

### 却下・保留した方向

- query API を多数追加する案: LLM は command を扱えるが、操作面が散ると「次の一手」が曖昧になるため、当面は `what-now` / `is-verified` / `why` に絞る。
- packet を正本化する案: 検索可能性は必要だが、正本性は Authority Plane に残す。
- performance / 待ち時間の議論で evidence model を縮退させる案: 性能改善は別論点として扱い、今回の設計判断からは切り離す。

## MD-2026-05-005: Structural Evidence の統合評価 anchor
- **状態**: retained-process
- **作成日**: 2026-05-16

7. LLM primary user という anchor から見ると、正しい方向は「削って 0 command に戻す」ではなく、「LLM が構造化情報を扱える前提で、Evidence を workflow の自然な背骨にし、既存 plane の力をもっと引き出す」ことである。

今後 Structural Evidence 周辺の提案を評価する時は、以下を問う。

1. それは LLM が得意な structured I/O、cross-reference、query 駆動を活かすか。
2. それは LLM が苦手な stale 判別、暗黙 context 探索、session 間記憶、次アクション把握を減らすか。
3. それは Authority / Structure / Index / Verification の既存 plane を強くするか、それとも Evidence Plane に新しい正本性を増やすだけか。
4. packet が requirement / knowledge / decision を定義する方向に drift していないか。
5. 人間向けの単純化を、LLM 向けの生産性向上と取り違えていないか。

### 却下・保留した方向

- `0 new commands` / commit message footer を主 ledger にする案: LLM の structured data 処理能力を活かせず、検索性、freshness、cross-reference、evidence tier を弱めるため不採用。
- command 数や packet field 数を主理由に削る案: LLM 主利用者の前提では弱い批判であり、具体的な疲労源に分解してから判断する。
- calibration profile / system-health / pattern synthesis の即時実装: 概念価値はあるが、十分な closed record 蓄積前は誤 signal になりやすいため保留。

## MD-2026-05-001: Brick/project/workspace intent maps
- **状態**: retained-process
- **作成日**: 2026-05-13
- **吸収先**: [`.llm/guide/POLYLITH_GUIDE.md §1.1`, `.llm/guide/POLYLITH_GUIDE.md §1.2`, `.llm/guide/POLYLITH_GUIDE.md §1.3`, `.llm/guide/POLYLITH_GUIDE.md §1.4`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.3`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.5.1`, `.llm/guide/BOOTSTRAP_GUIDE.md §2.5.2`, `.llm/guide/MAINTAINERS_GUIDE.md §5.14`, `CLAUDE.md §8.0`, `.llm/scripts/gen_brick_map.clj`, `.llm/scripts/gen_workspace_map.clj`, `.llm/scripts/check-brick-map.sh`, `.llm/scripts/check-workspace-map.sh`, `.llm/scripts/ensure-brick-map.sh`, `.llm/scripts/ensure-workspace-map.sh`, `.llm/scripts/propose-brick-edn.sh`, `.llm/scripts/propose-project-edn.sh`, `.llm/template-only/tests/check-map-scenarios.sh`]
- **保持理由**: `brick.edn` / generated map の位置づけは、正本の二重管理と機械化の境界を誤ると再検討が起きやすいため、判断過程を process narrative として残す

### 背景

Polylith brick が増えると、LLM と人間は「どの機能がどの brick にあるか」「新規実装すべきか、既存 capability を使うべきか」「base と component の責務を混同していないか」を毎回再発見することになる。

README や手書き Markdown に機能分担を書くだけでは drift し、テンプレートの疲労最小化・機械化・真実の一箇所化に弱い。一方で、コードや Polylith が既に正本として持つ情報を EDN に重複管理すると、別の drift を生む。

### 決定

`brick.edn` はコードの代替正本ではなく、コードだけから安全に復元できない brick の設計意図を持つ。

- component の capability ownership
- base の entrypoint と利用 capability
- `:brick/not-for` による誤配置防止
- DESIGN 要求 ID との対応
- 人間/LLM が既存機能を探索するための要約

公開 API と Malli 契約の正本は `interface.clj`、実装事実の正本は `core.clj` / `system.clj`、依存の正本は brick の `deps.edn`、Polylith 構造の正本は `workspace.edn` と実ディレクトリ構造に置く。

`docs/BRICKS.md` と `.llm/data/brick-map.edn` は正本ではなく生成物とする。前者は人間が読むビュー、後者は LLM / script が検索する index である。直接編集は禁止し、drift は `check-workspace-integrity.sh` 経由で検出する。

### 実装順序

新規 brick では、実装より先に `brick.edn` を作る。

1. DESIGN の要求を確認する
2. 既存 `docs/BRICKS.md` / `.llm/data/brick-map.edn` で重複 capability を探す
3. 新規 brick が必要な場合、`brick.edn` で capability ownership / entrypoint / not-for / requirements を宣言する
4. `interface.clj` の公開 API と `m/=>` 契約を設計する
5. `core.clj` / `system.clj` を実装する
6. `docs/BRICKS.md` / `.llm/data/brick-map.edn` を再生成する
7. integrity check で drift と境界違反を検出する

### 既存 repo への導入

既存 repo では `brick.edn` 欠落を単に ERROR にしない。まず `propose-brick-edn.sh` で案を表示し、必要なら `ensure-brick-map.sh` で skeleton と下流生成物を作る。

自動推測できるのは `:brick/name`、`:brick/type`、公開 API 候補までである。`:brick/purpose`、`:brick/provides`、`:brick/not-for`、`:brick/requirements` は設計意図なので TODO として残し、人間/LLM が DESIGN と実装を見て確定する。

`retrofit` / `partial` では TODO を WARN、`complete` では ERROR として扱う。

### 要求 ID 対応の検査順序

ID 対応は順序を誤ると、未実装の将来要求を不必要に block する。

1. `brick.edn` が参照する ID が `DESIGN.md` に存在しない場合は ERROR
2. `DESIGN.md` 内で同じ ID 定義が重複している場合は ERROR。ID 自体が壊れている状態では、未参照 / 参照済みの判定が不安定になる。文中参照、範囲表記、fenced code block 内の例示は定義として数えない
3. `DESIGN.md` の ID がどの brick にも参照されていない場合は WARN
4. 未割当要求を実装対象にする時は、先に capability / entrypoint を決めて `brick.edn` に ID を記録する

### 公開関数名

関数名だけで混乱する状態は重複実装の原因になる。ただし、同種の操作を別 brick に分ける場合、`invoice/create` と `customer/create` のように公開関数名を揃えることは自然である。

禁止すべきなのは関数名の重複そのものではなく、capability ownership が不明な重複である。許容条件は、namespace alias と関数名を合わせて意味が読め、`:brick/provides` が `:invoice/create` / `:customer/create` のように一意であること。

### `:brick/group` の扱い

類似機能の brick を俯瞰するために `:brick/group` を導入する案は有用だが、group を Polylith の構造単位として扱うと、component / base / project と `poly check` が担う境界に別軸の正本を増やしてしまう。

判断: `:brick/group` を導入する場合、その役割は検索・俯瞰・再分割 smell の発見に限定する。依存境界、capability ownership、project inclusion、テスト範囲、deploy 単位を group から導出しない。構造判断の正本は引き続き component / base / project、`interface.clj`、`workspace.edn`、`deps.edn`、`project.edn`、`poly check` に置く。

実装判断: `:brick/group` は任意の単数 keyword のみ許容する。set / vector による複数 group は採用しない。複数 group を許すと、brick の主責務が曖昧になり、generated Brick Map 上で同じ brick が複数箇所に現れ、再分割 smell の判断主体が曖昧になる。また group が検索補助ではなく tag や構造制約として使われ始めるリスクが高い。複数の補助軸が必要になった場合は、`:brick/group` の多値化ではなく、別 metadata として改めて採否を判断する。

帰結: group に対する機械検査は、形式検査、generated Brick Map の index、同一 group 内の近接 capability warning などの advisory に留める。group をまたぐ依存を ERROR にする、group から project includes を生成する、group 単位でテスト範囲を決める、といった使い方は採用しない。

実装後の補足: `docs/BRICKS.md` は group-first view を持ち、`.llm/data/brick-map.edn` は `:groups` index を持つ。これは LLM と人間が新規 brick 作成前に近傍 brick を見るための入口である。`CLAUDE.md §8.0` と `POLYLITH_GUIDE.md §1.2` から group 近傍確認へ接続し、LLM が新規 brick を提案する時は候補 group、同一 group の既存 brick、既存 brick に入れない理由を説明する。group mismatch、同一 group 内の近接 operation、base の多 group 利用は advisory warning として出すが、構造制約ではないため完了条件の ERROR にはしない。

### Project / workspace への拡張方針

同じ課題は project と workspace にもあるが、同じ解き方にしない。

`project` は capability を所有しない。導入するなら `projects/<name>/project.edn` とし、deploy / build / entrypoint inclusion の意図だけを持つ。classpath や依存の正本は `projects/<name>/deps.edn` に残す。

`:project/type` は検査ポリシーであり、`:app` / `:library` の 2 値に限定する。service / worker / CLI / batch / lambda などは実行形態であって検査ポリシーではないため、必要な場合だけ任意の `:project/runtime` に置く。3 軸以上の分類は、対応する機械検査が生まれるまで追加しない。

workspace は既に `workspace.edn`、`.llm/repo-context.edn`、`deps.edn` が正本を分担しているため、手書きの追加正本を増やさない。まずは既存正本群から `docs/WORKSPACE.md` / `.llm/data/workspace-map.edn` を生成する方向に留める。

### `poly` command との責務分担

Polylith が既に知っている構造事実は、テンプレート側で再実装しない。`poly check` / `poly test` / `poly info` が扱う領域は、まず Polylith CLI に委譲する。

`poly` に任せる領域:

- workspace 内の project / base / component 認識
- brick 間依存関係
- component / base の境界違反
- project ごとの構成
- 変更検知と影響範囲テスト
- `workspace.edn` の Polylith 的妥当性

テンプレート側が EDN で担う領域:

- capability ownership
- `:brick/not-for`
- DESIGN 要求 ID との対応
- base entrypoint と component capability の意味的対応
- deploy intent
- TODO / migration state
- generated docs / index の drift
- LLM が探索しやすい capability index

`poly` 出力の扱いは慎重にする。machine-readable output がある場合は workspace-map 生成の入力として使う。人間向け表示しかない場合、文字列 parse は壊れやすいため、`poly check` の pass/fail に委譲し、テンプレート側は file / EDN / deps の軽量整合に留める。

判断基準:

```text
poly が machine-readable に出せる構造事実
  → poly 出力を使う

poly が人間向け表示しか出さない構造事実
  → parse の価値と壊れやすさを比較し、原則として poly check に委譲する

poly が知らない設計意図
  → brick.edn / project.edn / generated map で管理する
```

### 却下した方向

- README / 手書き Markdown を機能分担の正本にする案: drift しやすく、機械検査に弱い
- `brick.edn` を実装事実の正本にする案: `interface.clj` / `deps.edn` / Polylith 構造との二重管理になる
- 既存 repo 導入時に欠落 `brick.edn` を即 ERROR にする案: retrofit の初期導入コストが高く、棚卸しが進まない
- 複数 brick の同名公開関数を全面禁止する案: `invoice/create` / `customer/create` のような自然な interface pattern を壊す
- `poly info` の人間向け出力を無条件に parse して workspace-map の正本相当にする案: CLI 表示形式に依存して壊れやすく、Polylith が提供する検査責務をテンプレート側へ重複実装することになる
- schema EDN を直ちに厳密 validator として外部化する案: 現段階では checker と schema の二重管理を増やすため保留。まず `gen_*_map.clj` と template E2E で運用実態を固める
- 自動修復で capability / requirement 対応を推測確定する案: 誤った設計意図を正本化する危険があるため不採用。機械は skeleton と TODO を作り、人間/LLM が DESIGN と実装に基づいて確定する

## MD-2026-05-013: Specification trace metadata boundaries
- **状態**: retained-process
- **作成日**: 2026-05-14
- **吸収先**: [`CLAUDE.md §4.1`, `CLAUDE.md §5.4.1`, `.llm/guide/CODING_GUIDE.md §2.1.1`, `.llm/guide/CODING_GUIDE.md §13.4.1`, `.llm/guide/POLYLITH_GUIDE.md §1.1`, `.llm/guide/SPEC_GUIDE.md §8.1`, `.llm/scripts/check_trace_metadata.clj`, `.llm/template-only/tests/check-trace-metadata-scenarios.sh`]
- **保持理由**: 仕様 trace をコード全体へ広げるか、安定境界へ限定するかは疲労最小化と refactor 容易性に直結するため、判断過程を残す

### 背景

DESIGN / design-ir / Clojure コード / テストコードの対応を機械検査できれば、LLM が仕様と実装をずらした時の検出が早くなる。一方で、実装内部の関数すべてに requirement ID や test obligation ID を付けると、内部 refactor のたびに trace 更新が必要になり、仕様駆動開発のための metadata が逆に保守疲労を増やす。

### 決定

実装コード側の trace metadata は stable public boundary に限定する。

- component では `interface.clj` の公開 `defn`
- base では外部 entrypoint に近い公開 boundary `defn`
- `core.clj`、private helper、adapter 内部には付けない
- test obligation は実装関数ではなく `deftest` の `:trace/test-obligations` にだけ置く
- `brick.edn :brick/requirements` は brick 全体の粗い ownership、Clojure metadata は公開関数単位の対応として使い分ける

### 機械化

`.llm/scripts/check-trace-metadata.sh` は `.llm/data/design-ir.edn` を正本として Clojure top-level form を検査する。

- 未知 requirement / use case / test obligation ID は ERROR
- 空 ID、空 vector、重複 ID は ERROR
- internal implementation への trace metadata は ERROR
- 実装関数への `:trace/test-obligations` は ERROR
- `deftest` の `:trace/requirements` / `:trace/use-cases` と test obligation の related IDs 不整合は、`:adoption-mode :complete` では ERROR、`:retrofit` / `:partial` では WARN
- design-ir の test obligation がどの `deftest` からも参照されない場合も、`:adoption-mode :complete` では ERROR、`:retrofit` / `:partial` では WARN

未対応 test obligation は既存 repo 導入時の移行余地を残すため、`:retrofit` / `:partial` では WARN に留める。strict 準拠完了後の `:complete` では ERROR とし、仕様義務がテスト trace から落ちた状態を完了条件で止める。

`.llm/scripts/gen-trace-index.sh` は `docs/TRACE.md` と `.llm/data/trace-index.edn` を生成する。これは検査ではなく活用層であり、requirement / use case / test obligation から public boundary と `deftest` へ辿る impact map を提供する。LLM は DESIGN 更新時に trace-index を読み、修正対象を先に列挙してから実装する。

### 却下した方向

- すべての関数に trace metadata を付ける案: refactor に弱く、内部実装の設計自由度を下げる
- implementation 関数へ `:trace/test-obligations` を付ける案: 「何を実装するか」と「何を検証したか」が混ざり、テスト義務の未充足を隠す
- コメントで ID を書く案: 構造検査できず、命名・文体変更で drift しやすい
