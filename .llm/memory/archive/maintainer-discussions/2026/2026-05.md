## MD-2026-05-002: Issue #10 観察報告（エラー教育性 / LLM フレンドリー度）への対応方針

- **議論対象**: STACK_GUIDE.md に「エラー教育性 / LLM 自走可能性」を選定基準として明示すべきという提案、polyguard hook 出力の自走支援強化、Stack 層 (aero / Integrant / Biff 経由 HTMX) でエラーメッセージの教育性にばらつきがあるという観察
- **判定基準** (MD-2026-05-001 と同じ 4 条件 AND):
  1. Clojure / Polylith / REPL 固有、または LLM 協働一般の現象
  2. 複数プロジェクトで再発する性質
  3. テンプレが制御する文書・スクリプトで対処可能
  4. CLAUDE.md §1 疲労最小化に反しない

### 提案項目別判定

- **評価軸の追加 (STACK_GUIDE)**: 採用。判定基準すべて満たす。machine-readable schema は触らず narrative レベルで明文化
- **polyguard hook の出力改善**: 採用。判定基準すべて満たす。hook ごとに教育目的の異なる例を分けて配置
- **`.llm/scripts/check-*.sh` 群の継続**: Issue が肯定観察として「既に十分機能」と明記しているため、規律的な変更は不要
- **具体 lib (aero / Integrant / Biff) の採否変更**: 不採用。単一観察を根拠とする採否変更は CLAUDE.md §1.2.5「承認は粗い単位で」と §1.2.4「早期破棄」に反する。観察は narrative SSOT として記録するに留める

### 結論（採用された規律）

- **STACK_GUIDE.md §3.0**: 「選定時の補助観点: エラー教育性 / LLM 自走可能性」段落を追記。新規 schema フィールド・タグは導入しない（generator 巻き込み回避）
- **STACK_GUIDE.md §3.1 / §3.2 / §3.22**: Integrant / aero / Biff の各 `;; lib-catalog` block 直前に `;;` コメントで Issue #10 観察を「由来: Issue #10」付きで記録。採否は `:recommended` のまま不変
- **`.clj-kondo/polyguard/hooks.clj`**: `check-broad-catch` メッセージに具体クラス例 (java.io.IOException / java.sql.SQLException / clojure.lang.ExceptionInfo) を追記、`check-empty-catch` メッセージに握り潰し回避の最小パターン例 (cause は ex-info 第 3 引数で渡す形) を追記

### 含意の記録

「mandatory stack に UI ベース技術 (HTMX 等) を含めない既存方針と整合する観察として記録する」。本テンプレートが UI 系技術を必須技術基盤に組み込まなかった既存判断について、Biff 経由 HTMX の診断特性に関する派生プロジェクト観察が補助的証拠を提供している。「実証された」「妥当性を逆向きに証明」のような勝利宣言的表現は避け、単一観察を既存判断の補助的証拠として位置づけ、将来の再評価余地を残す。

### 却下した代替案

- **`:error-opacity` 等の新タグ・新フィールド追加**: `.llm/scripts/gen_lib_catalog.clj` の `tag-values` / `entry-schema` が列挙型固定であり、追加は generator 変更を伴う。観点の明文化は narrative レベルで十分機能するため、機械化基盤への踏み込みを回避
- **該当 lib の採否降格** (`:recommended` → `:conditional` 等): 単一観察では根拠不足。§1.2.5「粗い承認単位」と §1.2.4「早期破棄」に反する不可逆方向への先走り。観察を `;;` コメントで可逆かつ累積可能な形で残し、独立 2 件以上の同方向観察が蓄積した時点でテンプレート保守規則として再評価
- **`.llm/memory/adr/` への ADR 発行**: scope 違反。`.llm/memory/adr/` は派生プロジェクトの ADR 発行領域（配布時は空、派生側で 0001 から採番）であり、テンプレ自身の決定を置くと派生プロジェクトの ADR 番号空間を汚染する (`.llm/memory/adr/README.md:68` および MAINTAINERS_GUIDE.md §3.4)。MD-2026-05-001 と同じく本議論アーカイブで保全
- **派生プロジェクト側に評価フレームワーク導入を促す変更**: STACK_GUIDE §1.2「主体ごとの扱い」既定により、派生側運用は派生側 ADR の責務。本 repo 側で派生に対応を強制する変更は行わない

## MD-2026-05-003: テンプレート保守 vs 派生プロジェクト保守の混同を構造的に防ぐ

- **日付**: 2026-05-13
- **発端**: MD-2026-05-001 (Issue #11 対応) と MD-2026-05-002 (Issue #10 対応) で **短期間に 2 回連続** で `.llm/memory/adr/` をテンプレ自身の決定の記録先として誤って使いそうになった。ユーザ指摘で archive へ誘導されたが、規律レベル防御（COLLABORATION_GUIDE §7.8 構造引きずられバイアス）だけでは抑えられないことが実証された。ユーザ再定義: **「本テンプレートそのもののメンテナンスと派生プロジェクトのメンテナンスが混同される」が根本問題**
- **議論対象**: ADR 固有問題ではなく一般化された「テンプレ保守 mode vs 派生プロジェクト mode」の構造的防止策

### 根本原因（3 層）

1. `MAINTAINERS_GUIDE.md` 自身がテンプレ自身の決定を ADR へ誘導していた（§5.3 / §7.1 / §7.2 / §5.x の "ADR を発行" 言及）。LLM は指示通り動いた
2. `.llm/memory/adr/README.md` に「派生プロジェクト専用」の明示文言がなかった
3. 機械化された境界検査が存在しなかった（規約と文書のみが防御線）

### 設計原則からの導出

- **CLAUDE.md §1.2.1 機械化**: 規律ではなくツールで強制する → manifest を SSOT とし script で enforce
- **SSOT 違反を作らない**: 所有権情報は manifest 1 ファイルのみが保持。banner や規約に enumerate しない（drift 防止）
- **§1.2.4 早期破棄 / §1.2 疲労最小化**: 実証された失敗箇所（`.llm/memory/adr/`）に集中。仮想失敗への banner ばら撒きをしない
- **§1.2.5 失敗早期検知**: bootstrap 中途状態を session-briefing 起動時に hard error
- **本テンプレの SSOT パターン**: `gen-lib-catalog.clj` が STACK_GUIDE から派生情報を生成する設計と同型

### 採用した構成（5 つの具体物）

1. **`.llm/repo-context.edn`**（新規、SSOT）: 機械可読 manifest。`:repo-kind`、`:project-owned`、`:template-owned`、`:section-scoped` を 1 ファイルに集約
2. **`.llm/scripts/session-briefing.sh`**（編集）: manifest を読み TEMPLATE MAINTENANCE / PROJECT モード判定。conflict 最優先（`:template` + bootstrap 完了痕跡 → hard error）。TEMPLATE モード時は派生向け section（open Q §2+ / 最新 ADR / DESIGN.md・KNOWLEDGE.md §1+ 参照）を suppress
3. **`.llm/scripts/check-mode-scope.sh`**（新規）: manifest を読み、所有権違反を機械検出。TEMPLATE モード時に `:project-owned` 配下のテンプレ保守マーカー混入、section-scoped 跨ぎ違反を WARN。`check-workspace-integrity.sh` から呼び出し
4. **`.llm/guide/MAINTAINERS_GUIDE.md`**（編集）: 全 ADR 言及を audit し「ADR または議論アーカイブ」→「議論アーカイブ」、独立 "ADR を発行" → "議論アーカイブに記録" に統一。§7.2.1 モード境界節を新設（scope は enumerate せず manifest を指す）

### 却下した代替案

- **bare marker `.llm/TEMPLATE_REPO`**: identity 検出はできるが path 分類 SSOT として弱い。manifest 採用で不要に
- **全空間に banner をばら撒く（KNOWLEDGE / QUESTIONS / DESIGN / components / bases / projects 各 README）**: SSOT 違反の重複源、drift リスク。実証された失敗は ADR のみで他箇所は「念のため」防御に該当（§1.2 疲労最小化に反する）
- **COLLABORATION_GUIDE §7.8 補強**: 既存 §7.8 は構造引きずられバイアス一般を扱い本ケースもその一例。機械化（manifest + check）で取り除く方が原則整合（§1.2.1）。規律重複は §1.2 疲労最小化に反する
- **bootstrap で manifest を削除**: SSOT が下流モードで破綻する。`:project` への transform に変更（codex v6→v7 指摘）
- **enumerate 形式の banner / §7.X モード境界節**: scope 情報を文書に複製すると drift する。manifest を指す pointer 形式に統一（codex v8 → v8.1 指摘）
- **派生プロジェクト用 `.llm/memory/adr/` への ADR 発行**（MD-2026-05-001 / 002 と同じ scope 違反）
- **pre-commit hook で commit を block**: WARN 運用との一貫性を取る。block 強制は他検査群の方針と整合しない

### 設計上のトレードオフ

- **manifest を SSOT にする初期投資**: bare marker より作成・運用コストはやや高いが、層 0〜4 が同一情報源を参照することで drift を構造的に排除。本テンプレの `gen-lib-catalog.clj` パターンと同型
- **section 粒度所有権**: ファイル単位の「DOWNSTREAM-ONLY」は誤り（KNOWLEDGE / QUESTIONS / DESIGN は二重所有）。`:section-scoped` で template / project 区間を表現
- **conflict 最優先の判定順序**: 単純な「manifest が `:template` → template mode」では bootstrap 中途状態を見落とす。conflict を分岐 1 に置くことで `§1.2.5` 失敗早期検知に整合
- **`components/*/**` 再帰 glob**: `components/*/` は brick ディレクトリのみマッチで中身を取り損ねる。`*/**` 再帰指定が必要（codex v7→v7.1 指摘）
- **heuristic 検査の限界**: 完全機械化は意味解析が要る。複合マーカー（`本テンプレート`、`MAINTAINERS_GUIDE` 参照等）で false positive を抑えつつ WARN 運用
- **`.llm/memory/adr/0001-cross-entity-mechanization.md`** が本検査で WARN を出す: テンプレ shipped ADR が `テンプレート保守者` などのマーカーを含んでおり、本検査の正しい signal。本タスク scope 外の pre-existing 違反として記録、retrospective cleanup（archive への移動）は別タスクで扱う
