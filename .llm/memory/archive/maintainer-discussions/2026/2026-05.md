## MD-2026-05-002: Issue #10 観察報告（エラー教育性 / LLM フレンドリー度）への対応方針

- **日付**: 2026-05-13
- **発端**: GitHub Issue #10 (fanannan/clojure-polylith-llm-starter)。派生プロジェクト product-osint 等から提出されたテンプレート使用体験の観察報告。改善要望ではなく観察共有と明記
- **議論対象**: STACK_GUIDE.md に「エラー教育性 / LLM 自走可能性」を選定基準として明示すべきという提案、polyguard hook 出力の自走支援強化、Stack 層 (aero / Integrant / Biff 経由 HTMX) でエラーメッセージの教育性にばらつきがあるという観察
- **判定基準** (MD-2026-05-001 と同じ 4 条件 AND):
  1. Clojure / Polylith / REPL 固有、または LLM 協働一般の現象
  2. 複数プロジェクトで再発する性質
  3. テンプレが制御する文書・スクリプトで対処可能
  4. CLAUDE.md §1 疲労最小化に反しない

### 提案項目別判定

- **評価軸の追加 (STACK_GUIDE)**: 採用。判定基準すべて満たす。machine-readable schema は触らず narrative レベルで明文化
- **polyguard hook の出力改善**: 採用。判定基準すべて満たす。hook ごとに教育目的の異なる例を分けて配置
- **`.llm/scripts/check-*.sh` 群の継続**: Issue が肯定観察として「既に十分機能」と明記しているため、規律的な変更は不要
- **具体 lib (aero / Integrant / Biff) の採否変更**: 不採用。単一観察を根拠とする採否変更は CLAUDE.md §1.2.5「承認は粗い単位で」と §1.2.4「早期破棄」に反する。観察は narrative SSOT として記録するに留める

### 結論（採用された規律）

- **STACK_GUIDE.md §3.0**: 「選定時の補助観点: エラー教育性 / LLM 自走可能性」段落を追記。新規 schema フィールド・タグは導入しない（generator 巻き込み回避）
- **STACK_GUIDE.md §3.1 / §3.2 / §3.22**: Integrant / aero / Biff の各 `;; lib-catalog` block 直前に `;;` コメントで Issue #10 観察を「由来: Issue #10」付きで記録。採否は `:recommended` のまま不変
- **`.clj-kondo/polyguard/hooks.clj`**: `check-broad-catch` メッセージに具体クラス例 (java.io.IOException / java.sql.SQLException / clojure.lang.ExceptionInfo) を追記、`check-empty-catch` メッセージに握り潰し回避の最小パターン例 (cause は ex-info 第 3 引数で渡す形) を追記

### 含意の記録

「mandatory stack に UI ベース技術 (HTMX 等) を含めない既存方針と整合する観察として記録する」。本テンプレートが UI 系技術を必須技術基盤に組み込まなかった既存判断について、Biff 経由 HTMX の診断特性に関する派生プロジェクト観察が補助的証拠を提供している。「実証された」「妥当性を逆向きに証明」のような勝利宣言的表現は避け、単一観察を既存判断の補助的証拠として位置づけ、将来の再評価余地を残す。

### 却下した代替案

- **`:error-opacity` 等の新タグ・新フィールド追加**: `.llm/scripts/gen_lib_catalog.clj` の `tag-values` / `entry-schema` が列挙型固定であり、追加は generator 変更を伴う。観点の明文化は narrative レベルで十分機能するため、機械化基盤への踏み込みを回避
- **該当 lib の採否降格** (`:recommended` → `:conditional` 等): 単一観察では根拠不足。§1.2.5「粗い承認単位」と §1.2.4「早期破棄」に反する不可逆方向への先走り。観察を `;;` コメントで可逆かつ累積可能な形で残し、独立 2 件以上の同方向観察が蓄積した時点でテンプレート保守規則として再評価
- **`.llm/memory/adr/` への ADR 発行**: scope 違反。`.llm/memory/adr/` は派生プロジェクトの ADR 発行領域（配布時は空、派生側で 0001 から採番）であり、テンプレ自身の決定を置くと派生プロジェクトの ADR 番号空間を汚染する (`.llm/memory/adr/README.md:68` および MAINTAINERS_GUIDE.md §3.4)。MD-2026-05-001 と同じく本議論アーカイブで保全
- **派生プロジェクト側に評価フレームワーク導入を促す変更**: STACK_GUIDE §1.2「主体ごとの扱い」既定により、派生側運用は派生側 ADR の責務。本 repo 側で派生に対応を強制する変更は行わない

### 設計上のトレードオフ

- **machine-readable judgment は意図的に未更新**: `;;` コメントは narrative SSOT (人間可読の判断根拠記録) の更新であり、`:judgment` / `:status` / `:tags` は触らない。観察累積が将来の machine-readable 更新の根拠データとなる二段階運用。`gen-lib-catalog` 空差分検証がこの設計意図の機械的保証となる
- **採否降格を見送る規律**: 派生プロジェクト 1 件の観察で `:recommended` を下げると、根拠不足のまま不可逆方向に動くリスクがある。可逆な `;;` コメント記録と Observation log の累積で受け止め、複数観察を待つ
- **観察カウントの曖昧性**: 「独立 2 件以上」の判定は人間の判断に依存する (同一プロジェクトからの繰り返し観察は 1 件として扱う、別プロジェクトからの観察は独立とみなす等)。機械的厳密性は持たせず、運用判断とする

- **観察累積に基づく採否再評価の閾値**: 「独立 2 件以上」は暫定。実運用で観察がどう累積するかを見て、必要なら閾値を調整。Observation log の蓄積パターンが見えた段階で QUESTIONS への起票を検討
- **machine-readable 化のタイミング**: 観察累積が一定数を超えた時点で `gen_lib_catalog.clj` の schema 拡張 (新タグ追加) を検討する余地あり。現時点では narrative レベルで十分機能するため見送り
