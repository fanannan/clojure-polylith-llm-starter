### 2026-04: 初版の設計判断

#### 通常版テンプレートと Polylith 版の統合
- **背景**: 当初は小規模プロジェクト向け「通常版」と中規模以上向け「Polylith 版」を並置していた
- **判断**: Polylith 版に統一、通常版は廃止
- **根拠**:
  - 後からの Polylith 移行コストは初期採用より数倍大きい（非対称性）
  - 2 テンプレート併存の保守負荷が実用上無視できない
  - Polylith の最小構成（components 1 + base 1 + project 1）と通常構成の `src/` + `test/` の認知負荷差は小さい
- **却下案**: 通常版を残し、サイズ判断で選ばせる → 原則 9 に照らして判定軸が不十分

#### 第一原理「疲労最小化」の文書最上位配置
- **背景**: 初期案では個別規約（Malli、clj-kondo、Polylith、REPL 等）が並列に列挙され、第一原理が文書に書かれていなかった
- **判断**: CLAUDE.md §1 として「疲労最小化原則」を明示し、三基底原則（全域性・不変性・副作用隔離）と四実装戦略（機械化・ループ短縮・小単位・早期破棄）を配置。各章は「§1.X.Y の実装」として自らを位置づける
- **根拠**: 原則 1（原理を最上位に）、原則 10（議論を残す）
- **却下案**: 原理を省いて個別規約だけで済ます → LLM が未知の状況で原則を外した形式適用に陥るリスク

#### 30 分ルールの具体化（自己停止プロトコル）
- **背景**: 当初は「30 分で止まれ」とだけ書いていたが、LLM に時間感覚はないため機能しない
- **判断**: CLAUDE.md §7 として、ターン数・試行回数ベースの自己停止プロトコルに変換
- **根拠**: 原則 2（規約だけでは守られない）
- **却下案**: 文書で「LLM は 30 分を意識せよ」と強く書く → 時間感覚の欠如は意識では補えない

#### 章順の再整理
- **背景**: 初期案は「Polylith 規約」が §2 にあり、技術スタックより前に置かれていた
- **判断**: 章順を「自動検証不能・影響甚大」を前方に並べ替え。禁止事項 → 技術スタック → 基底原則の実装 → 機械化規約 → poly コマンド → 自己停止プロトコル → 作業プロトコル → REPL → テスト → トラッカー の順
- **根拠**: 原則 8（自動検出されないものを前方に）
- **却下案**: Polylith 先行で構造制約を最初に示す → Polylith 違反は poly check で検出されるため、相対的に後方で良い

#### 配布物の 4 値判断の採用
- **背景**: 初期案では components/user/ などのサンプルを全部配布していた
- **判断**: 「即有効 / コメントアウト / 不配布 / 完全排除」の 4 値判断を採用。必須は即有効、用途依存はコメントアウト、ドメイン仮定は不配布、却下ライブラリは完全排除
- **根拠**: 原則 3（二値判断を避ける）、原則 5（LLM は削除が苦手）、原則 6（サンプルとテンプレートの分離）
- **却下案**:
  - 全サンプル配布 → 架空ドメインが LLM に混入
  - 全サンプル削除 → 標準形の可視性が失われる

#### `dev/user.clj` の配布形態
- **背景**: Web サービス特化か、REPL 汎用か判断が揺れた
- **判断**: 機能単位でコメントアウトして配布。`tn/set-refresh-dirs` は無条件で有効。Malli instrumentation / Integrant ライフサイクル / Portal はセクションごとに独立してコメントアウト。config 関数は placeholder
- **根拠**: 原則 4（「汎用」は相対概念）、原則 3（4 値判断）
- **却下案**:
  - 全部有効で配布 → Integrant 未採用時に動かない
  - 全く配布しない → Malli + Integrant の起動順序を LLM が誤りやすい

#### 3 文書体制（CLAUDE.md / CODING_GUIDE.md / POLYLITH_GUIDE.md）
- **背景**: 単一ドキュメントか分離かの判断
- **判断**: 3 文書体制。CLAUDE.md は常時制約、CODING_GUIDE.md は Clojure 書き方詳細、POLYLITH_GUIDE.md は Polylith 運用詳細
- **根拠**: 配置基準を明示化することで追記時の判断コストを下げる
- **却下案**:
  - 単一ドキュメント → CLAUDE.md が肥大化、読解コストが増加
  - 完全分離（CLAUDE.md を極小化） → 常時制約の参照先が遠のき、規約違反の事前回避が難しくなる

#### 本文書（MAINTAINERS_GUIDE.md）の新設

#### コメントアウト有効化プロトコルの確立と原則 11 の追加

- **却下案**:
  - プロセスを書き足さない → LLM が自力で手順を捏造して中間状態を作る事故が予見される
  - CLAUDE.md に書かず MAINTAINERS_GUIDE.md のみに書く → 有効化は日常作業で発生するため常時参照できる位置が必要

#### ADR 説明の追加、CLAUDE.md §0 の極小化、README.md 新設
- **背景**: 3 つの初見者視点の指摘を受けて対応：
  1. ADR という業界用語を暗黙前提にしていた（プロジェクトで初めて本テンプレートに触れる人が `.llm/memory/adr/README.md` を開いた時、定義が不在）
  2. CLAUDE.md §0 に残っていた「目的/配布形態/ランタイム/トップ名前空間」が原則 13 違反（仕様情報が規約文書に混入していた遡及適用の見落とし）
  3. リポジトリを初めて見る人間（LLM ではなく人間）の入口となる README.md が不在
- **判断**:
  - `.llm/memory/adr/README.md` の冒頭に「**ADR とは何か**」セクションを追加（定義、解決する問題、不変性の本質、似て非なるものとの比較）
  - **CLAUDE.md §0 を 5 行程度に極小化**。プロジェクト固有情報は DESIGN.md §8 に新設した「プロジェクト固有情報」節に一元化
  - **README.md をルート直下に新設**（テンプレート配布時の警告付き雛形。プロジェクト初期化完了時に完全書換を前提）
  - `.llm/guide/BOOTSTRAP_GUIDE.md` §3 完了チェックリストと §4 完了後作業に「README.md の書き換え」を追加
  - `.llm/guide/MAINTAINERS_GUIDE.md` §3.1 区分表に README.md を追加、§5.8 に README.md 雛形の保守規則を追加
- **根拠**:
  - 原則 13（§0 の情報を DESIGN.md に委譲し、CLAUDE.md は規約文書に専念）
  - 原則 7（文書の自己整合性 = 業界用語の暗黙前提を避ける）
  - **内部整合性と外部親切性の両立**: これまで内部構造の純度を高めてきたが、初見者の入口（README.md）が不在だった
- **却下案**:
  - ADR を README.md の末尾に短く書く → 初見者が運用ルールの前に定義を知る機会を失う。冒頭が正解
  - CLAUDE.md §0 を維持 → 原則 13 違反（仕様情報が規約文書に混入）
  - README.md を作らない → GitHub 訪問者や初見者が「どこから読むか」を判断できない
  - README.md を DESIGN.md と兼用 → 役割が正反対（内部説明 vs 外部説明）なので同じファイルに置くと混乱
- **副次的発見**:
  - 文書設計には「**内部整合性**」と「**外部親切性**」の 2 方向があり、両者を対として設計する必要がある
  - 業界用語（ADR、Polylith、Integrant 等）を使う時は、その定義が読者に共有されているか確認する規律が必要
  - 原則 13 の遡及適用を前回実施したはずが、CLAUDE.md §0 に仕様情報を残していた不完全さが今回露呈。**遡及適用は 1 回で完結せず、気付きに応じて継続する必要**がある
  - 読者の最初の接触点（README、各ディレクトリの README、冒頭セクション）を原則的に点検する観点を意識する（原則 14 候補として保留。類似事例が積み上がれば原則化を検討）

#### CLAUDE.md の KNOWLEDGE.md 連携強化と 4 種文書の統合案内

#### README.md ブートストラップ手順の役割分担明確化
- **背景**: ユーザより「README.md の開始手順は概論として分かるが、**誰が何をするかが不明確**。人間が LLM への指示をできるだけ少ない回数・低負担で行う観点から、必ず人間が行うことと具体的なプロンプト例を示すべき」との指摘

  - BOOTSTRAP_GUIDE.md は「LLM 側の詳細手順」だが、人間向けの視点がなかった
  - 原則 11（判断とプロセスの対称性）の観点で、「判断（何をする）」は書かれているが「プロセス（誰がどう動くか）」が欠落

    - 🧑 **人間が決めること・行うこと**（意思決定・確認作業）
    - 🤖 **LLM への指示プロンプト**（コピペ可能、`<...>` で埋めるべき箇所を明示）

- **根拠**:
  - **原則 11（判断とプロセスの対称性）**: 意思決定内容だけでなく、誰がどう動くかまで文書化
  - **疲労最小化（§1）**: 人間の指示回数を削減することで、人間側の認知疲労も最小化
  - **原則 5（LLM は削除が苦手）の対称**: 逆に LLM は「指示されたことを実行」が得意なので、具体的プロンプトを提供する設計が有効
- **却下案**:
  - BOOTSTRAP_GUIDE.md を人間向けに書き換える → LLM の詳細手順と人間向け概要が混ざって両方劣化

  - プロンプト例を汎用化（`<...>` なし） → 人間が毎回考える負担が残る
- **副次的発見**:
  - 「**2 視点ある作業は 2 文書で分離する**」のが原則。1 文書に 2 視点を混ぜると両方劣化する
  - README.md は初見者向けの顔だけでなく、**ブートストラップ期間中の人間の作業伴走役**としても機能する
  - プロンプト例を埋め込むことで、文書が**単なる説明書から実行可能なワークフロー**に変わる
  - 疲労最小化原則は LLM 側だけでなく**人間側にも適用される**。人間の指示回数と認知負荷を減らすことは、プロジェクト全体の持続可能性を高める

#### 責務整理による冗長削減
- **背景**: ユーザより「各文書の担当領域と関係を明確化することで冗長を減らし、保守負担を下げられる」との指摘。要素追加を重ねた結果、同一情報が複数文書に分散していた

#### 「整理優先の姿勢」の配置判断と原則化の見送り
- **背景**: 前項の改訂で「新規追加より整理を優先」を**原則 14 または 15 として立てる可能性**を残していた。ユーザより「これは原則として置くべきものか、位置が違う気がする」との問い
- **検証**:
  - 原則 1〜13 はすべて**テンプレート設計の判断基準**（対象レベル）を扱う
  - 「整理優先」は**判断基準群を適用する時の心構え**（メタレベル）であり、階層が違う
  - 原則化すると以下の弊害：原則群の階層的一貫性が崩れる、同種の姿勢論を次々追加したくなり原則の墓場になる、「整理せよ」はトートロジーで判断基準として機能しない、原則 7・12 との実質的重複
- **二つ目の観察（ユーザ指摘）**: 「整理優先」は**文書保守とコード保守の両面で有効**である。同一思想だが領域が違う
  - 文書保守: 冗長削減、責務純化、参照化、一次情報源の明示
  - コード保守: DRY、YAGNI、KISS、既存活用、関数分割、共通化
  - 両面を一つの原則に混ぜると混乱するが、完全に分離すると同一思想である認識が失われる
- **判断**:
  - **原則として立てない**。§4 原則群の階層的純度を守る
  - **領域ごとに分離配置し、相互参照で両面を示す**（案 1）:
    - 文書側: MAINTAINERS_GUIDE.md §9.3「保守作業における姿勢：整理優先（開発・保守共通）」を新設
    - コード側: CODING_GUIDE.md §2.4「整理優先の姿勢（開発・保守共通）」を新設
  - **両節の冒頭で共通認識を明示**: 「同一思想の両面」と明記、もう片方への参照を置く
  - **配置根拠**:
    - CODING_GUIDE.md §2 は三基底原則の詳細展開。その末尾に置くことで**基底原則を実装するための姿勢**として位置づけ。開発時・保守時の両面に適用される性格に合致
    - MAINTAINERS_GUIDE.md §9 は本文書自身の保守を扱う節。整理優先は保守作業の姿勢なので性格が合致
  - **原則 7・12 本文に §9.3 への短い参照を追加**: 「自己整合性は整理を通じて維持される」「遡及適用時は追加より整理の機会を先に点検する」
  - **DRY / KISS / YAGNI の用語を使う**: LLM にとって馴染みのある業界用語で具体性を高める
- **根拠**:
  - 原則 1（原理を文書の最上位に置く）の階層感覚：判断基準と姿勢論は階層が違う
  - 原則 7（自己整合性）：原則群の性格が揃うことが自己整合性の一部
  - 原則 13（分離）：同一思想でも領域が違うなら分離配置する（ただし相互参照で同一性を明示）
  - 実効性の優先：各領域の読み手が自領域の具体例を持つほうが行動に直結する
- **却下案**:
  - **原則 14 として採用** → 階層が違う、上記弊害

#### 推奨カタログ方式への再移行（`:stack/*` エイリアス方式 → 文書配布方式）
- **背景**: 段階 2 で `:stack/*` エイリアス方式を採用したが、実作業シミュレーションで重大な構造的問題が露呈：
  - **Polylith の brick deps.edn 構造との不整合**: Polylith は brick（base / component）の独立性を設計思想として持ち、各 brick は独自の deps.edn を持つ。本番ビルドは `projects/<deploy>/deps.edn` → `bases/.../deps.edn` → `components/.../deps.edn` の連鎖で依存解決される。ルートの `:stack/*` エイリアスは REPL 開発用にすぎず、**stack 層ライブラリが brick deps.edn とルート deps.edn の二重管理**になる
  - **STACK_GUIDE.md §3.6 と §4.2.3 の不整合**: Web API で DB を使う典型ケース（next.jdbc を §3.6 は web-api stack でも採用としているが §4.2.3 推奨ライブラリに含まれない）で LLM が判断に詰まる
  - **本番ビルド用 base deps.edn の指示不在**: BOOTSTRAP_GUIDE.md が stack エイリアスの採用しか扱わず、base deps.edn をどう書くかの具体的指示がない
- **ユーザからの本質的指摘**:
  - **「真実は一箇所にまとめたい」**: DRY 原則の深い解釈。同じライブラリ依存がルート deps.edn と brick deps.edn の両方に書かれるのは知識の重複
  - **「stack だけ特別扱いは変」**: 外部依存ライブラリは stack 所属かどうかで本質が変わらない。`:stack/*` エイリアス方式は stack 層のみ特別な構造を持たせる歪みを生んでいた
  - **「推奨ライブラリの完全一致を求めるのは間違い、漏れ検出は意味あり」**: 検証の種類を区別。stack 推奨の強制は不適切だが、機能カテゴリ充足や設定ファイル漏れの検出は価値がある
- **検討した選択肢（A〜H）**:
  - **A**: 現状維持（`:stack/*` エイリアス + brick deps.edn の二重管理受容）— 真実の一箇所化に反する、却下

#### stack 表の位置づけの明確化（判断結果のメモリーとしての性格）
- **背景**: 異分野のシミュレーションテスト（ML、ゲーム、ビジネスダッシュボード GUI）で「stack 表に未記載の領域に遭遇した LLM の動き」が議論に。stack 表のカバレッジ不足（ML stack や game stack の不在、データ可視化節の不在等、計 12 問題）が検出された
- **当初の誤った方向**: 検出された 12 問題への対処として、以下を順に提案してしまった
  - 案 1: 新 stack 追加（ML stack、game stack 等）と機能領域 §3 の拡充 → **stack 網羅性の追求**
  - 案 2: スコープ制限を明示（ML・ゲームは対象外と宣言） → Clojure + Polylith のせいにする誤り
  - 案 3: 未知への対処手続きを体系化（意思決定フロー、Q 雛形等） → **手続き網羅性の追求**（stack から手続きに対象を変えただけ、同じ誤り）
- **深い誤り診断**（ユーザ指摘により自己認識）:
  - 本テンプレートの第一原理は疲労最小化。**網羅の追求自体が疲労を生む**（網羅は永久に達成不可能な性質のもの）
  - Clojure + Polylith を採用した理由は「LLM が自律的に低負担で実装できる」ためで、適用分野とは独立。分野のせいにするのは誤り
  - stack・コード・技術選定は**すべて同じ原則（疲労最小化 + 三基底原則）から導出される**。原則は既に存在するので、あとは**未記載領域でも原則から導出する能力**を明示すれば足りる
  - 「補助」と位置づけるのも誤り。stack 表は単なる補助ではなく、**予め判断を済ませた結果のメモリー**として積極的価値を持つ
- **ユーザ指摘の核心**: 「stack 表は毎回複雑な判断をしないで済むようにするためのメモリー情報。stack 表の特性とプロジェクトのゴールが矛盾しないなら stack 表の利用は本件目的と矛盾しない。stack・コード・技術選定は全て同じ原則に従うだけ」
- **判断**: 以下の最小改訂で対処
  - **STACK_GUIDE.md §1.2**: stack 表を「判断結果のメモリー」として位置づけを明示。利用規律（矛盾しないなら信頼して利用、未記載領域は原則から導出、網羅を目的化しない）を記載
  - **CLAUDE.md §6.5.1**: stack 表の利用と原則からの導出の関係を 1 節で明示。両者は排他的でない。未記載領域でも第一原理から導出できる
  - **12 問題の個別対処は不要**: 原則からの導出で扱える問題として位置づけ
  - **新 stack・新機能領域の追加は不要**: 必要になった領域が原則からの導出を経てユーザ合意に至った時、メモリーに記録する（この順序を守る）
- **根拠**:
  - **自己適用性**: 本テンプレートの原則は本テンプレート自身の設計にも適用される。網羅の追求は疲労を生むため、それ自体が第一原理に反する
  - **AND 発想**: 「網羅か原則か」の二者択一ではなく、「メモリー（判断済み結果の記録）+ 原則からの導出（未記載への対処力）」の両立として枠組みを再構築
  - **Clojure + Polylith 採用の本質**: LLM の自律的・低負担実装を支える構造（brick 独立性、Malli 契約、data 駆動、全域性）は、適用分野に依存せず原則からの導出を可能にする土台として機能する
- **副次的発見**:
  - **メモリーと網羅の違い**: メモリーは「知っていることを記録する」、網羅は「全てを記録しようとする」。性格が全く異なる。前者は疲労最小化に貢献し、後者は疲労を生む
  - **網羅主義からの脱却は繰り返し発生する誘惑**: 私（設計者 / LLM）は 3 回連続で「何かを追加する」方向に走った（stack 追加、スコープ制限、手続き体系化）。自己適用性の規律を明示することで、今後の保守でも網羅主義への回帰を防ぐ
  - **シミュレーションの真の価値**: 異分野シミュレーションは stack 表の網羅性の問題ではなく、**設計哲学の自己矛盾**を炙り出す機能を持った。検出された 12 問題は「対処しない」が、検証プロセスとしては極めて有効だった
  - **「然程難しくない」の意味**: 原則が既に書かれている以上、必要なのは「それを未知への対処の拠り所として明示する」ことだけ。新規の規約・フロー・網羅を書く必要はない。これこそ疲労最小化に従った改訂姿勢
- **MAINTAINERS_GUIDE.md §9 姿勢セクションへの追加**: 本件の洞察を原則化した「自己適用性」の項を追加（§9.4）。今後の保守で「また網羅を足したくなる」誘惑への予防線

#### DESIGN.md の改訂方針の明確化（全面書き換え、差分表記なし）
- **背景**: 「実装中または実装後に仕様変更・追加がある場合の開発者の動き方」に関する質問。現状の文書に仕様変更手順の導線が明示的になく、また DESIGN.md §11 変更履歴という節が存在することで「DESIGN.md 内に履歴を残す」方針とも解釈できる状態だった
- **判断**: DESIGN.md は**現在の仕様の一次情報源**として機能する。変更履歴は本ファイル内に残さず、ADR・git・QUESTIONS.md アーカイブで保全する。改訂時は該当節を**全面書き換え**する（追記・差分表記にしない）
- **根拠**:
  - **原則 13（4 種文書分離）**: DESIGN は「何を作るか（現在形）」、ADR は「なぜ決めたか（不変の履歴）」、KNOWLEDGE は「現在有効な契約」、QUESTIONS は「判断保留」。履歴は ADR の責務であり DESIGN の責務ではない
  - **KNOWLEDGE.md §0.5 との対称性**: KNOWLEDGE は既に「上書きを恐れない、過去の内容は残さない」方針。DESIGN も同じ性格（現在を示す文書）なので同じ原則が適用される
  - **原則 7（文書の自己整合性）**: 履歴と現在形が混在すると「今何が有効か」の判定コストが増大
  - **疲労最小化**: 追記方式は時間と共に肥大化し、読み手が「古い記述と新しい記述」を区別する疲労を生む
  - **軌跡保全の十分性**: ADR（判断経緯）+ git（差分）+ QUESTIONS アーカイブ（未決事項の経緯）で軌跡は完全に保全される。DESIGN.md 内の履歴は冗長
- **判断の帰結として実施した修正**:
  - **CLAUDE.md §8.5 追加**: 仕様変更・追加への対処フロー（6 ステップ）。関連文書への導線明示。新規章ではなく §8 作業プロトコルの一節として配置（網羅主義を避ける）
  - **DESIGN.md §0.5 改訂**: 旧「§11 変更履歴に記録」を「ADR・git・QUESTIONS.md で保全、本ファイル内に履歴を残さない」に変更
  - **DESIGN.md §11 変更履歴の削除**: 旧方針の名残を廃止
  - **DESIGN.md 冒頭補強**: 「現在の仕様の一次情報源、変更履歴は本ファイル内に残さない」と明示
- **副次的発見**:
  - **導線整備と網羅主義の境界**: §8.5 追加は網羅主義か導線整備か。判断基準は「新規情報を書くか、既存リソースへの参照を書くか」。§8.5 は 6 ステップすべて既存文書の責務を引用する構成で、既存情報への導線整備として正当化される（§9.4 自己適用性の範囲内）
  - **文書間整合性の自己点検**: 今回、既存 §11 変更履歴の存在に気づいたのはユーザ質問への回答準備中。定期的に文書間の運用ルール整合性を点検する規律の価値を再確認（§5.9 の類似点検プロセス）
  - **ユーザ質問の検証機能**: 「DESIGN.md を全面書き換えしていいか」というご質問は、単に確認の意図を持っただけでなく、**文書体系の運用ルールが自己整合しているかの検証**にもなった。ユーザ質問が設計検証の機能を果たす構造は、LLM-人間協働の独特の強み

#### Malli を必須層として実体化する対応（宣言と実装の最終整合）
- **背景**: 外部レビューで「docstring は Malli instrumentation を全プロジェクト有効化と宣言しているが、実体は require も helper も両方コメントアウト状態」という指摘。前回の棚卸しで「Malli は必須層」と位置づけを明文化したが、**配布コードの実体がそれに追従していなかった**
- **問題の構造**: 設計上の宣言（Malli 必須層化）と配布コードの実体（コメントアウト）が乖離。これは `(go)` の説明でも顕在化し、POLYLITH_GUIDE.md §7.1 は「(go) で Integrant + Malli instrumentation 起動」と書きつつ、dev/user.clj の実体では `malli-on!` 自体が存在しない状態だった
- **判断**: Malli の require と helper 関数をコメントアウト解除してデフォルト有効化する。理由：
  - Malli は必須層であり、ワークスペースルート deps.edn で常に依存に入っているため、require しても壊れない
  - 全プロジェクトで使うことが確定している層について、コメントアウト状態を残す理由がない（YAGNI の逆 — 「使わないかもしれない」ではなく「必ず使う」なのだから、使える状態で配布すべき）
  - 「必須層は有効化された状態で配布、stack 層の Integrant/Portal は扱い指針とともに配布（使わない場合は削除）」という**層の扱い分け**が明確になる
- **対処**:
  - **dev/user.clj**: malli.dev と malli.dev.pretty の require をコメントアウト解除、`malli-on!` 関数の定義もコメントアウト解除。Malli セクションヘッダで「必須層。削除不可」と明示
  - **dev/user.clj docstring**: 主要コマンドに `(malli-on!)` を追加。扱い指針で「Integrant を使わないプロジェクトでは (malli-on!) を明示的に呼ぶ」と明記
  - **dev/user.clj §2.3 参照修正**: config 関数実装例の参照先を POLYLITH_GUIDE.md §2.3 → §2.4 に訂正（§2.3 は project、§2.4 が config 関数）
  - **README.md**: `clj -M:poly test` を `clj -M:poly test :all` に統一（初期ブートストラップ時は stable タグが存在しないため `:all` 必要）。関連する `poly test` 言及も統一
  - **POLYLITH_GUIDE.md §7.1**: `(go)` の説明を精確化。「Integrant を使うプロジェクトでは (go) で Integrant + Malli 一括起動、使わないプロジェクトでは (malli-on!) を明示的に呼ぶ」という両ケース対応の記述に
- **根拠**:
  - **層の扱い分けの原則**: 必須層（全プロジェクト共通）と stack 層（採用プロジェクトのみ）は配布時の扱いも異なるべき。必須層は有効状態で配布、stack 層はコメントまたは完成例として配布して選択的に削除
  - **宣言と実装の整合性（原則 7 文書の自己整合性）**: 「Malli は必須層」と宣言するなら、配布コードでも必須層として扱うのが自己整合的
  - **疲労最小化**: コメントアウト状態の必須層コードを毎回解除する作業は疲労増。配布時点で動く状態の方が LLM も人間も楽
- **副次的発見**:
  - **設計の宣言と実装の乖離は段階的に発生する**: Malli の位置づけを「必須層」と明確化した段階では、配布コードの修正が連動しなかった。**設計原則を変更した時、それが配布物の実体にどう反映されるかを同時に点検する規律**が必要
  - **「コメントアウトされたコードが残っている理由」への注意**: コメントアウト状態は「そのうち使う」「使わないかもしれない」「常に使う」のどれを意味するかが曖昧。今回の Malli は「常に使う」だったのでコメントアウト自体が不適切だった。今後、コメントアウトされたコードを見たら「これがコメントアウトされている意図は何か」を必ず確認する
  - **レビュアーの指摘の層が深まる**: 今回のレビューは既に浅い問題を除外して、残る本質的な矛盾（docstring と実体の乖離、test コマンドの不統一、内部参照のズレ）に絞って指摘していた。レビューのサイクルを通じて**問題の層が深まっていく**過程は、設計の成熟度を測る一つの指標

#### kaocha 削除とフィードバックループの原則化（疲労最小化の徹底適用）
- **背景**: ユーザの問い「kaocha --watch の活用について詳しく」「watch で検出した問題をフィードバックする仕組みが回って初めて意味がある」「疲労最小化の原則から解釈するとどうなりますか」「poly test によるテスト検出の明示的なルーチン化とそのフィードバックの利用を文書化するということですね? そこで出てきた問題はタスクとして捉えますか?」という段階的な問い直しから、kaocha という道具の議論ではなく、**フィードバックループのアーキテクチャ**を疲労最小化原則から設計し直す論点に到達
- **問題の構造**: 当初 kaocha は STACK_GUIDE.md §2.1 で必須層に位置づけられ、`kaocha --watch` が CLAUDE.md §1.2 のループ短縮実装例として言及されていた。しかし調査の結果、(a) `kaocha --watch` を動作させるための `tests.edn` 設定ファイルが同梱されていない、(b) `:test` エイリアスの実装は Polylith の brick 構造を拾えない状態、(c) `clj -M:poly test --watch` という存在しないフラグが記述されていた、等の**宣言と実装の乖離**が判明。kaocha は「名目上必須層だが実際には使える状態で配布されていない」という状態だった
- **疲労最小化原則からの解釈**: watch という非同期監視モデルは、**人間の集中力が分散している状況で背景監視として価値**を持つが、LLM は単一のターンに完全集中するため背景監視の価値が発生しない。むしろ LLM は**別プロセスの端末出力を読めない**ため、watch 型のフィードバックは構造的に LLM に届かない。疲労最小化の観点では、**LLM のフィードバックループは編集単位でターン内に閉じる**のが最も疲労が少ない。これは LLM の制約ではなく、LLM の特性が疲労最小化と自然に整合する結果
- **Polylith ネイティブでの代替**: `poly test` は stable タグからの diff で影響範囲を自動判定する。LLM が毎回「どこまで走らせるか」を考える疲労を省ける。完了条件は `poly test :all` で全体検証する。これで watch の代替として必要十分
- **判断・対処**:
  - **kaocha 関連の全面削除**（ユーザ指示「明示的な活用が想定できない kaocha に関する記述は削除するべき」）:
    - deps.edn: `:test` エイリアス全体削除（kaocha + kaocha-cloverage の依存も除去）、コメントの `clj -M:test` 言及削除
    - CLAUDE.md §1.2: `kaocha --watch` を削除し「ターン内検証」に置き換え
    - CLAUDE.md §10: `clj -M:poly test --watch`（存在しないフラグ）を削除し「監視モードに依存しない」を明示
    - STACK_GUIDE.md §2.1: 必須層表から kaocha 削除、必須エイリアス列挙から `:test` 除去。Polylith 組み込みテストランナーの採用を明記

    - DESIGN.md §4: ベンチマークテストの `kaocha プロファイル` 言及を削除
  - **フィードバックループ原則の明示**（CLAUDE.md §8.0.0 新設）:
    - 「LLM のフィードバックループは編集単位でターン内に閉じる」原則を明示
    - サイクル: 編集 → 影響範囲検証 → 結果読解 → 対処
    - 完了条件と日常作業の検証の使い分けを明記
  - **検出された失敗の振り分け判断軸の明示**（CLAUDE.md §8.0.0 内）:
    - 既存の受け皿（ターン内修正・QUESTIONS.md・KNOWLEDGE.md・ADR・§7 自己停止）への流し方を 5 パターンの表で提示
    - 「タスク」概念は本テンプレートに存在しないことを明示（既存受け皿への流し方で網羅できる）
- **根拠**:
  - **疲労最小化からの道具選択**: 「LLM のフィードバックは編集単位でターン内に閉じる」という原則が確立すれば、watch 型ツールは不要になる。kaocha は**この原則に合致しない道具**であり、必須層から外すのは自然な帰結
  - **宣言と実装の乖離の解消**: kaocha --watch を「戦略の実装例」として原則表に載せながら、実際には動かない状態で配布するのは原則 2（規約を明文化するだけでは守られない）に反する。削除は乖離の根本的解消
  - **「タスク」概念を導入しない理由**: 既存の 4 種文書分離（DESIGN / KNOWLEDGE / ADR / QUESTIONS）と §7 自己停止プロトコルで、作業中の全事象は性格別に受けられる。「タスク」という汎用層を追加すると、既存の受け皿とどう棲み分けるかを毎回判断する疲労が発生する。疲労最小化は**新しい概念を増やさないこと**を求める
  - **Polylith ネイティブの優位性**: Polylith の `poly test` は影響範囲自動判定という本テンプレートの疲労最小化方針と構造的に一致する。外部ツール（kaocha）を介する理由がない
- **副次的発見**:
  - **道具の議論と原則の議論の区別**: 「kaocha をどうするか」という道具の議論に入り込むと、「フィードバックループをどう閉じるか」という本質的な原則の議論を見失う。ユーザの段階的な問い直し（「詳しく」「フィードバックの仕組み」「疲労最小化の原則から」）によって、道具の層から原則の層へ議論が深まった
  - **LLM の特性を制約ではなく強みと捉え直す**: LLM が非同期通知を受け取れないことは一見制約だが、**ターン内で集中して完結するフィードバックが最も疲労が少ない**という結論に至ると、制約と価値が逆転する。LLM の特性は疲労最小化と自然に整合する
  - **振り分け判断軸の集約の価値**: 「検出された問題をどこに書くか」を毎回判断する疲労を、一度の明示で LLM の参照先に変える。これは §5 機械化原則の文書版。判断が機械化されれば疲労が減る
  - **既存概念の使いこなしが新規概念の追加より優れる**: 「タスク管理」という汎用層を追加するのではなく、既存の 4 種文書分離と §7 自己停止プロトコルを使い分ける判断軸を明示することで、新規概念の追加なしに問題を解決した。これは §9.4 自己適用性の実地適用

  - `polyfy/polylith` group id（git 取得時は正しい、Maven 取得なら `polylith/clj-poly` になる）
  - `poly create tag` が存在しない旨の記述（前回修正済み、正しい）
  - `poly test --watch` が存在しない旨の記述（前回修正済み、正しい）
  - `poly test project:<name>` の記法（公式例と一致、正しい）
  - `poly check` / `poly info` / `poly libs` / `poly deps` の記法（公式例と一致、正しい）
  - `poly create component name:<name>` / `poly create base name:<name>` / `poly create project name:<name>` の引数形式（公式例と一致、正しい）
- **副次的発見**:
  - **公式ドキュメントは版ごとに変化する**: tag-patterns の正規表現は 0.2.21 以前と 0.2.22 以降で異なる。「公式に準拠」と思い込んでいても、**どの版の公式か**を常に意識する必要がある
  - **Configuration ページと実例のブレ**: 公式 Configuration ページの表では `:compact-view`（単数）と記載されていたが、実際の例・他ページ・公式 workspace.edn 例はすべて `:compact-views`（複数形）だった。公式ドキュメント内にも typo や表記ブレがあり、**表記だけでなく実例と照合することが重要**
  - **LLM は「公式に準拠した」と主張しがち**: 今回の点検で、本テンプレートは設計思想は公式に合わせていたが、**具体的な設定ファイルの細部**で古い版・実機能しない独自キー・欠落が積み重なっていた。「公式準拠」という主張は**実証可能な形で検証されない限り信頼してはいけない**
  - **設定ファイルの『死んだキー』は検出しにくい**: `:release {:auto-tag? false}` のような Polylith が無視するキーは、動作には影響しないため通常の lint・test では検出されない。**公式仕様との網羅的照合**が唯一の検出手段。これは自動化が難しい領域で、定期的な人的点検が必要
  - **ユーザの明示指示が公式照合を駆動した**: LLM は内部的には「公式に準拠している」という信念を持ちがちだが、その信念自体を疑う契機はユーザの明示指示でしか生まれない。「勘違い、思い込み、不整合、コマンド仕様等でおかしなところがないか再確認」という問いの力は、**LLM の内的信念と外的実態を照合する作業を起動する点**にある

#### 2026-04-25: CLAUDE.md 判断面レビューの反映と章番号互換の維持
- **背景**: CLAUDE.md のレビューで、§1.2.5 承認設計、§8 検証粒度、§11 原則 13、`STACK_GUIDE.md §4.2` 参照など、多数の曖昧さが列挙された。個別の文言不足ではなく、**原理・判定基準・操作手順・外部参照が同じ層で混在している**ことが根本原因だった
- **判断**:
  - **章番号は API として扱う**: CLAUDE.md は LLM が頻繁に参照する入口文書であり、関連文書からの節番号参照も多い。大規模リナンバリングは一見きれいでも参照破壊を招くため、既存の主要番号は維持し、欠番や局所節の追加で補正する
  - **CLAUDE.md は入口・判定・ルータに徹する**: 詳細の正本は `COLLABORATION_GUIDE.md`、`STACK_GUIDE.md`、`BOOTSTRAP_GUIDE.md`、`MAINTAINERS_GUIDE.md` に残す。CLAUDE.md には日常判断に必要な最小定義、判定表、参照先を置く
  - **「単独完結」ではなく「辿れる文書グラフ」を目標にする**: すべてを CLAUDE.md に写すと二重管理になる。重要なのは、LLM がどの条件でどの詳細文書を読むかを迷わないこと
- **対処**:
  - CLAUDE.md §2 に L0/L1/L2/L3 の入口判定を追加し、禁止・承認必須・提案可・自動実行可の混同を減らした。詳細マッピングは `COLLABORATION_GUIDE.md` §2 に委譲
  - CLAUDE.md §7 に「ターン」「編集 1 回」「同一テストケース」「確度」の用語定義を追加し、自己停止プロトコルの再現性を高めた
  - CLAUDE.md §8 は §8.0 を着手前確認、§8.0.0 をターン内検証フィードバックとして整理し、検証粒度表・REPL 必須トリガ・失敗振り分けを分離した
  - CLAUDE.md §9 は Live Diagnosis Loop を条件分岐表に変換し、nREPL attach、bounded output、`:reload`、test 昇格の判断基準を明示した
  - CLAUDE.md §11 は原則 13 の短い定義と 4 文書の更新モードを追加し、詳細定義は MAINTAINERS_GUIDE.md §4 に委譲した
  - `STACK_GUIDE.md` に欠番だった §4.2 を追加し、`COLLABORATION_GUIDE.md` §2.2 の「記載あり / 記載なし」参照を実体化した
  - `BOOTSTRAP_GUIDE.md` の「完了後に archived へ移動」という旧儀式を削除し、CLAUDE.md §0 と同じ「フェーズ判定で自然に読まれなくなる」運用に統一した
- **根拠**:
  - **判断表は説明文より LLM に強い**: 自然言語の長い段落は、該当判定の途中で説明に埋もれる。トリガ・判定・次の行動を表に分ける方が、LLM の行動選択が安定する
  - **外部参照は節番号まで検査する**: 参照文が正しくても参照先節が存在しなければ、LLM はそこで停止する。文書改修時は `rg` で参照先の存在を確認し、欠番なら章番号互換を保ったまま補う
  - **原則 13 は毎日読む短縮定義と保守者向け完全定義を分ける**: CLAUDE.md に完全定義を置くと肥大化するが、定義が全くないと日常判断に使えない。短縮定義 + 詳細参照が最も保守負荷が低い
- **副次的発見**:
  - §8.0.0 のような「0.0」節は meta 手順を後から差し込んだ痕跡になりやすい。削除や大改番ではなく、前段に §8.0 を置いて層を分けると既存参照を壊さず整理できる
  - 承認規律は「不可逆性」だけでは足りず、「LLM が決定してよいか」「提案してよいか」「実行してよいか」の 3 軸で読まれる。L0/L1/L2/L3 の短い入口表が必要
  - ブートストラップ期の例外は長文で説明すると例外が正規ルートに見える。状態表にして「今どの状態か → 何を走らせるか」を明示する方が安全
