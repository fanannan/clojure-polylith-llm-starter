# KNOWLEDGE.md — 生きた知識

本プロジェクトの**現時点で有効な契約・不変条件・暗黙知**を集約する。
原則 13（`.llm/guide/MAINTAINERS_GUIDE.md` §4）で定義される**生きた知識（KNOWLEDGE）**の実装であり、QUESTIONS.md（判断保留）、adr/（決定履歴）とは性質が異なる。

**核心的な違い**: KNOWLEDGE は**上書き更新**される。旧版は消える。更新時の経緯が重要なら ADR に記録する。

---

## 0. 運用プロセス（原則 11 の実装）

> **呼び出し元**: 本節は `CLAUDE.md §8.0`（実装着手前の確認）の「既存知識の確認」ステップから呼び出される運用プロセス。空の場合の扱い（空スキャンで完了）は呼び出し元 §8.0 で一括規定（による相互参照構築）。
>
> **初期状態**: §1〜§5 の各節はエントリ 0（テンプレート配布時）。実装中に発見が出たら §0.4 フォーマットで追記する。

### 0.1 エントリのライフサイクル

```
    [発見 / Q resolved / 実装中の気付き]
                   │
                   ▼
              ┌─────────┐    更新     ┌─────────┐
              │ 追加     │ ─────────→ │ 有効    │ ──→ 廃止
              └─────────┘             └─────────┘
                                          │
                                  大きな方針変更
                                          │
                                          ▼
                                    新 ADR 発行
                                    + KNOWLEDGE を上書き
```

### 0.2 各操作の条件

| 操作 | トリガー | 手順 |
|---|---|---|
| **追加** | (a) Q resolved 時に昇格先が KNOWLEDGE と判定、(b) 実装中に新しい不変条件を発見、(c) Malli スキーマで表現しきれない契約に気づいた時 | 該当節に追記、`追加日` を記録、Q 発祥なら Q-ID を参照記載 |
| **更新** | ドメイン理解の深化、契約の精緻化、前提の変化 | 当該エントリを**上書き**、`更新日` を更新、大きな変更は ADR 発行して `背景: ADR-NNNN` を追記 |
| **廃止** | 機能削除、契約撤廃、前提の完全失効 | 当該エントリを**削除**、廃止理由を ADR で記録 |

### 0.3 Q からの昇格手順（QUESTIONS.md §0.5 の適用）

QUESTIONS.md §0.5 の判定で「KNOWLEDGE への昇格」が選ばれた場合：

1. 該当 Q の結論を、本ファイルの適切な節（§1〜§5）に**新エントリとして追記**
2. エントリに **`由来: Q-YYYY-MM-NNN`** を記載（軌跡の紐付け）
3. 背景が複雑で決定経緯も残すべきなら、ADR も併発し、エントリに `背景: ADR-NNNN-topic` を追記
4. QUESTIONS.md §0.4 に従い、Q を `resolved` としてアーカイブ、`反映先` に `KNOWLEDGE.md §X`（+ 必要なら ADR）を記入

### 0.4 エントリ記載フォーマット

```markdown
### <1 行タイトル>
- **追加日**: YYYY-MM-DD
- **更新日**: YYYY-MM-DD（更新時のみ）
- **由来**: Q-YYYY-MM-NNN / 実装中の発見 / DESIGN.md §X 由来
- **背景**: adr/NNNN-topic.md（必要な場合のみ、決定経緯の詳細はそちらへ）
- **内容**: 現在有効な契約・不変条件・暗黙知の本文

  具体例、適用範囲、例外条件など
- **関連コード**: `components/<n>/src/.../core.clj` の `<function>` 等
- **関連 Malli スキーマ**: `<namespace>/<Schema>`（スキーマで表現されている場合）
```

### 0.5 更新時の原則

- **上書きを恐れない**。KNOWLEDGE は「現時点の真実」。過去の内容は残さない
- **大きな変更は ADR を先に発行**し、KNOWLEDGE エントリに `背景: ADR-NNNN` を追記してから上書き
- `更新日` を必ず更新する
- 前提の変化・解釈の変更など、非自明な更新理由がある場合は ADR を必ず発行する

### 0.6 廃止エントリの扱い

完全に廃止されたエントリは本ファイルから削除し、**ADR で廃止理由を記録**する。
過去の KNOWLEDGE を「参考のため」として残さない（原則 13 違反の一因になる）。

削除した時の履歴は git commit が唯一の記録になる。ADR に該当 commit ハッシュを記載すると追跡が容易。

### 0.7 LLM による更新の承認

KNOWLEDGE.md を含む 4 種文書の編集権限マトリクスは **`.llm/guide/COLLABORATION_GUIDE.md` §2.3** が一次情報源。本節はその要約のみ示す。

- **LLM が独断で編集することは禁止**（`CLAUDE.md §2` 禁止事項の対象）
- LLM が実施してよい典型例: (1) Q resolved 時の昇格（QUESTIONS.md §0.4 に従う）、(2) ユーザの明示的指示、(3) 実装中の発見で事前承認を得た場合
- それ以外は、LLM は新エントリ案を QUESTIONS.md に Q として立て、承認を経てから追記する

詳細条件と例外（特別承認・部分承認の不採用等）は `COLLABORATION_GUIDE.md §2.3` を参照。

### 0.8 節構成の原則

以降の §1〜§5 は**推奨骨組み**であり、プロジェクトの性質に応じて節を増減してよい。
ただし以下を守る：

- **§ 番号は変えない**（参照の安定性）
- 節を追加する場合は末尾に `§6 その他` 以降として追加
- 既存節の大幅な再構成を行う時は ADR を発行

### Malli `m/=>` 契約は `interface.clj` に集約する
- **追加日**: 2026-04-24
- **由来**: 実装中の発見（clj-kondo の redefined-var 誤検出をきっかけに配置規約を統一）
- **内容**: brick の公開 `m/=>` 関数契約は **`interface.clj` に集約して書く**。`core.clj` には置かない。
  - 理由: §1.1.1 全域性「境界契約は境界で宣言」、Polylith の「interface 経由呼び出し原則」との整合
  - instrumentation カバレッジ: 外部呼び出しは interface 経由が原則（poly check で強制、テストも §10 で interface 経由）なので、interface.clj 側の契約が入力・出力を検証すれば十分
  - 機械検証: `.llm/scripts/check-interface-contracts.sh` が interface.clj 内の `(defn)` に対応する `(m/=>)` の存在を grep 検査する
  - core.clj 内部の相互呼び出しは brick 実装詳細で契約対象外（必須化しない）
- **関連コード**: `components/<name>/src/**/interface.clj`
- **関連設定**: `.clj-kondo/config.edn`（`:lint-as {malli.core/=> def-catch-all}` を設定**しない**こと。設定すると同一 ns 内の `(m/=> foo ...)` と `(defn foo ...)` が `:redefined-var` として誤検出される既知の罠。`:unresolved-symbol :exclude` は `.clj-kondo/imports/metosin/malli/config.edn` で既に設定済みのため `lint-as` 不要）
- **関連ガイド**: CLAUDE.md §4.1, §8.1 / CODING_GUIDE.md §2.1.1 / POLYLITH_GUIDE.md §2
