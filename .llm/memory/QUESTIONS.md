# QUESTIONS.md — 判断保留トラッカー

LLM が作業中に判断に迷った事項、設計判断が必要な事項を記録する。
**CLAUDE.md §7.3 撤退プロトコルの「D. 人間による設計判断を求める」の受け皿**でもある。

本ファイルは `.llm/memory/` 配下に置かれる。「分類管理の原則」（MAINTAINERS_GUIDE.md §4）で定義される**判断保留（QUESTIONS）**の実装であり、同配下の KNOWLEDGE.md（現時点で有効な知識）、adr/（決定履歴）と役割が異なる。

| 項目 | 内容 |
|---|---|
| **対象** | 未決の判断 |
| **更新するタイミング** | 判断がまだ確定していない時、自己停止時、仕様や境界で迷った時 |
| **更新しないもの** | 既に継続参照すべき事実、決定済みの理由、現在仕様 |
| **最初に見る節** | §0 運用プロセス |

### 更新トリガ早見表

| 起きたこと | ここに書くか |
|---|---|
| 実装を進める前に人間判断が必要 | 書く |
| 仕様・境界・技術選定が未確定 | 書く |
| 自己停止プロトコルで D を選んだ | 書く |
| 既に結論が出ており継続参照したい | 書かない。`KNOWLEDGE.md` か `ADR` |
| 一度きりの軽微な確認で履歴不要 | 通常は書かない |

## 0. 運用プロセス（判断とプロセスの対称性の実装）

> **呼び出し元**: 本節は `CLAUDE.md §8.0`（実装着手前の確認）の「未決判断の確認」ステップから呼び出される運用プロセス。空の場合の扱い（着手前確認は通過とみなす）は呼び出し元 §8.0 で一括規定する。
>
> **初期状態**: §2 未対応 / §3 解決済み / §4 却下・統合済み は、テンプレート配布時は §2 にサンプル Q が 1 件、§3・§4 は空。

### 0.1 Q の状態遷移

```
                      [LLM が提起]
                           │
                           ▼
                      ┌──────────────────┐
                      │   未対応(open)   │ ─── 2週間経過 ───→ エスカレーション（§0.6）
                      └────────┬─────────┘
                           │ [ユーザが議論を開始]
                           ▼
                   ┌──────────────────────┐
                   │ 議論中(in-discussion) │
                   └─────────┬────────────┘
                          │ [回答確定]
                ┌─────────┼─────────┐
                │         │         │
                ▼         ▼         ▼
           ┌────────────────────┐ ┌────────────────┐ ┌─────────────────────┐
           │解決済み(resolved)  │ │却下(wontfix)   │ │統合済み(superseded)│
           └────────┬───────────┘ └────────────────┘ └─────────────────────┘
               │
               └─(必要に応じて)─→ KNOWLEDGE.md §X / adr/NNNN-topic.md に反映

  別ルート: 未対応(open) → 保留(blocked) （外部事情・他Q依存）→ 未対応(open) に復帰
```

### 0.2 各状態の定義

| 状態 | 意味 | 遷移可能先 |
|---|---|---|
| **未対応(open)** | LLM が提起した直後、ユーザ未対応 | 議論中(in-discussion), 保留(blocked), 却下(wontfix) |
| **議論中(in-discussion)** | ユーザが回答・議論中 | 解決済み(resolved), 却下(wontfix), 統合済み(superseded) |
| **保留(blocked)** | 他 Q や外部事情で対応保留 | 未対応(open)（解消時）, 却下(wontfix) |
| **解決済み(resolved)** | 回答が反映された（§0.4 で処理済み）| — |
| **却下(wontfix)** | 議論の結果、対応しないと決定 | — |
| **統合済み(superseded)** | 別の Q に統合・代替された | — |

### 0.3 Q の記載フォーマット

```markdown
## Q-YYYY-MM-NNN: <1 行要約>
- **状態**: 未対応(open) / 議論中(in-discussion) / 保留(blocked) / 解決済み(resolved) / 却下(wontfix) / 統合済み(superseded)
- **提起日**: YYYY-MM-DD
- **更新日**: YYYY-MM-DD（状態遷移時に更新）
- **提起の経路**: 自己停止プロトコル §7.3 / Polylith 境界判断 / その他
- **文脈**: なぜこの判断が必要か（背景・制約）
- **選択肢**:
  - A. <案>: <利点・欠点>
  - B. <案>: <利点・欠点>
  - C. <案>: <利点・欠点>
- **推奨**: <LLM としての推奨案と理由>
- **影響範囲**: <変更が波及するファイル・モジュール>
- **反映先**: <解決済み(resolved) 時のみ記入。§0.5 の反映先分類を参照>
```

### 0.4 解決処理（解決済み(resolved) は実施後報告 (L2)、曖昧時のみ確認）

Q の解決済み(resolved) 化は、解決内容がユーザ回答・承認済み判断・実装反映から明確な場合、LLM が実施して事後報告する（実施後報告 (L2)）。毎回の「解決済み(resolved) にしてよいか」確認は承認儀式を増やし、疲労最小化に反する。

1. 解決根拠を確認する（ユーザ回答、ゲート承認済み判断、反映済み差分、実装結果など）
2. **§0.5 の反映先判定**を行い、必要なら DESIGN.md / KNOWLEDGE.md / ADR へ反映する
3. 状態を `解決済み(resolved)` に変更し、`更新日` と `反映先` を記入する
4. **§0.7 の選別ルールに従って処理**（ADR 反映時は削除可、他は 3 行要約を §3 に残す）
5. ユーザへ「Q-YYYY-MM-NNN を `<反映先>` に反映し 解決済み(resolved) にしました」と事後報告する

**確認が必要な場合**: ユーザ回答が曖昧、反映先が複数あり判断が割れる、または LLM が「解決した」と推定しているだけの場合は、解決済み(resolved) 化せず確認を求める。
削除判断は §0.7 に従う。編集権限の統一マトリクスは COLLABORATION_GUIDE を一次情報源とする。
∵ .llm/guide/COLLABORATION_GUIDE.md §2.3

### 0.5 反映先の判定（分類管理の原則の適用）

解決済み(resolved) Q の内容が、以下のいずれに該当するか判定する：

| 判定 | 反映先 | 理由 |
|---|---|---|
| **現時点で有効な契約・不変条件・暗黙知で、今後も更新され続ける** | `KNOWLEDGE.md` の該当節 | 現時点で有効な知識として継続参照 |
| **なぜそう決めたかの設計判断で、今後改訂しない（改訂時は新 ADR 発行）** | `adr/NNNN-topic.md`（新規発行） | 「決定履歴」として不変保持 |
| **プロダクト仕様に影響する** | `DESIGN.md` の該当節 | 「仕様」として合意の起点 |
| **一度きりの判断で、継続参照の必要なし** | 追加反映なし（アーカイブのみ） | 軌跡として残すだけで十分 |

**両方に該当する場合**（例: ADR として決定理由を残しつつ、契約として KNOWLEDGE にも書く）は、両方に記載してよい。ただし：
- **KNOWLEDGE 側には「背景: ADR-NNNN」と短く書く**（詳細は ADR）
- **ADR の側には「関連 KNOWLEDGE: §X」を書く**（実装状況は KNOWLEDGE）
- Q の `反映先` 欄に両方を記載

### 0.6 エスカレーション

提起から 2 週間経過した `未対応(open)` Q は、ユーザに再度確認を促す：

1. LLM が次回ユーザとの対話時に「Q-YYYY-MM-NNN は 2 週間 未対応(open) です。対応を決めたいのですが」と言及
2. それでも確定しない場合、状態を `保留(blocked)` に移し、理由を記載

### 0.7 軌跡の保全（「議論の軌跡を残す」の適用による選別化）

解決済み(resolved) / 却下(wontfix) / 統合済み(superseded) になった Q は、**反映先によって扱いを分ける**:

| 反映先 | Q の扱い | 理由 |
|---|---|---|
| **ADR 発行** | `§3` から**削除可**（反映した ADR を指す 1 行メモだけ残す） | ADR 本体の Context / Considered Alternatives に判断過程（選択肢・利点欠点）が完全保全されるため、Q の残存は冗長 |
| **DESIGN.md 反映** | `§3` に**軽く残す**（Q-ID・結論・反映先の 3 行要約） | DESIGN.md には結論のみ書かれ「なぜその結論に至ったか」が保全されない。遡読時の手がかりとして要約を残す |
| **KNOWLEDGE.md 反映** | 同上 | 同上 |
| **却下(wontfix) / 統合済み(superseded)** | `§3` に**軽く残す**（3 行要約） | 結論も反映先もないため、アーカイブが唯一の軌跡 |
| **一度きりの判断（追加反映なし）** | `§3` に**軽く残す**（3 行要約） | 軌跡として保全 |

**廃止された規約**: 「アーカイブが 100 件を超えたら年次分離」は 選別化で §3 が軽量化されるため、100 件到達の前に自然に吸収される。

削除する場合の判断は LLM 独断禁止、ユーザ承認を経る。詳細な履歴は git log が保全する。

### 0.8 LLM の自走禁止ルール

`未対応(open)` または `議論中(in-discussion)` 状態の Q に関わる箇所では：

- **推測で実装を進めない**
- 該当箇所のコードに `;; TODO(Q-YYYY-MM-NNN): <保留している判断>` を残す
- CI で `grep -rn "TODO(Q-" components bases development` により残存 Q を検出できるようにする（Polylith 構造では `src/` は存在せず、コードは `components/<n>/src`、`bases/<n>/src`、`development/src` に分散する）
- Q が `解決済み(resolved)` / `却下(wontfix)` / `統合済み(superseded)` になったら、対応する TODO コメントを削除して事後報告する

### 0.9 自己停止プロトコル（CLAUDE.md §7）からの連携

§7.3 撤退プロトコルで選択肢 D（人間による設計判断を求める）を選んだ場合：

1. §7.3 の報告フォーマット（試みた内容・残障害・仮説）を、そのまま**本ファイルの新規 Q の `文脈` と `選択肢` に転記**
2. ID を採番（`Q-YYYY-MM-NNN`）、状態を `未対応(open)` で記録
3. ユーザへの報告で「`.llm/memory/QUESTIONS.md` に Q-YYYY-MM-NNN として記録しました」と言及
4. 以降は §0.1 〜 §0.8 の通常運用に従う

### 0.10 スクラブ運用

スクラブ時期：月次（または機能リリース時）。実施者は人間またはユーザの指示を受けた LLM。

1. 全 `未対応(open)` Q を点検
2. 2 週間経過したものは §0.6 のエスカレーション
3. 類似 Q は統合（一方を `統合済み(superseded)`、他方に集約）
4. 前提が変わって意味を失った Q は `却下(wontfix)` に
5. `保留(blocked)` の解消条件が既に満たされているものは `未対応(open)` に戻す
6. アーカイブが肥大していたら年次分離を実施

## 1. 提起の優先対象（以下に該当したら必ず Q を立てる）

自己判断禁止の領域：

### 1.1 Polylith 構造判断

- 新規コンポーネントを切るかどうか
- 既存コンポーネントの分割・統合
- `interface.clj` の関数を変更・削除
- 新規 base / project の追加
- コンポーネント間の依存関係を変える判断
- 共通スキーマ・型の配置先

### 1.2 技術選定・設計

- brick（base / component）deps.edn へのライブラリ追加・変更（必要な用途別機能カテゴリの推奨反映、CLAUDE.md §6.2、選定論理は `.llm/guide/STACK_GUIDE.md`）
- 新しいライブラリの採用提案
- §1 原則（全域性・不変性・副作用隔離）の解釈で迷う場面
- 原則間の競合（例: 副作用隔離と性能のトレードオフ）

### 1.3 ドメイン・契約

- KNOWLEDGE.md に記載すべき新しい不変条件の発見
- 既存 KNOWLEDGE エントリとの矛盾に気づいた時
- DESIGN.md の仕様に曖昧さや矛盾を発見した時

### 1.4 CLAUDE.md §7 自己停止プロトコルで D を選択した時

§0.9 の連携手順に従い、必ず Q を立てる。
