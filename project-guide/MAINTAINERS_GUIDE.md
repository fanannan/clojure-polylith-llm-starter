# MAINTAINERS_GUIDE.md — テンプレート保守者のための設計原則

本文書は**このテンプレート自体を改修・保守する人間および LLM のための羅針盤**である。

日々の開発で LLM が読む必要はない（それは CLAUDE.md / CODING_GUIDE.md / POLYLITH_GUIDE.md の役割）。
本文書が必要になるのは以下の場合：

- **ライブラリ依存を更新・追加・削除する時**
- **新しい規約や落とし穴を各種ガイドに追記する時**
- **このテンプレートを別プロジェクトに複製・派生させる時**
- **配布形態（即有効 / 推奨カタログ / 不配布 / 完全排除）を変更する時**

**設計判断を表層で真似ず、原則に遡って再導出する**ための基盤として読まれたい。

---

## 1. このテンプレートの設計目的

### 1.1 目的：LLM と人間の共同開発における修復コストの最小化

本テンプレートは**疲労最小化原則**（CLAUDE.md §1）を配布物のレベルで実装する試みである。
具体的には、Clojure + Polylith + Malli + Integrant を技術スタックとするプロジェクトを、**LLM が最も誤りにくい形で立ち上げる**ための初期配布物である。

### 1.2 適用範囲

- Clojure 1.12 以降、tools.deps ベース
- Polylith ワークスペース構造を採用
- Malli を境界契約として必須採用（§1.1.1 全域性の実装）
- その他（HTTP、DB、ロギング、Integrant、aero 等）は**選定固定だが有効化は任意**

非適用：
- Leiningen プロジェクト
- 非 Polylith の単一プロジェクト
- ClojureScript / babashka のみのプロジェクト

## 2. 配布物設計の 4 値判断

ファイルおよびその内部の各要素は、以下の 4 値のいずれかに分類される。
**これがテンプレート設計の最重要判定軸である**。

| 値 | 定義 | 配布形態 | 例 |
|---|---|---|---|
| **即有効** | どのプロジェクトでも必要、かつ初期コストがゼロ | そのまま配布 | CLAUDE.md、.clj-kondo 必須 linter、Malli の deps |
| **推奨カタログ（文書配布）** | 選定済だが目的依存で、プロジェクト開始時に採用判断。brick の deps.edn に反映される | STACK_GUIDE.md §4.2 で推奨ライブラリとして文書化。deps.edn には出現しない | Integrant、Ring、next.jdbc、mulog（各 stack の推奨として §4.2.X に記載） |
| **不配布（文書化）** | 特定ドメイン・架空のサンプル | 配布せず、POLYLITH_GUIDE.md にコード例として埋め込む | user component、api base |
| **完全排除** | 技術選定で却下されたもの | 名前も出さない（禁止・非推奨として STACK_GUIDE.md §8 に記録） | §8.1 禁止ライブラリの 3 件 |

### 2.1 判定の原則

新規要素をテンプレートに加える提案が来たら、以下の順で判定：

1. **どのプロジェクトでも必ず使うか？** → Yes なら **即有効**
2. **技術選定として固定されているが、目的依存か？** → Yes なら **推奨カタログ（文書配布）**（どの stack に含めるかは STACK_GUIDE.md §4.2 で判断）
3. **特定ドメイン・架空のサンプルか？** → Yes なら **不配布**（文書化）
4. **技術選定で却下されたか？** → Yes なら **完全排除**（名前も出さない、または STACK_GUIDE.md §8 に禁止・非推奨として記録）

### 2.2 推奨カタログ配布の運用

**真実の一箇所化**: ライブラリ依存の一次情報源は **brick の deps.edn**（Polylith の本番ビルドはそこから依存解決する）。テンプレート側はライブラリ依存を実装として持たず、**STACK_GUIDE.md §4.2 で推奨カタログとして文書化**する。各 brick の deps.edn に推奨を書く際のガイドとして機能する。

推奨カタログとして配布する要素は**動作が保証された標準形**でなければならない。動作不明なものを推奨すると、採用時にハマる。したがって：

- 推奨ライブラリは**実在のバージョンで動作確認した後**に STACK_GUIDE.md §4.2 に掲載する（§5.6.2 動作検証）
- 各推奨の上に選定根拠（STACK_GUIDE.md §3 該当節）と却下した代替（§3 該当節、§8 禁止・非推奨）を書く
- バージョン目安は定期的に更新する（§5.1 参照）
- 採用時の確認事項を §4.2.X に記載し、機能カテゴリ充足・設定漏れの防止に活用する

**推奨カタログ方式の利点**:
- **特別扱いなし**: stack 層ライブラリもプロジェクト固有ライブラリも、どちらも brick の deps.edn に書かれ、扱いが対称
- **Polylith の brick 独立性と完全整合**: brick の deps.edn が自己完結
- **二重管理の回避**: ワークスペースルートの deps.edn には必須層のみ配置、stack 層は brick に集約
- **推奨の柔軟性**: 推奨からの逸脱は ADR 発行で記録し、文書化で許容（機能カテゴリ充足が確認できれば具体ライブラリ一致は強制しない）

設計根拠の詳細は **STACK_GUIDE.md §1.2 本文書の性格**。推奨カタログの保守規律は **§5.9** で規定。

| ファイル | 区分 | 配布形態 | プロジェクト運用 |
|---|---|---|---|

| project-memory/KNOWLEDGE.md | E | §0 運用プロセス + 空の §1〜§5 | エントリを上書き更新 |
| project-memory/adr/README.md | E | 運用ルール（不変） | — |
| project-memory/adr/template.md | E | ADR 雛形（不変） | — |
| project-memory/adr/NNNN-topic.md | E | テンプレートには含めない | プロジェクトで発行、発行後は不変 |

### 3.5 不配布（C: 特定用途）

以下は**このテンプレートには含めない**。POLYLITH_GUIDE.md 内にコード例として記述する：

- `components/<any>/` 配下のファイル（ドメイン仮定）
- `bases/<any>/` 配下のファイル（エントリ種別仮定）
- `projects/<any>/` 配下のファイル（デプロイ単位名仮定）
- `projects/<any>/resources/config.edn`（aero + profile 構成の仮定）
- `projects/<any>/build.clj`（tools.build 採用とメインクラス名の仮定）

これらは `poly create` で生成される、または `project-guide/BOOTSTRAP_GUIDE.md` に従って初回作成される。

## 4. 設計 13 原則（本テンプレートの作成過程で得られた学び）

本テンプレートの保守を担う者は、以下の原則に沿って判断する。
表層の「こうなっている」を踏襲せず、**原則に遡って判断する**こと。

### 原則 1: 原理を文書の最上位に置く

**内容**: 疲労最小化という第一原理は、CLAUDE.md §1 に常に最上位で存在し、各章は「§1.X の実装」として自らを位置づける。
**守らないとどうなるか**: 個別規約の羅列になり、LLM は**なぜその規約があるか**を理解できず、未知の状況で原則を外した形式適用をする。
**保守時のチェック**: 新規に章や規約を追加する時、「これは §1 のどの原則の実装か」を答えられなければ追加しない。

### 原則 2: 規約を明文化するだけでは守られない

**内容**: 「〜してはならない」を文書に書くだけで LLM が守る保証はない。実効性を持たせるには、**機械化（ツールで強制）** または **自己停止プロトコル（明示の発動条件）** のいずれかで守る手段を同時に設計する。
**守らないとどうなるか**: 文書が祈りになる。30 分ルールが典型例で、LLM は時間感覚を持たないためターン数・試行回数への変換が必要。
**保守時のチェック**: 新規規約を追加する時、「これを守らせる手段は何か」を明記できなければ追加しない。

### 原則 3: 配布物の二値判断を避ける

**内容**: 「配布するか、しないか」ではなく、「即有効 / 推奨カタログ（文書配布）/ 不配布 / 完全排除」の **4 値で判断する**。使用頻度・目的依存性・バイアス注入の懸念が要素ごとに違うため、配布形態にグラデーションを設ける。推奨カタログは STACK_GUIDE.md §4.2 で文書として配布され、実装は各 brick の deps.edn に反映される（真実の一箇所化、§2.2 参照）。
**守らないとどうなるか**: 「全部入りで配布」して余計なバイアスを注入するか、「最小で配布」して毎回判断コストを発生させるかの両極端になる。
**保守時のチェック**: §2.1 の判定フローで各要素を分類する。推奨カタログの詳細運用は §5.6、選定論理は `STACK_GUIDE.md` 参照。

### 原則 4: 「汎用」は相対概念。基準を明示する

**内容**: 「このファイルは汎用」と言った時、それは「Clojure 言語として汎用」なのか「このテンプレートの技術選定下で汎用」なのかを明示する。後者の場合はファイルの docstring / 冒頭コメントに「〜の採用の帰結として配布される」と書く。
**守らないとどうなるか**: LLM / 保守者がファイルを「調整対象」と「不可侵」で誤判定する。
**保守時のチェック**: 新規配布ファイルには必ず冒頭コメントで前提を明示する。

### 原則 5: LLM は削除が苦手

**内容**: 与えられたコードを LLM は「利用すべきもの」として解釈する傾向がある（Rails 等の従来テンプレート文化では「雛形から削る」が一般だったが LLM 時代には不適）。したがって**最初から余計なものを置かない**。
**守らないとどうなるか**: 架空ドメイン（`user`）、架空エントリ（`api`）、架空 project 名（`api-server`）などがプロジェクトの「慣行」として誤認される。
**保守時のチェック**: 新規ファイル追加時、「これは LLM が削除できない前提で配布されるが問題ないか」を自問する。

### 原則 6: サンプルとテンプレートは役割が違う

**内容**: テンプレートは「プロジェクト共通の初期構成」、サンプルは「書き方の教材」。サンプルをテンプレートに混ぜると、テンプレートが汎用性を失い、サンプルが教材としての純粋性を失う。
**守らないとどうなるか**: 両方が劣化する。
**保守時のチェック**: サンプルは POLYLITH_GUIDE.md / CODING_GUIDE.md のコード例ブロックに埋め込む。テンプレートファイルとしては配布しない。

### 原則 7: 文書の自己整合性

**内容**: 文書が自らの述べている原則を自らに適用できているかを、設計レビューの最終段階で必ず検証する。たとえば「規約を機械化せよ」と書きながら、自らの規約（30 分ルール等）を機械化していないのは矛盾。
**守らないとどうなるか**: LLM / 保守者は文書の建前と実態の乖離を感じ取り、文書全体への信頼を失う。
**保守時のチェック**: 文書を改訂したら、「この文書は自らの原則に反していないか」を問う一回路を最終工程に置く。**自己整合性は整理を通じて維持される**。具体的な整理姿勢は §9.3 を参照。

### 原則 8: 自動検出されないものを前方に置く

**内容**: 文書の章順は「自動検証できないもの」「違反影響が甚大なもの」を前方に、「ツールが検出するもの」を後方に並べる。違反を後から検出できるものは文書の前方で目立たせる必要性が低い。
**守らないとどうなるか**: 冒頭から細かいツール設定が並び、LLM が最重要の不可逆操作禁止を見落とす。
**保守時のチェック**: 章順を変更する時、「これは自動検証されるか / 影響がどれだけ不可逆か」で再評価する。

### 原則 9: 設計判断の軸を先に確定する

**内容**: 何かを「含める / 除外する」を判断する前に、判定軸が**網羅的か**を先に検証する。軸が一つだけだと表層的な結論になる。
**守らないとどうなるか**: 結論が恣意的になり、同じ問題で繰り返し再検討が発生する。
**保守時のチェック**: 重要な判断を下す前に「判定軸を何個用意したか、それで網羅できているか」を確認する。

### 原則 10: 議論の軌跡を残す

**内容**: 設計判断の結果だけでなく、その**判断に至った経緯・検討した反対仮説・却下した選択肢**も本文書に記録する。これにより将来の保守者は、判断を真似るのではなく、原則から再導出できる。
**守らないとどうなるか**: 時間経過で判断が「自明の前提」化し、前提が変わった時に気づけない。
**保守時のチェック**: 新しい設計判断を下したら、「判断」「根拠」「検討した代替案と却下理由」を本文書に追記する。

### 原則 11: 判断とプロセスの対称性

**内容**: 設計判断（what）を定義したら、その判断を**運用・実行するプロセス（how）**も同時に定義する。判断だけ文書化してプロセスを暗黙にすると、LLM / 人間は判断だけ受け取ってプロセスを自力で捏造する。
**守らないとどうなるか**: 「配布形態は決めたが有効化手順はない」「禁止事項は書いたが違反検出方法は書いていない」「規約は定めたが遵守確認手段はない」のような片手落ちが累積する。規約が祈りに、判断が抽象論になる。
**保守時のチェック**: 新しい設計判断を下した時、以下を同時に答えられるか確認する：
  - この判断は**誰が・いつ・どの順序で**実行するのか
  - 実行後の整合性は**どう検証する**のか
  - 失敗時の**復旧手順**は何か
  答えられないなら、プロセス未定義の判断として追加してはならない。原則 2（規約だけでは守られない）の一般化である。

### 原則 12: 原則追加時の遡及適用

**内容**: 新しい原則を §4 に追加した時、**既存の全ての判断・規約・文書にその原則を遡及適用して違反を点検する**。新原則を立てただけで放置すると、既存体系に原則違反が潜伏し続ける。
**守らないとどうなるか**: 新原則が「今後の判断には適用するが既存は例外」という二重基準になる。時間経過で新旧の規約が矛盾し、文書全体の信頼性が損なわれる。
**保守時のチェック**: 新原則を追加したら、以下の遡及適用プロセスを必ず実行する：
  1. 全文書（CLAUDE.md、CODING_GUIDE.md、POLYLITH_GUIDE.md、QUESTIONS.md、KNOWLEDGE.md、DESIGN.md、ADR、BOOTSTRAP_GUIDE.md、本文書）を新原則で点検
  2. 違反箇所をリストアップし、修正可否を判定（修正コスト vs 効果）
  3. 修正する場合は、単独追記ではなく**既存体系全体の改善として統合実施**
  4. 点検結果と修正内容を §7 議論の軌跡に記録
  原則の追加は「原則を 1 つ増やす」ではなく「既存体系を新原則で再評価する」作業である。**遡及適用時は追加よりも整理の機会を先に点検する**。整理姿勢の詳細は §9.3 を参照。

### 原則 13: 仕様・知識・決定履歴・判断保留の分離

**内容**: プロジェクトに関わる文書を以下の 4 種に明確に分離し、役割を混同しない。各種別は性質・配置・ライフサイクルが対照的であり、混在すると文書の信頼性が崩壊する。

| 種別 | 性質 | 配置 | ライフサイクル |
|---|---|---|---|
| **仕様（DESIGN）** | 何を作るか。合意の起点 | `DESIGN.md`（ルート） | プロジェクト初期に確定、大きな方針転換時のみ改訂 |
| **生きた知識（KNOWLEDGE）** | 現時点の真実。契約・不変条件・暗黙知 | `project-memory/KNOWLEDGE.md` | 実装中に継続更新、常に最新状態を保つ（上書き） |
| **決定履歴（ADR）** | なぜそう決めたかの不変記録 | `project-memory/adr/NNNN-topic.md` | 一度発行したら変更禁止、改訂は新 ADR で supersede |
| **判断保留（QUESTIONS）** | 未決の判断。一時的 | `project-memory/QUESTIONS.md` | open → resolved で閉じる、軌跡はアーカイブ |

**守らないとどうなるか**:
- KNOWLEDGE（現時点の真実）が ADR（不変履歴）に混入 → 後から書き換えられて歴史改変が起きる
- ADR（不変履歴）が KNOWLEDGE に混入 → 更新時に元の決定理由が失われる
- QUESTIONS（一時的判断）が KNOWLEDGE に混入 → 未決事項が継続参照の源泉と誤認される
- DESIGN（仕様）が KNOWLEDGE に混入 → 合意の起点と実装知識の区別が消える

**保守時のチェック**: 新しい情報を記録する時、以下を順に自問する：
  1. これは「何を作るか」の仕様か → DESIGN.md
  2. これは現時点の契約・不変条件で、今後も更新され続けるか → KNOWLEDGE.md
  3. これは「なぜそう決めたか」の経緯で、今後改訂しないか → ADR
  4. これは未決の判断で、いずれ結論が出るか → QUESTIONS.md
  判断できない場合は、QUESTIONS.md に Q を立てて分類自体を相談する。

**補足 — Q からの昇格**: QUESTIONS.md の Q が resolved になった時、その内容が「現時点の真実として継続参照される」なら KNOWLEDGE.md へ、「なぜそう決めたかの不変記録」なら ADR へ昇格する。resolved Q 自体はアーカイブに残り、昇格先への参照を `反映先` 欄に記録する。

## 5. 保守・改修の判断フロー

### 5.1 ライブラリ依存の更新

`clj -M:outdated` で更新候補を確認後（stack 層ライブラリは brick の deps.edn 経由で走査される、§5.6.1 参照）：

1. **セキュリティパッチ系**: 即適用（必須層・推奨カタログ両方。推奨カタログは STACK_GUIDE.md §4.2 のバージョン目安に反映）
2. **メジャーバージョンアップ**:
   - 必須層の依存は、CI の全テスト通過後に適用
   - 推奨カタログ内の依存は、該当 stack の動作検証（§5.6.2）時にまとめて STACK_GUIDE.md §4.2 に反映
3. **API 破壊的変更を含む更新**:
   - STACK_GUIDE.md §3 選定根拠・§4.2 推奨ライブラリ表を更新
   - 変更影響を CODING_GUIDE.md / POLYLITH_GUIDE.md に反映
   - 必要なら CLAUDE.md の記述も修正

### 5.2 新しいライブラリを採用する場合

以下を順に検討：

1. **そもそも必要か？**
   - Clojure 標準（clojure.string, clojure.set, clojure.walk 等）で足りないか
   - 既に採用している Malli や各 stack の推奨ライブラリで代替できないか
2. **§2.1 の 4 値判断でどの区分に入るか**（即有効 / 推奨カタログ / 不配布 / 完全排除）
3. **推奨カタログに入れる場合、どの stack に含めるか**（STACK_GUIDE.md §4.2 で判断）
4. **STACK_GUIDE.md §3 に選定根拠を追記、代替として何を却下するか**を同時に決める
5. **既存コード・文書への影響範囲**を確認

詳細は §5.6.3 新規ライブラリ採用時の手順、§5.9 STACK_GUIDE.md の保守。

### 5.3 ライブラリを削除する場合

1. **なぜ削除するか**を本文書 §7（議論の軌跡）に記録
2. **代替は何か**を明示（なし、別ライブラリ、Clojure 標準）
3. **完全排除するか、STACK_GUIDE.md §8.2 非推奨に落とすか**を判定
4. STACK_GUIDE.md §3・§4.2 から削除、§8.2 非推奨に追加（推奨代替ありタグ）
5. 関連文書（CLAUDE.md / CODING_GUIDE.md / POLYLITH_GUIDE.md）の記述を整合的に更新

詳細は §5.6.4 推奨カタログの削除・置換、§5.9.5 推奨ライブラリの差し替え。

### 5.4 新しい規約を追加する場合

1. **原則 1**: §1 のどの原則の実装か明示
2. **原則 2**: 守らせる手段（機械化 / 自己停止プロトコル / チェックリスト）を同時設計
3. **原則 8**: 自動検出されるか否かで文書配置を決める
4. **原則 5**: LLM が形式適用に陥らないよう、意図を「なぜ」で説明

### 5.5 新しい LLM 落とし穴を追加する場合

CODING_GUIDE.md §1 に追加。フォーマットは既存の項目（§1.1〜§1.14）と同じ：

- 兆候（どんな時に現れるか）
- 対処（どう直すか、どう回避するか）
- 必要なら良い例 / 悪い例

追加順は時系列でよい（§1.15, §1.16, ...）。

### 5.6 STACK_GUIDE.md §4.2 推奨カタログの保守

STACK_GUIDE.md §4.2 で推奨カタログとして配布されている各 stack の推奨ライブラリは「採用されなくても腐ってよい」わけではない。各 stack の推奨が実在・動作する状態を保つ。原則 11（判断とプロセスの対称性）に従い、以下のプロセスで保守する。

**推奨カタログの一次情報源は `STACK_GUIDE.md` §4.2**（本ファイルは deps.edn を一次情報源としない、選択肢 H）。本節は推奨カタログの保守（バージョン更新、動作検証、新規採用、削除・置換）を扱う。stack 構成の論理変更（新 stack 追加、構成変更）は `STACK_GUIDE.md` および §5.9 を参照。

#### 5.6.1 バージョン更新

- **問題**: ワークスペースルートの deps.edn には stack 層のライブラリが含まれないため、`clj -M:outdated`（antq）は stack 層ライブラリを直接走査できない。各 brick の deps.edn、または検証用プロジェクトを介して確認する
- **対処**:
  - 四半期に 1 回、検証用プロジェクト（§5.6.2）を作成し、`clj -M:outdated` を brick 別に実行
  - 更新が必要なものを STACK_GUIDE.md §4.2 のバージョン目安に反映
  - セキュリティパッチは即時反映（§5.1）

#### 5.6.2 動作検証（年 1 回）

推奨カタログが経年で壊れていないか定期検証する：

1. テンプレートから派生した**検証用プロジェクト**を作成（実プロジェクトとは別）
2. 各 stack を採用して brick を作成し、STACK_GUIDE.md §4.2 の推奨ライブラリを brick deps.edn に反映
3. 各 brick が単独で依存解決できることを確認:
   ```bash
   cd bases/<entry> && clj -Spath > /dev/null && echo ok
   cd components/<domain> && clj -Spath > /dev/null && echo ok
   ```
4. 典型的な組み合わせで REPL 起動・テスト通過を確認:
   ```bash
   clj -M:dev:nrepl
   ```
5. `clj -M:lint` / `clj -M:poly check` / `clj -M:poly test :all` / uberjar ビルドが通ることを確認
6. 各 stack の §4.2.X 採用時の確認事項を実際に点検
7. 通らない箇所を本テンプレート側（STACK_GUIDE.md §4.2）で修正

この作業は MAINTAINERS_GUIDE.md §7 議論の軌跡に「<日付>: 統合検証実施、修正点 <...>」として記録する。

#### 5.6.3 新規ライブラリ採用時の手順

§5.2 の手順 + 以下を追加：

1. ライブラリが「推奨カタログ」区分なら：
   - **STACK_GUIDE.md §3 に選定根拠**を追加（採用・検討した代替・採用理由・採用 stack）
   - **STACK_GUIDE.md §4.2 の該当 stack**の推奨ライブラリ表に追加
   - 該当 stack の §4.2.X **採用時の確認事項**を必要に応じて更新
   - `development/src/dev/user.clj` に使用例の placeholder が必要なら追加
   - `.clj-kondo/config.edn` の `discouraged-var` 追記が必要なら追加
   - **POLYLITH_GUIDE.md §2 のコード例を更新**（使用例が必要な場合）
2. 配布前に、§5.6.2 の動作検証を該当 stack について実行

#### 5.6.4 推奨カタログの削除・置換

推奨カタログからライブラリを削除する、または別ライブラリに置換する場合（§5.9.5 推奨ライブラリの差し替えと連動）：

1. 本文書 §7 議論の軌跡に削除・置換理由を記録
2. **STACK_GUIDE.md §3 の該当節を更新**（採用理由の書き換え、または採用から却下への移動）
3. **STACK_GUIDE.md §4.2 該当 stack** の推奨ライブラリ表を更新
4. **STACK_GUIDE.md §8.2 非推奨ライブラリ**に旧ライブラリを追加（推奨代替ありタグ、移行方針を記載）
5. 該当 stack の §4.2.X **採用時の確認事項**を必要に応じて更新
6. `development/src/dev/user.clj` / `.clj-kondo/config.edn` から該当箇所を削除（使用例があった場合）
7. POLYLITH_GUIDE.md §2 コード例から該当部分を削除
8. CLAUDE.md §3 技術スタック表（もし言及あれば）から除外

**新 stack の追加・既存 stack の廃止**は `STACK_GUIDE.md` と MAINTAINERS_GUIDE.md §5.9.2 / §5.9.3 の手順に従う。

### 5.7 project-memory 文書群の保守（原則 13 の実装）

区分 E（プロジェクト固有の継続更新対象）に属する QUESTIONS.md / KNOWLEDGE.md / adr/ は、テンプレートから派生したプロジェクトで運用される。テンプレート保守者はこれらの**運用規則自体**を保守する責任を持つ。

#### 5.7.1 KNOWLEDGE.md のライフサイクル規則

テンプレートの KNOWLEDGE.md §0 運用プロセスを改訂する場合：

1. 改訂理由を本文書 §7 議論の軌跡に記録
2. KNOWLEDGE.md §0 を更新
3. 既存プロジェクトへの影響（過去エントリの扱い変更など）を文書化
4. QUESTIONS.md §0.5 の昇格先判定との整合性を確認
5. 原則 12 遡及適用：本文書 §4 の原則群との衝突がないか点検

#### 5.7.2 ADR 運用規則の改訂

`project-memory/adr/README.md` を改訂する場合：

1. **発行基準の変更**は慎重に。ADR は不変性が本質なので、ルール変更は過去の ADR 全てに影響する
2. 過去 ADR の status 更新規則変更は禁止（superseded の仕組みは変更不可）
3. 新しい書式セクションの追加は可、既存セクションの削除は禁止（過去 ADR が無効扱いになる）
4. template.md の変更は新規 ADR にのみ影響（過去 ADR には遡及しない）

#### 5.7.3 DESIGN.md 雛形の改訂

`DESIGN.md`（テンプレートのルート）の雛形を改訂する場合：

1. 🔴 必須項目の追加：慎重に。既存プロジェクトのブートストラップ完了状態を破壊する可能性
2. 🟡 推奨 / ⚪ 任意項目の追加：影響は限定的、自由度が高い
3. 項目削除は原則禁止（過去プロジェクトで既に埋められている）
4. プロダクト特性による追加項目は、本テンプレートには反映せず派生プロジェクト側で追加する

#### 5.7.4 QUESTIONS.md 運用規則の改訂

状態機械（§0.1）、昇格先判定（§0.5）、エスカレーション閾値（§0.6）などの変更：

1. 変更理由を本文書 §7 議論の軌跡に記録
2. 既存の open / in-discussion / blocked Q への影響を評価（マイグレーション手順を記述）
3. 自己停止プロトコル（CLAUDE.md §7.3）との連携（§0.9）に影響がないか確認

### 5.8 README.md 雛形の保守

README.md はテンプレート配布時と派生プロジェクト運用中で**役割が正反対**（前者は内部向け説明、後者は外部向け説明）。両者の混在防止が保守の要点。

#### 5.8.1 テンプレートの README.md 改訂時

- 冒頭の**警告ブロック**（書き換え前提の明示）は**絶対に消さない**
- ファイル構成図・導線表・開始手順はテンプレート全体の変更に応じて更新
- プロダクト機能の説明は書かない（それは DESIGN.md の役割）
- 書き換え手順への参照（`project-guide/BOOTSTRAP_GUIDE.md` §4）を維持

#### 5.8.2 派生プロジェクトでの書き換え検証

年 1 回の統合検証（§5.6.2）で、**検証用派生プロジェクトで README.md を実際に書き換える**ことを手順に含める。書き換え手順が煩雑すぎたり、書くべき内容が不明瞭な場合は、テンプレート側の BOOTSTRAP_GUIDE.md §4 を改善する。

#### 5.8.3 README.md と DESIGN.md の重複回避

両者は役割が違う：

- **README.md**: プロジェクトに初めて触れる人向けの入口、ファイル構成・開始手順・ビルド方法
- **DESIGN.md**: 実装者・保守者向けのプロダクト仕様、目的・スコープ・機能要件・受入基準

派生プロジェクトで書き換える時、両者に同じ内容を書かない。README.md は DESIGN.md への導線を提供する形にする。

### 5.9 STACK_GUIDE.md の保守

STACK_GUIDE.md は**テンプレート設計者の知見を蓄積する中核文書**であり、他ガイドと異なる保守規律を持つ（STACK_GUIDE.md §1.2 本文書の性格）。

#### 5.9.1 基本方針

- **継続的充実**: stack・機能領域・選定根拠は時間とともに増える。ファイルサイズを気にしない
- **「なぜ」を必ず書く**: 選定理由・却下理由が不足すると LLM も人間も将来判断できなくなる
- **派生プロジェクトでは更新しない**: 保守はテンプレート側で行う
- **整理優先（§9.3）は適用される**: 新規追加より既存の整理で済まないかを先に問う

#### 5.9.2 新 stack を追加する場合

ブートストラップで新しい用途への対応が必要と判明した時の手順：

1. **既存 stack で実現できないか点検**（§9.3 整理優先）
   - 既存 stack の組み合わせで対応できないか（例: web-api stack + worker stack）
   - 既存 stack の選定ポイントに知見追加で済まないか
2. 独立 stack として必要なら以下を実施：
   - **STACK_GUIDE.md §2.2 stack 層の一覧**に新 stack を追加
   - **STACK_GUIDE.md §4.1 選定基準表**に追加
   - **STACK_GUIDE.md §4.2 に新しい節**を追加（統一フォーマット: 目的・必要機能・推奨ライブラリ・選定ポイント・避けるべきライブラリ・採用時の確認事項）
   - **§3 機能別選定根拠**に必要な新機能が含まれる場合、§3 にも追記
   - **ADR を発行**（`adr/NNNN-add-stack-XXX.md`）。検討した却下案も記録
3. MAINTAINERS_GUIDE.md §7 議論の軌跡への記録（原則 10）
4. 検証用プロジェクトで該当 stack を採用し、brick deps.edn 反映→ `clj -Spath` 確認（§5.6.2）
5. CI に brick 単位の依存解決確認を追加（`cd bases/<entry> && clj -Spath`）

#### 5.9.3 新機能領域（§3）を追加する場合

新しい機能カテゴリ（例: 新しい認証方式、新種のストレージ等）が必要になった時：

1. **既存 §3.X で扱えないか点検**
2. 独立した機能領域として必要なら：
   - **STACK_GUIDE.md §3 に新節を追加**（統一フォーマット: 採用・検討した代替・採用理由・採用 stack・ノウハウ）
   - 該当する既存 stack の **§4.2 推奨ライブラリ表**に反映
3. ADR 発行は**テンプレート側の大きな方針変更時のみ**（軽微な追加は §7 議論の軌跡のみで可）

#### 5.9.4 既存ライブラリのバージョン更新

- **セキュリティパッチ**: 即時反映（§5.1 参照）
- **マイナー/パッチアップデート**: §5.1 の定期更新で反映
- **メジャーアップデート**: 破壊的変更の可能性があるため、動作確認の上で反映。場合によっては §3 の採用理由に影響がないか再評価

#### 5.9.5 推奨ライブラリの差し替え

既存の推奨ライブラリを他ライブラリに差し替える場合（例: mulog → 新しい構造化ログ系）：

1. **差し替え根拠を明確化**: 現行の何が不足で、新候補の何が優れるか
2. ADR を発行（`adr/NNNN-replace-XXX-with-YYY.md`）
3. **STACK_GUIDE.md §3 の該当節**を更新（採用・採用理由を書き換え）
4. **§8.2 非推奨に旧ライブラリを移動**（推奨代替ありタグ付き、移行方針を記載）
5. **§4.2 の該当 stack**の推奨ライブラリ表を更新
6. **deps.edn** を更新
7. **派生プロジェクトへの影響**: KNOWLEDGE.md への移行ガイド記載を検討

#### 5.9.6 §8.1 禁止ライブラリへの追加

セキュリティ・ライセンス・メンテ停止等の**強い理由**がある場合のみ追加：

1. **事実確認**: CVE 番号、公式声明、ライセンス条項等の**一次資料を確認**（憶測で追加しない）
2. ADR を発行（`adr/NNNN-forbid-XXX.md`）、事実根拠を記載
3. **STACK_GUIDE.md §8.1** に追加（理由タグを §8.0 の標準から選択）
4. 既存の派生プロジェクトで使用されている可能性がある場合、周知が必要

#### 5.9.7 §8.2 非推奨ライブラリへの追加

推奨代替が明確な場合の追加：

1. **代替の実在を確認**（代替が推奨できる状態にあるか）
2. ADR を発行（`adr/NNNN-deprecate-XXX.md`）
3. **STACK_GUIDE.md §8.2** に追加（理由タグ・推奨代替・移行方針を記載）
4. 関連する **§3 検討した代替**表と**§4.2 避けるべきライブラリ**欄を更新

#### 5.9.8 避けるべき改訂パターン

- **根拠なき追加**: 「なんとなく嫌い」「流行りでない」等、一次資料のない判断による追加
- **理由タグなしの分類**: §8.0 理由タグを付けずに追加すると、後続の判断者が根拠を再構築できない
- **§3 と §8 の混同**: §3 は機能別の採用判断、§8 はテンプレート全体の禁止・非推奨。同じライブラリが両方に出るのは正常だが、役割を混同しない
- **§4.2 の「避けるべき」欄の肥大化**: stack 固有の重要な注意のみ記載。汎用的な非推奨は §8 への参照で十分

## 6. 避けるべきアンチパターン

### 6.1 文書の肥大化

**症状**: 「詳細も書いておこう」で CLAUDE.md が 1000 行を超える。
**対処**: CLAUDE.md は常時コンテキストに存在する前提なので、**300 行前後を上限目安**とする。詳細は CODING_GUIDE.md / POLYLITH_GUIDE.md に移す。

### 6.2 規約の形骸化

**症状**: 「書いてあるが守られない規約」が累積する。
**対処**: 原則 2 に従い、規約を追加する時は守らせる手段を同時設計する。手段が設計できないなら規約を削除する。

### 6.3 技術選定の揺らぎ

**症状**: 「より新しいライブラリを見つけた」で選定が変更される。
**対処**: 技術選定の変更は**本文書 §7 への議論記録を伴う**。議論なき変更は禁止。

### 6.4 サンプルの混入

**症状**: 「これがあると分かりやすい」でドメイン仮定が入ったサンプルが追加される。
**対処**: 原則 6 に従い、サンプルは POLYLITH_GUIDE.md / CODING_GUIDE.md のコード例ブロックに埋め込む。テンプレートファイルとしては配布しない。

### 6.5 自動検証の無効化

**症状**: clj-kondo の警告が多すぎて `:level :off` にしてしまう。
**対処**: 警告が多いなら**コードが間違っている**。規約は緩めない。規約が現実に合っていないと判明した時のみ、本文書 §7 に議論を記録して変更する。

### 6.6 「万全の準備」化

**症状**: 「あれば便利」を追加し続けてテンプレートが肥大化する。
**対処**: 原則 5 に従い、配布物は最小化する。「あれば便利」は文書内コード例に留める。

## 7. 議論の軌跡（主要な設計判断の記録）

### 2026-04: 初版の設計判断

#### 通常版テンプレートと Polylith 版の統合
- **背景**: 当初は小規模プロジェクト向け「通常版」と中規模以上向け「Polylith 版」を並置していた
- **判断**: Polylith 版に統一、通常版は廃止
- **根拠**:
  - 後からの Polylith 移行コストは初期採用より数倍大きい（非対称性）
  - 2 テンプレート併存の保守負荷が実用上無視できない
  - Polylith の最小構成（components 1 + base 1 + project 1）と通常構成の `src/` + `test/` の認知負荷差は小さい
- **却下案**: 通常版を残し、サイズ判断で選ばせる → 原則 9 に照らして判定軸が不十分

#### 第一原理「疲労最小化」の文書最上位配置
- **背景**: 初期案では個別規約（Malli、clj-kondo、Polylith、REPL 等）が並列に列挙され、第一原理が文書に書かれていなかった
- **判断**: CLAUDE.md §1 として「疲労最小化原則」を明示し、三基底原則（全域性・不変性・副作用隔離）と四実装戦略（機械化・ループ短縮・小単位・早期破棄）を配置。各章は「§1.X.Y の実装」として自らを位置づける
- **根拠**: 原則 1（原理を最上位に）、原則 10（議論を残す）
- **却下案**: 原理を省いて個別規約だけで済ます → LLM が未知の状況で原則を外した形式適用に陥るリスク

#### 30 分ルールの具体化（自己停止プロトコル）
- **背景**: 当初は「30 分で止まれ」とだけ書いていたが、LLM に時間感覚はないため機能しない
- **判断**: CLAUDE.md §7 として、ターン数・試行回数ベースの自己停止プロトコルに変換
- **根拠**: 原則 2（規約だけでは守られない）
- **却下案**: 文書で「LLM は 30 分を意識せよ」と強く書く → 時間感覚の欠如は意識では補えない

#### 章順の再整理
- **背景**: 初期案は「Polylith 規約」が §2 にあり、技術スタックより前に置かれていた
- **判断**: 章順を「自動検証不能・影響甚大」を前方に並べ替え。禁止事項 → 技術スタック → 基底原則の実装 → 機械化規約 → poly コマンド → 自己停止プロトコル → 作業プロトコル → REPL → テスト → トラッカー の順
- **根拠**: 原則 8（自動検出されないものを前方に）
- **却下案**: Polylith 先行で構造制約を最初に示す → Polylith 違反は poly check で検出されるため、相対的に後方で良い

#### 配布物の 4 値判断の採用
- **背景**: 初期案では components/user/ などのサンプルを全部配布していた
- **判断**: 「即有効 / コメントアウト / 不配布 / 完全排除」の 4 値判断を採用。必須は即有効、用途依存はコメントアウト、ドメイン仮定は不配布、却下ライブラリは完全排除
- **根拠**: 原則 3（二値判断を避ける）、原則 5（LLM は削除が苦手）、原則 6（サンプルとテンプレートの分離）
- **却下案**:
  - 全サンプル配布 → 架空ドメインが LLM に混入
  - 全サンプル削除 → 標準形の可視性が失われる

#### `dev/user.clj` の配布形態
- **背景**: Web サービス特化か、REPL 汎用か判断が揺れた
- **判断**: 機能単位でコメントアウトして配布。`tn/set-refresh-dirs` は無条件で有効。Malli instrumentation / Integrant ライフサイクル / Portal はセクションごとに独立してコメントアウト。config 関数は placeholder
- **根拠**: 原則 4（「汎用」は相対概念）、原則 3（4 値判断）
- **却下案**:
  - 全部有効で配布 → Integrant 未採用時に動かない
  - 全く配布しない → Malli + Integrant の起動順序を LLM が誤りやすい

#### 3 文書体制（CLAUDE.md / CODING_GUIDE.md / POLYLITH_GUIDE.md）
- **背景**: 単一ドキュメントか分離かの判断
- **判断**: 3 文書体制。CLAUDE.md は常時制約、CODING_GUIDE.md は Clojure 書き方詳細、POLYLITH_GUIDE.md は Polylith 運用詳細
- **根拠**: 配置基準を明示化することで追記時の判断コストを下げる
- **却下案**:
  - 単一ドキュメント → CLAUDE.md が肥大化、読解コストが増加
  - 完全分離（CLAUDE.md を極小化） → 常時制約の参照先が遠のき、規約違反の事前回避が難しくなる

#### 本文書（MAINTAINERS_GUIDE.md）の新設
- **背景**: ここまでの議論で得られた設計原則が、文書本体には断片的にしか残らない
- **判断**: 保守者向けに原則・軌跡・アンチパターンを集約した文書を新設
- **根拠**: 原則 10（議論の軌跡を残す）、テンプレートの時間経過による劣化防止
- **却下案**:
  - CLAUDE.md 内に書く → 日常で読む必要がない情報が常時コンテキストに載る
  - 書かない → 時間経過で原則が失われ、表層模倣のみが残る

#### コメントアウト有効化プロトコルの確立と原則 11 の追加
- **背景**: 「必須即有効 / 用途依存コメントアウト」の 4 値配布判断を採用したが、
  コメントアウトされた要素を**どう有効化するか**のプロセスが未定義だった。

- **発見された不備**:
  - 有効化タイミングの判断基準が LLM にない
  - 有効化前後の整合性チェック手順がない
  - コメントアウト状態の依存バージョン更新プロセスがない
  - セット依存（Integrant と aero、Ring と Integrant 等）の同時有効化ルールがない

- **判断**:
  - CLAUDE.md §6.5 に「コメントアウト要素の有効化プロトコル」を新設（前提確認・セット依存表・有効化手順・整合性チェック・失敗パターン）

- **根拠**: 原則 7（文書の自己整合性）、原則 11（今回新設した原則）
- **却下案**:
  - プロセスを書き足さない → LLM が自力で手順を捏造して中間状態を作る事故が予見される
  - CLAUDE.md に書かず MAINTAINERS_GUIDE.md のみに書く → 有効化は日常作業で発生するため常時参照できる位置が必要

- **背景**: CLAUDE_QUESTIONS.md は「一度の判断のアーカイブ」しか扱えず、

- **根拠**: 原則 13（新設）、原則 7（自己整合性）、原則 10（軌跡保全）、原則 11（判断とプロセスの対称性）

  - 4 層構造（CLAUDE.md + DESIGN.md + project-guide/ + project-memory/）で役割純度が最大化

- **却下案**:
  - ADR を README.md の末尾に短く書く → 初見者が運用ルールの前に定義を知る機会を失う。冒頭が正解
  - CLAUDE.md §0 を維持 → 原則 13 違反（仕様情報が規約文書に混入）
  - README.md を作らない → GitHub 訪問者や初見者が「どこから読むか」を判断できない
  - README.md を DESIGN.md と兼用 → 役割が正反対（内部説明 vs 外部説明）なので同じファイルに置くと混乱
- **副次的発見**:
  - 文書設計には「**内部整合性**」と「**外部親切性**」の 2 方向があり、両者を対として設計する必要がある
  - 業界用語（ADR、Polylith、Integrant 等）を使う時は、その定義が読者に共有されているか確認する規律が必要
  - 原則 13 の遡及適用を前回実施したはずが、CLAUDE.md §0 に仕様情報を残していた不完全さが今回露呈。**遡及適用は 1 回で完結せず、気付きに応じて継続する必要**がある
  - 読者の最初の接触点（README、各ディレクトリの README、冒頭セクション）を原則的に点検する観点を意識する（原則 14 候補として保留。類似事例が積み上がれば原則化を検討）

#### README.md ブートストラップ手順の役割分担明確化
- **背景**: ユーザより「README.md の開始手順は概論として分かるが、**誰が何をするかが不明確**。人間が LLM への指示をできるだけ少ない回数・低負担で行う観点から、必ず人間が行うことと具体的なプロンプト例を示すべき」との指摘

  - 旧 README.md の §開始手順は「時系列の作業一覧」のみで、役割分担・プロンプト例がなかった

  - BOOTSTRAP_GUIDE.md は「LLM 側の詳細手順」だが、人間向けの視点がなかった
  - 原則 11（判断とプロセスの対称性）の観点で、「判断（何をする）」は書かれているが「プロセス（誰がどう動くか）」が欠落
- **判断**:
  - **README.md §開始手順を全面改訂**。ステップ 0〜7 の各ステップに以下 3 項目を明示：
    - 🧑 **人間が決めること・行うこと**（意思決定・確認作業）
    - 🤖 **LLM への指示プロンプト**（コピペ可能、`<...>` で埋めるべき箇所を明示）

- **根拠**:
  - **原則 11（判断とプロセスの対称性）**: 意思決定内容だけでなく、誰がどう動くかまで文書化
  - **疲労最小化（§1）**: 人間の指示回数を削減することで、人間側の認知疲労も最小化
  - **原則 5（LLM は削除が苦手）の対称**: 逆に LLM は「指示されたことを実行」が得意なので、具体的プロンプトを提供する設計が有効
- **却下案**:
  - BOOTSTRAP_GUIDE.md を人間向けに書き換える → LLM の詳細手順と人間向け概要が混ざって両方劣化
  - README.md を現状維持 → 人間の負担が減らない
  - プロンプト例を汎用化（`<...>` なし） → 人間が毎回考える負担が残る
- **副次的発見**:
  - 「**2 視点ある作業は 2 文書で分離する**」のが原則。1 文書に 2 視点を混ぜると両方劣化する
  - README.md は初見者向けの顔だけでなく、**ブートストラップ期間中の人間の作業伴走役**としても機能する
  - プロンプト例を埋め込むことで、文書が**単なる説明書から実行可能なワークフロー**に変わる
  - 疲労最小化原則は LLM 側だけでなく**人間側にも適用される**。人間の指示回数と認知負荷を減らすことは、プロジェクト全体の持続可能性を高める

#### 責務整理による冗長削減
- **背景**: ユーザより「各文書の担当領域と関係を明確化することで冗長を減らし、保守負担を下げられる」との指摘。要素追加を重ねた結果、同一情報が複数文書に分散していた
- **発見された冗長**:
  - 4 種文書の運用規定が CLAUDE.md §11、各文書 §0、COLLABORATION_GUIDE §6 の 3 箇所に類似記述
  - 編集権限が CLAUDE.md §2、CLAUDE.md §11.3（旧）、COLLABORATION_GUIDE §2.3 の 3 箇所
  - 昇格先判定が QUESTIONS.md §0.5、CLAUDE.md §11.2（旧）、COLLABORATION_GUIDE §6.2 の 3 箇所
  - 仕様曖昧性点検が CLAUDE.md §8.0、COLLABORATION_GUIDE §4.2 の 2 箇所

  - **CLAUDE.md §11 を簡素化**: サイクル図（羅針盤として保持）、4 種文書の一覧と参照先、LLM の複数役割のみに絞る。詳細運用は各文書 §0 へ参照委譲

  - **COLLABORATION_GUIDE §6**: サイクル図・役割定義・シナリオの再掲を削除し、協働特有の観点（起票時の留意点、具体プロンプト例）のみに絞る

  - **DESIGN.md §0 を新設**（**案 D**）: 本ファイルの埋め方、セクション区分、埋める順序と担当、曖昧性指摘、仕様成熟 3 段階、改訂ルールを統合

  - Q 運用プロセス詳細 → `QUESTIONS.md` §0 のみ
  - KNOWLEDGE ライフサイクル詳細 → `KNOWLEDGE.md` §0 のみ
  - ADR 運用ルール詳細 → `adr/README.md` のみ
  - 編集権限マトリクス詳細 → `COLLABORATION_GUIDE.md` §2.3 のみ

  - **原則 12（遡及適用）**: これまでの要素追加で既存体系との冗長が蓄積していた。遡及点検による全体整理

  - サイクル図を COLLABORATION_GUIDE.md に移動 → CLAUDE.md は毎セッション読まれる羅針盤。図は常時参照できる位置に置くべき（**ユーザ判断で保持**）

  - DESIGN.md §0 を新設せず README.md に残す → ブートストラップ時以外の改訂時に参照されない、埋め方ガイドが一元化されない

- **副次的発見**:
  - **新要素を追加するより冗長を削るほうが本質的改善になる局面がある**。時間経過で冗長は必ず不整合を生み、保守コストを累積的に増やす
  - **「一次情報源」の明示は設計文書において最も重要な規律の一つ**。「どこに真実を書くか」を決めるだけで、多重記載の誘惑を構造的に抑止できる
  - 原則として立てることを当初検討したが、後の議論で再評価し原則化を見送った（次の軌跡項目参照）

#### 「整理優先の姿勢」の配置判断と原則化の見送り
- **背景**: 前項の改訂で「新規追加より整理を優先」を**原則 14 または 15 として立てる可能性**を残していた。ユーザより「これは原則として置くべきものか、位置が違う気がする」との問い
- **検証**:
  - 原則 1〜13 はすべて**テンプレート設計の判断基準**（対象レベル）を扱う
  - 「整理優先」は**判断基準群を適用する時の心構え**（メタレベル）であり、階層が違う
  - 原則化すると以下の弊害：原則群の階層的一貫性が崩れる、同種の姿勢論を次々追加したくなり原則の墓場になる、「整理せよ」はトートロジーで判断基準として機能しない、原則 7・12 との実質的重複
- **二つ目の観察（ユーザ指摘）**: 「整理優先」は**文書保守とコード保守の両面で有効**である。同一思想だが領域が違う
  - 文書保守: 冗長削減、責務純化、参照化、一次情報源の明示
  - コード保守: DRY、YAGNI、KISS、既存活用、関数分割、共通化
  - 両面を一つの原則に混ぜると混乱するが、完全に分離すると同一思想である認識が失われる
- **判断**:
  - **原則として立てない**。§4 原則群の階層的純度を守る
  - **領域ごとに分離配置し、相互参照で両面を示す**（案 1）:

#### 推奨カタログ方式への再移行（`:stack/*` エイリアス方式 → 文書配布方式）
- **背景**: 段階 2 で `:stack/*` エイリアス方式を採用したが、実作業シミュレーションで重大な構造的問題が露呈：
  - **Polylith の brick deps.edn 構造との不整合**: Polylith は brick（base / component）の独立性を設計思想として持ち、各 brick は独自の deps.edn を持つ。本番ビルドは `projects/<deploy>/deps.edn` → `bases/.../deps.edn` → `components/.../deps.edn` の連鎖で依存解決される。ルートの `:stack/*` エイリアスは REPL 開発用にすぎず、**stack 層ライブラリが brick deps.edn とルート deps.edn の二重管理**になる
  - **STACK_GUIDE.md §3.6 と §4.2.3 の不整合**: Web API で DB を使う典型ケース（next.jdbc を §3.6 は web-api stack でも採用としているが §4.2.3 推奨ライブラリに含まれない）で LLM が判断に詰まる
  - **本番ビルド用 base deps.edn の指示不在**: BOOTSTRAP_GUIDE.md が stack エイリアスの採用しか扱わず、base deps.edn をどう書くかの具体的指示がない
- **ユーザからの本質的指摘**:
  - **「真実は一箇所にまとめたい」**: DRY 原則の深い解釈。同じライブラリ依存がルート deps.edn と brick deps.edn の両方に書かれるのは知識の重複
  - **「stack だけ特別扱いは変」**: 外部依存ライブラリは stack 所属かどうかで本質が変わらない。`:stack/*` エイリアス方式は stack 層のみ特別な構造を持たせる歪みを生んでいた
  - **「推奨ライブラリの完全一致を求めるのは間違い、漏れ検出は意味あり」**: 検証の種類を区別。stack 推奨の強制は不適切だが、機能カテゴリ充足や設定ファイル漏れの検出は価値がある
- **検討した選択肢（A〜H）**:
  - **A**: 現状維持（`:stack/*` エイリアス + brick deps.edn の二重管理受容）— 真実の一箇所化に反する、却下
  - **B**: brick deps.edn を最小化、`:local/root` 継承で統合 — Polylith の brick 独立性を崩す、却下
  - **C**: brick の deps.edn を component 間参照のみに、ライブラリは projects に集約 — 同上、却下
  - **D**: `:stack/*` エイリアス完全廃止、STACK_GUIDE.md は純粋な推奨カタログ — 方向性として採用候補
  - **E**: brick deps.edn 最小化 + `:local/root` 継承 — B と同質
  - **F**: Polylith の公式機能で解決 — 公式機能に該当機構なし、却下
  - **G**: 機械的強制検証スクリプト — 初版では過剰、継続充実で後日
  - **H（採用）**: stack エイリアス廃止 + brick deps.edn 一次情報源 + STACK_GUIDE.md は推奨カタログ
- **旧コメントアウト方式への回帰検討（ユーザ提案）**:
  - 段階 2 で廃止した旧方式を再評価：「真実は一箇所にまとめたい」に反する（ルート deps.edn にコメントアウトで置くとブートストラップ時に brick に移動する作業が発生、その時点で一時的に両方に存在）
  - 旧コメントアウト方式は「deps.edn に配布標準形を物理的に示す」点で魅力的だが、一次情報源の分散を招く
  - ユーザ判断「**真実は一箇所にまとめたい、Hのほうが好き**」で選択肢 H を採用決定
- **概念レベルと実装レベルの分離**:
  - **レベル 1: 実装としての `:stack/*` エイリアス（deps.edn の機能）** → 廃止
  - **レベル 2: 概念としての分類（文書上の推奨構成の分類名）** → 維持
  - `:stack/*` というキーワード記法は実装を示唆するため廃止し、「web-api stack」「batch stack」等の非キーワード表記に変更
  - 段階 1 の成果（10 種分類、15 機能領域、禁止・非推奨の分離、理由タグの標準化）は推奨カタログとして維持
- **検証の方針（ユーザ指摘を反映）**:
  - **推奨一致の検証は不適切**（推奨は推奨であって強制ではない、逸脱は ADR で記録）
  - **漏れの検証は適切**（edn 設定は漏れがち、機能カテゴリ充足と設定ファイル存在のチェックは価値あり）
  - 実装方法: 各 stack の §4.2.X に「採用時の確認事項」を文書化（機能カテゴリレベル、具体ライブラリ名の強制なし）
  - 機械化（Babashka タスク等）は継続充実項目として後日
- **判断（段階 5 として実施）**:
  - **deps.edn の全面改訂**: `:stack/*` エイリアス 10 種を全廃、必須層（Clojure、Malli）のみ残す。`:dev` は REPL 駆動専用（tools.namespace）、運用エイリアス（`:nrepl`、`:test`、`:poly`、`:lint`、`:format`、`:outdated`）のみ維持

  - **STACK_GUIDE.md §1.2 本文書の性格**: 「推奨カタログ」「真実の一箇所化」の節を新設、brick deps.edn が一次情報源である旨を明示

#### 段階 5 後の実作業シミュレーション検証（選択肢 H の動作保証強化）
- **背景**: 段階 5 完了後、再度実作業シミュレーションを実施（inventory-service、web-api stack + dev-tools stack + PostgreSQL 使用）。前回検出の 6 問題（概念的設計整合性）はすべて解消を確認。ただし**技術的動作レベル**で新たに 4 件の問題を検出
- **検出された問題**:
  - **問題 A（中程度）**: BOOTSTRAP_GUIDE.md §2.5 で development の `:dev :extra-paths` に brick ソースパスを追加する指示はあるが、`:dev :extra-deps` に brick を `:local/root` 登録する指示が欠落。tools.deps の仕様では `:extra-paths` はパスの追加のみで、そのパスにある deps.edn の `:deps` は自動解決されない。選択肢 H の「brick deps.edn を一次情報源」方針では、development が brick を `:local/root` で依存登録し、推移的解決させる必要がある。これを忘れると `ClassNotFoundException: integrant.core` 等のエラーで REPL 起動失敗
  - **問題 B（軽微）**: config.edn 読み込み方法が本番（`io/resource`）と開発（`io/file "projects/<deploy>/resources/config.edn"`）で異なる。本番と開発で統一したほうが整合性が高い
  - **問題 C（軽微、B と関連）**: §2.5 の `:dev :extra-paths` 追加項目に `projects/<deploy>/resources` が含まれていない。これがあれば両方で `io/resource` に統一可能
  - **問題 D（軽微、A と関連）**: §5.3 失敗時の対処リストに brick 依存解決失敗（ClassNotFoundException）のケースが不在。問題 A が発生時に LLM が対処法を見つけられない
- **判断**: 修正方針として選択肢 2（暫定対応）を採用
  - 問題 A は REPL 起動に直接影響する可能性が高く、修正内容（brick の `:local/root` 登録）は tools.deps の基本機能で確信度 80%
  - 実プロジェクトでの起動検証は別途必要だが、動作保証を強化する暫定対応として各文書の指示を更新
- **修正内容（段階 5 補遺として実施）**:
  - **BOOTSTRAP_GUIDE.md §2.5**: `:dev :extra-deps` に brick を `:local/root` 登録する指示を追加、`:dev :extra-paths` に `projects/<deploy>/resources` を追加する指示も明記、「なぜ `:local/root` 登録が必要か」の説明追加
  - **BOOTSTRAP_GUIDE.md §5.3**: よくある失敗に「ClassNotFoundException（brick 依存未解決）」「FileNotFoundException: config.edn」を追加、§2.5 への導線を明示
  - **deps.edn の `:dev` エイリアスコメント**: brick の `:local/root` 登録手順、`projects/<deploy>/resources` の追加指示、dev-tools stack 採用時の追加を明示。選択肢 H との関係を明示
  - **POLYLITH_GUIDE.md §2.4**: config 関数実装例を `io/resource` ベースに変更、`projects/<deploy>/resources` が `:dev :extra-paths` にある前提を明示、ファイルパス代替も残す
  - **POLYLITH_GUIDE.md §3.1**: 新規 brick 追加時の手順 6 として `:dev :extra-deps` への `:local/root` 登録を追加
  - **POLYLITH_GUIDE.md §7.2**: 新規 brick 追加時の development 更新を 2 箇所（`:extra-paths` と `:extra-deps`）に分けて明記、両方の忘却による失敗症状を明示
  - **POLYLITH_GUIDE.md §7.3**: development の `:dev :extra-deps` への追加は「開発ツール」と「brick の `:local/root` 登録」の 2 種類のみと明確化
  - **STACK_GUIDE.md §5.2**: brick deps.edn への推奨ライブラリ反映手順のステップ 6 として `:local/root` 登録を追加
- **根拠**:
  - 原則 1.2.1（機械化）: 手順書による規律だけでは守られないため、`:local/root` 登録忘れを症状から診断できる指示を明記
  - 原則 7（文書の自己整合性）: BOOTSTRAP_GUIDE・POLYLITH_GUIDE・STACK_GUIDE・deps.edn の指示を統一
  - 原則 12（遡及適用）: 新方針（選択肢 H）による新しい失敗モード（brick 依存未解決）を文書体系全体に反映
- **副次的発見**:
  - **概念的設計整合性と技術的動作保証は別次元の検証**: 文書上の整合性（grep で検出可能）と、実際に動作するかの検証（実装を走らせる必要）は異なる層の問題。今回のシミュレーションで前者は解消していたが後者が漏れていた
  - **tools.deps の `:extra-paths` と `:extra-deps` の役割分離**: パス追加と依存解決は別機能。これを暗黙視するとハマる。文書上で明示的に区別する必要あり
  - **実地検証の必要性**: 推測による「動くはず」は 100% でない。MAINTAINERS_GUIDE.md §5.6.2 動作検証（年 1 回）の範囲を超えて、**初回配布前の動作検証**も別枠で必要。ただし本セッションのスコープを超えるため、Docker / GitHub Actions での実環境検証は別機会
  - **Polylith 公式慣用の確認**: 今回の修正（brick の `:local/root` 登録）は私の 80% 確信度での対応。Polylith 公式リポジトリの RealWorld 実装等で実際の慣用を確認し、必要に応じて修正する余地がある

#### stack 表の位置づけの明確化（判断結果のメモリーとしての性格）
- **背景**: 異分野のシミュレーションテスト（ML、ゲーム、ビジネスダッシュボード GUI）で「stack 表に未記載の領域に遭遇した LLM の動き」が議論に。stack 表のカバレッジ不足（ML stack や game stack の不在、データ可視化節の不在等、計 12 問題）が検出された
- **当初の誤った方向**: 検出された 12 問題への対処として、以下を順に提案してしまった
  - 案 1: 新 stack 追加（ML stack、game stack 等）と機能領域 §3 の拡充 → **stack 網羅性の追求**
  - 案 2: スコープ制限を明示（ML・ゲームは対象外と宣言） → Clojure + Polylith のせいにする誤り
  - 案 3: 未知への対処手続きを体系化（意思決定フロー、Q 雛形等） → **手続き網羅性の追求**（stack から手続きに対象を変えただけ、同じ誤り）
- **深い誤り診断**（ユーザ指摘により自己認識）:
  - 本テンプレートの第一原理は疲労最小化。**網羅の追求自体が疲労を生む**（網羅は永久に達成不可能な性質のもの）
  - Clojure + Polylith を採用した理由は「LLM が自律的に低負担で実装できる」ためで、適用分野とは独立。分野のせいにするのは誤り
  - stack・コード・技術選定は**すべて同じ原則（疲労最小化 + 三基底原則）から導出される**。原則は既に存在するので、あとは**未記載領域でも原則から導出する能力**を明示すれば足りる
  - 「補助」と位置づけるのも誤り。stack 表は単なる補助ではなく、**予め判断を済ませた結果のメモリー**として積極的価値を持つ
- **ユーザ指摘の核心**: 「stack 表は毎回複雑な判断をしないで済むようにするためのメモリー情報。stack 表の特性とプロジェクトのゴールが矛盾しないなら stack 表の利用は本件目的と矛盾しない。stack・コード・技術選定は全て同じ原則に従うだけ」
- **判断**: 以下の最小改訂で対処
  - **STACK_GUIDE.md §1.2**: stack 表を「判断結果のメモリー」として位置づけを明示。利用規律（矛盾しないなら信頼して利用、未記載領域は原則から導出、網羅を目的化しない）を記載
  - **CLAUDE.md §6.5.1**: stack 表の利用と原則からの導出の関係を 1 節で明示。両者は排他的でない。未記載領域でも第一原理から導出できる
  - **12 問題の個別対処は不要**: 原則からの導出で扱える問題として位置づけ
  - **新 stack・新機能領域の追加は不要**: 必要になった領域が原則からの導出を経てユーザ合意に至った時、メモリーに記録する（この順序を守る）
- **根拠**:
  - **自己適用性**: 本テンプレートの原則は本テンプレート自身の設計にも適用される。網羅の追求は疲労を生むため、それ自体が第一原理に反する
  - **AND 発想**: 「網羅か原則か」の二者択一ではなく、「メモリー（判断済み結果の記録）+ 原則からの導出（未記載への対処力）」の両立として枠組みを再構築
  - **Clojure + Polylith 採用の本質**: LLM の自律的・低負担実装を支える構造（brick 独立性、Malli 契約、data 駆動、全域性）は、適用分野に依存せず原則からの導出を可能にする土台として機能する
- **副次的発見**:
  - **メモリーと網羅の違い**: メモリーは「知っていることを記録する」、網羅は「全てを記録しようとする」。性格が全く異なる。前者は疲労最小化に貢献し、後者は疲労を生む
  - **網羅主義からの脱却は繰り返し発生する誘惑**: 私（設計者 / LLM）は 3 回連続で「何かを追加する」方向に走った（stack 追加、スコープ制限、手続き体系化）。自己適用性の規律を明示することで、今後の保守でも網羅主義への回帰を防ぐ
  - **シミュレーションの真の価値**: 異分野シミュレーションは stack 表の網羅性の問題ではなく、**設計哲学の自己矛盾**を炙り出す機能を持った。検出された 12 問題は「対処しない」が、検証プロセスとしては極めて有効だった
  - **「然程難しくない」の意味**: 原則が既に書かれている以上、必要なのは「それを未知への対処の拠り所として明示する」ことだけ。新規の規約・フロー・網羅を書く必要はない。これこそ疲労最小化に従った改訂姿勢
- **MAINTAINERS_GUIDE.md §9 姿勢セクションへの追加**: 本件の洞察を原則化した「自己適用性」の項を追加（§9.4）。今後の保守で「また網羅を足したくなる」誘惑への予防線

#### DESIGN.md の改訂方針の明確化（全面書き換え、差分表記なし）
- **背景**: 「実装中または実装後に仕様変更・追加がある場合の開発者の動き方」に関する質問。現状の文書に仕様変更手順の導線が明示的になく、また DESIGN.md §11 変更履歴という節が存在することで「DESIGN.md 内に履歴を残す」方針とも解釈できる状態だった
- **判断**: DESIGN.md は**現在の仕様の一次情報源**として機能する。変更履歴は本ファイル内に残さず、ADR・git・QUESTIONS.md アーカイブで保全する。改訂時は該当節を**全面書き換え**する（追記・差分表記にしない）
- **根拠**:
  - **原則 13（4 種文書分離）**: DESIGN は「何を作るか（現在形）」、ADR は「なぜ決めたか（不変の履歴）」、KNOWLEDGE は「現在有効な契約」、QUESTIONS は「判断保留」。履歴は ADR の責務であり DESIGN の責務ではない
  - **KNOWLEDGE.md §0.5 との対称性**: KNOWLEDGE は既に「上書きを恐れない、過去の内容は残さない」方針。DESIGN も同じ性格（現在を示す文書）なので同じ原則が適用される
  - **原則 7（文書の自己整合性）**: 履歴と現在形が混在すると「今何が有効か」の判定コストが増大
  - **疲労最小化**: 追記方式は時間と共に肥大化し、読み手が「古い記述と新しい記述」を区別する疲労を生む
  - **軌跡保全の十分性**: ADR（判断経緯）+ git（差分）+ QUESTIONS アーカイブ（未決事項の経緯）で軌跡は完全に保全される。DESIGN.md 内の履歴は冗長
- **判断の帰結として実施した修正**:
  - **CLAUDE.md §8.5 追加**: 仕様変更・追加への対処フロー（6 ステップ）。関連文書への導線明示。新規章ではなく §8 作業プロトコルの一節として配置（網羅主義を避ける）
  - **DESIGN.md §0.5 改訂**: 旧「§11 変更履歴に記録」を「ADR・git・QUESTIONS.md で保全、本ファイル内に履歴を残さない」に変更
  - **DESIGN.md §11 変更履歴の削除**: 旧方針の名残を廃止
  - **DESIGN.md 冒頭補強**: 「現在の仕様の一次情報源、変更履歴は本ファイル内に残さない」と明示
- **副次的発見**:
  - **導線整備と網羅主義の境界**: §8.5 追加は網羅主義か導線整備か。判断基準は「新規情報を書くか、既存リソースへの参照を書くか」。§8.5 は 6 ステップすべて既存文書の責務を引用する構成で、既存情報への導線整備として正当化される（§9.4 自己適用性の範囲内）
  - **文書間整合性の自己点検**: 今回、既存 §11 変更履歴の存在に気づいたのはユーザ質問への回答準備中。定期的に文書間の運用ルール整合性を点検する規律の価値を再確認（§5.9 の類似点検プロセス）
  - **ユーザ質問の検証機能**: 「DESIGN.md を全面書き換えしていいか」というご質問は、単に確認の意図を持っただけでなく、**文書体系の運用ルールが自己整合しているかの検証**にもなった。ユーザ質問が設計検証の機能を果たす構造は、LLM-人間協働の独特の強み

#### 文書体系の構造的整合性の再点検と修正（ユーザ質問による発見）

- **根拠**:

  - **予防策の限界**: 今回発見された 4 問題はすべて過去の遡及適用漏れに起因する。完璧な予防策は存在せず、**定期的な点検**が必要。ただし点検それ自体が網羅主義に陥らないよう、**機械的な基本確認**（節番号連続性、参照先実在性、見出しと内容の一致、ファイル構成図の網羅性）に絞るのが原則 9（整理優先）との整合

## 9. 本文書の保守

本文書自身の更新時は：

- §7 の「議論の軌跡」には必ず追記する（原則 10）
- 新しい原則を §4 に追加する場合、連番を続ける（§4.原則 13, 14, ...）
- **原則を追加した場合、原則 12 に従い全文書への遡及適用を必ず実施する**
- 原則の削除・改訂は慎重に。変更前の版を §7 に追記する
- CLAUDE.md 冒頭からの参照リンクを維持する

### 9.1 原則 12 遡及適用の実施手順

新原則を §4 に追加した場合：

1. **全文書リストで点検対象を確定**:
   - ルート: README.md、CLAUDE.md、DESIGN.md
   - project-guide/: CODING_GUIDE.md、POLYLITH_GUIDE.md、STACK_GUIDE.md、COLLABORATION_GUIDE.md、BOOTSTRAP_GUIDE.md、本文書
   - project-memory/: QUESTIONS.md、KNOWLEDGE.md、adr/README.md、adr/template.md、既発行 ADR
2. **各文書を新原則で読み直し、違反箇所を洗い出す**
3. **違反一覧を表にまとめ、「修正コスト × 修正効果」で判定**（全体として改善するか）
4. **修正実施。単独追記ではなく既存体系の改善として統合実施**
5. **点検結果と修正内容を §7 議論の軌跡に記録**

このプロセスは「原則を増やすだけでなく、既存体系を新原則で再評価する」作業である（原則 12 本文参照）。

**機械的検索の活用**: 遡及適用時は**推測による影響範囲判断を避け、`grep -rn` 等で該当箇所を網羅確認**する。実例として stack 概念導入時、既存文書の「Integrant」「コメントアウト」「§6.5」等の言及箇所を grep で確認し、影響範囲（9 ファイル・58+ 箇所）を正確に把握できた。LLM は「意識的に機械的確認を行う」規律を持たないと、知識の穴を推測で埋める傾向がある。

**注意**: 遡及適用は 1 回で完結しない。気付きに応じて継続的に再点検する。実例として原則 13 追加時の遡及適用で CLAUDE.md §0 の仕様情報残存を見落とし、後日の README.md 新設時に併せて修正した。

### 9.2 構造的対称性への気付き

ファイル・文書の配置において、**対称性や一貫性の欠落に気付いたら即時に解消する**。
原則追加時でなくても、既存体系の対称性を高める機会は逃さない。
実例：当初 `CLAUDE_QUESTIONS.md` のみルート直下だった配置を `project-memory/` 対称配置に修正、
`docs/` への違和感から `project-memory/` と `project-guide/` の対称構造に再編成。
これらは新原則追加ではなく、構造的直感に基づく改善であった。

### 9.3 保守作業における姿勢：整理優先（開発・保守共通）

> 「新規追加より整理を優先する」という姿勢は、**文書とコードの両面で有効**であり、本テンプレートの品質維持の両輪をなす。
> コード側の具体化は `CODING_GUIDE.md` §2.4 を参照。本節は文書側を扱う。

#### 9.3.1 基本姿勢

文書に何かを**加える前に、既存文書を点検する**。以下の順序で判断：

1. **既存の節・記述・参照関係で実現できないか** → できるなら追加しない（YAGNI）
2. **既存の記述を整理すれば実現できないか** → そちらを優先
3. **新しい節・文書が本当に必要か** → 必要性を議論（原則 13 の 4 種文書分離に照らす）
4. **上記を経て必要と判断されたものだけを追加する**

この姿勢は原則 7（文書の自己整合性）の**実装技法**であり、原則 12（遡及適用）を実施する時の**心構え**でもある。

#### 9.3.2 具体場面

**場面 A: 新しい節を追加したい時**

- 既存節で扱うべき内容ではないか確認
- 既存節の拡張で済まないか検討
- 本当に独立した節が必要なら追加

**場面 B: 新しい原則を立てたい時**

- 既存原則 1〜13 のどれかで説明できないか確認
- 既存原則の延長・実装技法として位置づけられないか検討
- **原則群の階層を崩す概念**（判断基準レベルではない姿勢論・方法論）は原則として立てない（本節の新設もその判断の結果）
- 既存原則の深い運用で対応できないなら、原則 12 遡及適用を経て新原則として追加

**場面 C: 同じ情報を複数箇所に書きたい時**

- **DRY 違反の予兆**。どこを**一次情報源**とするか決める
- 他の文書は一次情報源への参照のみを持つ
- 情報の実効性が分散で高まる場合に限り、意図的な冗長を許容する（例: CLAUDE.md §11.2 サイクル図）

**場面 D: 既存文書の役割が曖昧になってきた時**

- 責務の再確認。4 種文書分離（原則 13）、project-guide / project-memory の区分に照らす
- 複数の責務が 1 文書に混在しているなら分割を検討
- 同じ責務が複数文書に分散しているなら統合を検討

#### 9.3.3 整理の具体手法

| 手法 | 適用場面 | 注意点 |
|---|---|---|
| **一次情報源の明示と参照化** | 同一情報が複数箇所にある | どこを真実の源とするか明確に決める |
| **節の統合** | 責務が重複する節が分散 | 原則 10（議論の軌跡）を壊さない |
| **節の分割** | 1 節が複数の責務を担っている | 分割後も相互参照で全体像を見失わない |
| **参照表の整備** | 文書間の関係が追いにくい | `CLAUDE.md` 冒頭の参照表のような集約点を作る |
| **非推奨化と削除** | 古くなった記述 | 削除時は §7 議論の軌跡に経緯を残す |

#### 9.3.4 整理のタイミング

- **新機能・新原則追加の着手前**: §9.3.1 の判断フローを必ず適用
- **原則 12 遡及適用時**: 追加よりも整理の機会を先に点検する
- **文書改訂依頼を受けた時**: 改訂と同時に冗長削減の機会がないか探す
- **テンプレート統合検証時（§5.6.2）**: 年 1 回の検証で全体の整理機会を点検

#### 9.3.5 整理を避けるべき場面

整理優先は原則だが、**例外もある**：

- **変化が激しい議論の最中**: まだ収束していない論点の早期整理は後戻りを招く
- **原則 5（LLM は削除が苦手）への配慮**: LLM による大規模整理は誤削除リスクが高い。人間レビュー必須
- **原則 10（議論の軌跡）との競合**: 古い記述でも議論の軌跡として価値がある場合、削除より保持を優先

**整理が整理のための整理にならないよう**、常に「この整理は将来のどの保守負担を防ぐか」を自問する。

#### 9.3.6 本節と原則 7・12 との関係

- **原則 7（文書の自己整合性）**: 本節は原則 7 の実装技法。自己整合性は整理を通じて維持される
- **原則 12（遡及適用）**: 遡及適用時は**追加よりも整理の機会を先に点検**する。本節は原則 12 の実施姿勢でもある
- **原則として独立させていない理由**: 本節は**判断基準**ではなく**姿勢・方法論**。原則群の階層的性格（テンプレート設計の判断基準）とは階層が異なるため、原則ではなく §9 保守姿勢の節として配置した（§7 議論の軌跡の該当エントリ参照）

### 9.4 自己適用性：テンプレートの原則はテンプレート自身の設計にも適用される

本テンプレートの原則（疲労最小化、三基底原則、13 原則）は、**テンプレート自身の設計にも適用される**。テンプレート保守者が新規の規約・stack・手続き・網羅を追加しようとする時、その追加自体が原則に反していないかを必ず点検する。

#### 9.4.1 具体的な陥穽

以下の動きは原則違反の典型：

- **網羅の追求**: stack 表、機能領域、手続きリスト等を「すべて書き尽くそう」とする動き。網羅は永久に達成不可能（疲労最小化と自己矛盾）。**メモリーは「知っていることを記録する」、網羅は「全てを記録しようとする」。性格が全く異なる**
- **形式的な当てはめ**: 判断基準を第一原理に求めず、「stack 表にあるか」「手順書にあるか」で判断する動き。LLM が未記載領域で思考停止する
- **分野のせいにする**: 「ML は Clojure に向かない」「ゲームは JVM に向かない」等の分野スコープ制限で問題を転換する動き。本テンプレートの採用理由は分野とは独立（LLM の自律的低負担実装）
- **手続きの肥大化**: 「未知への対処フロー」「Q の雛形」等を事前に網羅する動き。網羅対象が stack から手続きに変わっただけで、同じ誤り
- **二重管理の放置**: 同じ情報を複数箇所に書く動き。真実の一箇所化（選択肢 H で確立）に反する

#### 9.4.2 点検の自問

新規追加を検討する時、以下を自問する：

1. この追加は**網羅を目指す動き**になっていないか
2. 第一原理から導出すれば、この追加なしで解決できないか
3. 追加による**保守コスト**は、得られる便益を上回らないか
4. 追加内容は**判断済み結果のメモリー**か、それとも**網羅の追求**か
5. 同じ情報が他の場所に既に存在しないか（二重管理のリスク）

自問の結果、追加が正当化されない場合、**追加しない**という判断が正しい。

#### 9.4.3 本節が §4 原則ではなく §9 姿勢に置かれる理由

自己適用性は**原則間の関係を律する姿勢**であり、**判断基準としての原則**とは階層が異なる。原則 12（遡及適用）が「既存文書への原則の適用」を扱うのに対し、本節は「テンプレート設計自身への原則の適用」を扱う。両者は補完関係にあるが、位置づけは異なる。

#### 9.4.4 §7 議論の軌跡との関係

本節の規律は、§7 議論の軌跡に記録された「設計者が同じ誤りを繰り返した経緯」から導出された。網羅主義への誘惑は**繰り返し発生する**ため、議論の軌跡での記録だけでは防げない。保守姿勢として明文化することで、将来の保守者（人間・LLM）への予防線として機能する。
